# 需求拆解

## 一句话定义
把一段模糊的产品想法，拆成「必须做 / 可选做 / 硬约束 / 信息缺口」四张清单的过程——它是原理图之前真正的第 0 步，比画电路重要。

## 它解决什么问题 / 为什么存在
新手拿到"做个温控风扇"就直接开画，结果画到一半发现要 WiFi 却没留串口、要 12V 电机却只设计了 5V 电源。需求不拆，原理图必返工。拆解把"感觉"变成"可检查的条目"。

## 核心原理（大二能懂的水平）
拿到需求，先问六件事，缺的标「待确认」：
- 功能：这东西到底要干嘛（测温？控温？上报？）
- 指标：精度(±1℃?)、速率(1Hz?100Hz?)、功耗(电池续航?)、容量
- 供电：电池 / USB / 适配器，电压电流各多少
- 接口：要和谁通信（UART/I²C/SPI/USB/无线），速率多少
- 尺寸形态：板子多大、什么形状、要不要塞进外壳
- 环境：温度/湿度/是否便携/是否工业干扰

拆完后分三类：
1. 必须实现（MUST）—— 不做就不叫这产品
2. 可选实现（NICE）—— 有空再加
3. 硬约束（CONSTRAINT）—— 电压域、最大电流、信号速率、温区、尺寸上限，直接框死后面选型

## 关键参数 / 易错点
- **易错**：只记功能不记指标 → "要通信"不说速率，选型时 UART 够不够不知道。
- **易错**：不写信息缺口 → AI/自己默认假设，做完才发现货不对板。
- **易错**：把 NICE 当 MUST → BOM 爆炸、板子画不下。

## 类比（帮助理解）
像接外包：客户说"做个网站"，你得反问他要注册吗、要付钱吗、多少人用、什么时候上线——不问清就开工，必返工。

## 设计时怎么用（反推思维）
模糊需求 → 六问清单 → MUST/NICE/CONSTRAINT 三分 → 每条约束变成后面选型的硬指标（如"最大电流 2A" → 电源芯片必须 ≥2A）。

## 典型应用
任何从零开始的板子：温控风扇、数据采集节点、毕业设计主控板。
