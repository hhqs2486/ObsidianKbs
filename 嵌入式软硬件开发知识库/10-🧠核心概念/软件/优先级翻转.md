# 优先级翻转

## 一句话定义
> 优先级翻转（Priority Inversion）是 RTOS 中高优先级任务因等待低优先级任务持有的共享资源而被阻塞，导致**中优先级任务先于高优先级任务执行**的异常现象。

## 它解决什么问题 / 为什么存在
- 这个问题不能"解决"（它是优先级调度 + 资源共享的固有矛盾），只能**缓解**
- FreeRTOS 提供互斥量的**优先级继承**机制来缓解翻转
- 理解它才能诊断"为什么我的高优先级任务偶尔延迟异常大"的 bug

## 核心原理（大二能懂的水平）
- 前提：三个任务 H（高优先级）、M（中优先级）、L（低优先级），H 和 L 共享一个锁
- 翻转三步骤：
  1. L 拿到锁，开始干活
  2. H 就绪 → 试图拿锁 → 失败（L 占着）→ H 阻塞等锁
  3. M 就绪 → M 优先级 > L → M 抢占 L 的 CPU
  4. **此时**：M 在跑，H 在等 L，L 在等 CPU（被 M 抢了）→ 倒挂了！
- 本质：调度器只知道优先级、不知道锁依赖；H 被 L 间接阻塞，但 M 能畅通无阻
- 危害：H 的响应延迟 = L 的临界区时间 + M 可能执行无数轮的时间（不可控）

## 关键参数 / 易错点
- **信号量没有优先级继承**：FreeRTOS 的二值/计数型信号量不带优先级继承，做互斥必须用 `xSemaphoreCreateMutex()` 创建的互斥量
- 优先级继承是**临时且递进的**：H 等 L → L 的优先级被抬到 H；如果 L 又等 L2 的锁 → L2 也被抬到 H——可以递归继承
- L 释放锁后优先级**立即恢复原值**
- 优先级天花板协议（另一种方案）：所有访问共享资源的任务统一设最高优先级——简单粗暴但牺牲调度灵活性
- 锁持有时间越短越好：临界区越短，翻转窗口越小

## 类比（帮助理解）
- 高速公路收费站：大货车（低优先级 L）先进了唯一通道（拿锁），一分钟后救护车（高优先级 H）来 → 等；这时普通小轿车（中优先级 M）从旁边应急车道超到货车前面排队——结果 M 先过，H 卡在货车后面
- 优先级继承 = 收费站给大货车临时挂"救护车优先"牌子，让它优先通过

## 设计时怎么用（反推思维）
> 如果这条知识能用于「从需求到设计」，在这里写一句：做 XX 设计时，我会用它能解决 YY。
- 做任何涉及多任务共享资源的系统设计时：凡是互斥访问都用 [[互斥锁 Mutex]] 而非 [[二值信号量]]——即使"够用"也预留优先级继承
- 做实时性敏感的设计时：审查所有共享锁的持有时间，超过 1ms 的考虑拆分成更小的临界区

## 典型应用 / 我在哪见过
- 1997 年火星探路者（Pathfinder）事故：气象数据采集任务（低优先级）持有 SPI 总线锁时间过长，导致高优先级通信任务被中优先级任务严重延迟，系统反复复位——NASA JPL 通过远程打补丁启用优先级继承修复
- 任何用 SPI Flash + GUI 的系统：文件系统操作（低优先级）占锁 → UI 渲染（高优先级）卡死
