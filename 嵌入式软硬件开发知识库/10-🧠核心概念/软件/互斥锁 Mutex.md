# 互斥锁 Mutex

## 一句话定义
> 互斥锁（Mutex）是 FreeRTOS 中用于**保护共享资源互斥访问**的同步原语，带有**优先级继承**机制——当高优先级任务等锁时，临时把持锁的低优先级任务的优先级抬上去，防止被中优先级任务插队（优先级翻转）。

## 它解决什么问题 / 为什么存在
- 多个任务访问同一个全局变量/外设/缓冲区 → 不保护则数据竞态（A 改一半 B 读）
- 用二值信号量也能互斥——但信号量没有"所有者"概念，不能做优先级继承，可能出现优先级翻转
- Mutex 是信号量的"互斥专用版本"：增加了所有权跟踪和优先级继承

## 核心原理（大二能懂的水平）
- Mutex 在二值信号量的基础上加了两条规则：
  1. **所有权**：谁 Take 的必须谁 Give——不能跨任务释放（递归 Mutex 可以同任务嵌套 Take）
  2. **优先级继承**：Task H（高优先级）Take 失败时，内核发现锁被 Task L（低优先级）持有 → 临时把 L 的优先级抬高到 H 的水平 → 中优先级 Task M 无法抢占 L → L 尽快跑完临界区释放锁 → L 优先级恢复原值
- 创建：`xSemaphoreCreateMutex()`（动态）/ `xSemaphoreCreateMutexStatic()`（静态）
- Take/Give API 和信号量相同：`xSemaphoreTake()` / `xSemaphoreGive()`——句柄类型都是 `SemaphoreHandle_t`
- **递归互斥量**（Recursive Mutex）：允许同一任务多次 Take（内部维护一个递归计数），Give 相同次数才算释放。用于函数 A 中 Take 锁 → 调函数 B → B 又 Take 同一把锁的场景。

## 关键参数 / 易错点
- **谁 Take 谁 Give**：Mutex 不能跨任务释放——Task A Take 的锁，Task B 去 Give 会失败（二值信号量可以）
- **中断里不能 Take Mutex**：ISR 不"属于"任何任务，无从谈所有权——只能用信号量 `FromISR`
- **持锁时间越短越好**：锁本质是串行化点，持有时间长 = 其他任务等得久 = 系统吞吐下降
- **死锁**：A 等 B 的锁、B 等 A 的锁 → 约定统一的加锁顺序（如先锁外设 X 再锁外设 Y）可避免
- **优先级继承不是银弹**：如果 L 临界区本身就长（3 秒），抬优先级后 M 还是得等 3 秒——根本解决办法是缩短临界区
- 递归互斥量创建用 `xSemaphoreCreateRecursiveMutex()`

## 类比（帮助理解）
- 二值信号量像公共厕所（谁进去都行、谁出来都行，不分人）
- Mutex 像酒店房间（拿钥匙的人(Take)才能进去，只能由同一个人还钥匙(Give)出来；贵宾(高优先级)来了，前台把当前房客的房卡升级(优先级继承)，让他赶紧收拾出来）
- 递归互斥量 = 酒店套间（可以进大门进客厅进卧室，每进一扇门计数器 +1，退出来时 -1，退完所有门才算真正离开）

## 设计时怎么用（反推思维）
> 如果这条知识能用于「从需求到设计」，在这里写一句：做 XX 设计时，我会用它能解决 YY。
- 做任何多任务共享资源的设计时：首选 [[互斥锁 Mutex]] 做互斥保护，而非 [[二值信号量]]——收益：自动获得优先级翻转防护
- 做分层软件架构时：底层驱动 Take 锁、调上层回调、上层回调又想 Take 同一把锁 → 用递归互斥量防止死锁

## 典型应用 / 我在哪见过
- 共享 SPI Flash 读写（文件系统任务 vs UI 渲染任务）
- 共享全局数据结构（日志缓冲区、传感器融合数据）
- I2C 总线保护（多个任务共用一条 I2C 总线）
