# FreeRTOS 内存管理

## 一句话定义
> FreeRTOS 内存管理是内核为动态任务创建、队列、信号量等对象**分配和回收堆内存**的机制，提供了 heap_1 到 heap_5 五种可选策略（通过选择不同的 `heap_x.c` 文件切换）。

## 它解决什么问题 / 为什么存在
- 嵌入式 MCU 的堆非常小（通常 10-30KB），标准 `malloc/free` 可能有线程安全问题、碎片问题、不确定性延迟
- 不同应用对内存管理的需求不同：有的只需要"创建一次不删除"（heap_1），有的需要碎片整理（heap_4），有的有外部 RAM（heap_5）
- FreeRTOS 让开发者可以根据实际需求**插拔式选策略**，而不是强制用一种

## 核心原理（大二能懂的水平）

| 方案 | 算法 | 能否释放 | 碎片处理 | 适用场景 |
|------|------|----------|----------|----------|
| heap_1.c | 简单递增指针 | 不支持 | 无碎片（只增不减） | 任务创建后永不删除 |
| heap_2.c | 首次适配，有释放 | 能释放 | 会碎片（不合并） | 不推荐，已过时 |
| heap_3.c | 包装标准 malloc/free | 能释放 | 取决于 C 库 | 需要线程安全 malloc 包装 |
| heap_4.c | 首次适配 + 相邻块合并 | 能释放 | 主动合并相邻空闲块 | **最常用**，推荐首选 |
| heap_5.c | 同 heap_4，但跨多块内存 | 能释放 | 同 heap_4 | 有外部 SRAM/SDRAM |

- heap_1：一个指针 `pucAlignedHeap` 从堆头往后走，分配一块指针前移，永不回头——最快、最简单、零碎片但无法释放
- heap_4：维护空闲块链表，分配时找第一块够大的；释放后检查邻居块——如果相邻空闲就合并成一个更大的块，减少碎片
- heap_5：和 heap_4 一样的算法，但堆空间可以**分散在多块不连续的物理内存**上（如 20KB 内部 SRAM + 1MB 外部 SDRAM），用 `vPortDefineHeapRegions()` 注册内存区域
- 堆总大小由 `configTOTAL_HEAP_SIZE` 宏决定（在 `FreeRTOSConfig.h` 中设置）

## 关键参数 / 易错点
- **`configTOTAL_HEAP_SIZE` 必须 > 所有动态对象的开销之和**：任务(TCB+栈) + 队列(管理结构+缓冲区) + 信号量 + 定时器 + 事件组 + 软件定时器
- **监控剩余堆**：用 `xPortGetFreeHeapSize()` 定时打印，若持续下降 → 有内存泄漏
- **heap_1 删不了任务**：用 heap_1 时 `vTaskDelete` 不会释放内存（TCB + 栈占着不放），别误用
- heap_2 碎片问题：频繁创建/删除不同大小的任务会导致堆出现"瑞士奶酪"——总空闲够但都是小洞
- **线程安全**：heap_3 依赖 C 库 `malloc`，需要确认编译器的 C 库是否线程安全（很多嵌入式 C 库不是）

## 类比（帮助理解）
- heap_1 = 一本只能往后写不能撕的笔记本：写了就不能擦掉，但永远不乱
- heap_4 = 一本能撕页的笔记本：撕了一页后，如果左右两页也空着就把它们合在一起变成更大的空白区
- heap_5 = 不只用一本笔记本，桌子上一本 + 抽屉里一本 + 书包里一本，分开记但逻辑上都是一块堆

## 设计时怎么用（反推思维）
> 如果这条知识能用于「从需求到设计」，在这里写一句：做 XX 设计时，我会用它能解决 YY。
- 做"系统启动后任务固定、不增删"的产品时：用 heap_1——零碎片、零开销、最高确定性的选择
- 做需运行数月/年的物联网设备时：用 heap_4——内存碎片会合并，防止长期运行后无法分配
- 做带外部 SDRAM 的复杂系统时：用 heap_5——把小对象放内部 SRAM，大缓冲放外部 SDRAM

## 典型应用 / 我在哪见过
- 绝大多数 FreeRTOS 项目默认选 heap_4（官方推荐）
- 极简产品（如 LED 控制器）：heap_1（省事、可靠）
- STM32 开发板外扩 SRAM/SDRAM 的项目：heap_5
