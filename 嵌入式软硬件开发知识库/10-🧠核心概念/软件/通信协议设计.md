# 通信协议设计

## 一句话定义
通信协议设计是规定"两个设备之间怎么把数据打包、怎么知道一帧结束、怎么校验、怎么应答"的工程约定；本教程涉及工业串口协议 Modbus 与物联网云协议 MQTT 两类范式。

## 它解决什么问题 / 为什么存在
没有协议，两端收到的就是一堆无意义的字节。协议解决三件事：**帧边界**（一帧从哪到哪）、**语义**（这字节是读还是写）、**可靠性**（传错能否发现）。不同场景选法不同：板内/工业总线用 Modbus，跨互联网用 MQTT。

## 核心原理（大二能懂的水平）
**Modbus RTU（主从、串口）**
- 帧 = 设备地址 + 功能码 + 数据 + CRC16。
- 帧边界靠"3.5 字节空闲时间"判定（9600bps 下约 3ms 空闲即一帧结束），没有帧头帧尾。
- 主从架构避免总线冲突：主机主动、从机只应答。
- 四类寄存器当"共享状态表"：线圈(bit 读写)/离散输入(bit 只读)/保持寄存器(2B 读写)/输入寄存器(2B 只读)。

**MQTT（发布/订阅、TCP）**
- 设备与云通过"主题(topic)"解耦：终端 `PUB` 遥测、订阅 `SUB` 命令。
- 用 JSON 传参（如 `{"method":"led1Set","params":1}`），服务器用 RPC/attributes 下发。
- 传输层交给 4G 模组，MCU 只发 AT 指令。

## 关键参数 / 易错点
- Modbus：功能码 0x01–0x10 含义要记；CRC16 必须收发端同算法；地址 0 广播、1–247 单播。
- 串口帧边界依赖定时器超时，移植层需 [[定时器与PWM]] + [[中断NVIC]] 配合（教程用 TIM3）。
- MQTT：主题写错订阅收不到；AT 指令要等 `OK` 并加超时；断线要重连。
- 提升效率可给 Modbus 配 [[UART]]+DMA。

## 类比（帮助理解）
Modbus 像工厂里的对讲机点名：班长(主机)喊"3号报温度"，3号(从机)回数据，其他人听到不是喊自己就忽略。MQTT 像公司的公告栏+投稿箱：你往某个栏目贴数据，关心的人自己订阅那个栏目。

## 设计时怎么用（反推思维）
- 反推"要可靠" → 必须带校验(CRC16/CRC32)和应答，不能发了就不管。
- 反推"要解耦/可扩展" → 用发布订阅(MQTT)而非点对点长连接；用寄存器模型统一状态。
- 反推"要省 MCU" → 联网协议栈下沉到通信模组，MCU 只发文本指令。

## 典型应用
工业 PLC 采集(Modbus)、设备上云(MQTT)——本项目 [[2026-OTA智能控制终端]] 同时用到两者（本地 Modbus + 云端 MQTT）。
