# 05-企业实战1-OTA智能控制终端

## 这条教程在解决什么
把学校里零散学的通信协议（Modbus / MQTT）、STM32 Flash 操作、Bootloader 跳转，串成一个**企业里真实会做的东西**：一台能远程升级固件的"智能控制终端"。核心痛点是——设备卖到客户手里后没有下载线、客户也不是工程师，怎么"傻瓜式"地让它自己更新程序？答案就是 OTA + Bootloader 双分区。

教程主线是四章协议 + 一个综合项目：先讲 Modbus（工业串口协议）、MQTT（云平台通信）、CANOpen（顺带提一句），最后第四章用这些零件拼出 OTA 智能控制终端。

## 关键内容（按 PDF 章节提纲）
### 第 01 章 Modbus 协议实战
- **Modbus 是什么**：1979 年施耐德为 PLC 通信提出的串行协议，已是工业事实标准；本质是一种"请求/应答"通信约定。
- **三种传输模式**：RTU（最常用，二进制紧凑）、ASCII（文本，人易读）、TCP（跑在以太网端口 502）。本教程只用 RTU。
- **主从架构**：一主多从，主机主动发、从机只能应答；地址 0 广播、1–247 单播。靠"3.5 字节空闲时间"来判断一帧结束（如 9600bps 下一个字节约 0.8ms，空闲约 3ms 即认为帧结束）。
- **四类寄存器**（本质是约定的存储区，不是真实硬件寄存器）：
  - 线圈寄存器：bit 级，可读可写（开关量），功能码 `0x01/0x05/0x0f`
  - 离散输入寄存器：bit 级，只读（读按键），功能码 `0x02`
  - 保持寄存器：2 字节/个，可读可写（存数据如时间），功能码 `0x03/0x06/0x10`
  - 输入寄存器：2 字节/个，只读（读 AD 值），功能码 `0x04`
- **帧格式**：设备地址 + 功能码 + 数据码 + CRC16 校验（2 字节）。
- **FreeModbus**：开源协议栈，适用于 MCU（资源占用小，对比 LibModbus 偏 Linux）。关键是三个函数：`eMBInit()` 初始化、`eMBEnable()` 使能、`eMBPoll()` 循环轮询。移植层用 TIM3 做 3.5 字符超时定时器（因为 WiFi/4G 占了 TIM4），底层靠 [[UART]] 接收中断 + [[中断NVIC]]。

### 第 04 章 OTA 智能控制终端实战（核心）
- **4.1 OTA 介绍**：Over-The-Air，无线远程升级。FOTA（固件/底层，像刷 BIOS）vs SOTA（软件/App）。流程三步：生成更新包（常差分）→ 加密传输到云端 → 安装并验证（完整性 + 数字签名 + 回滚）。
- **4.2 STM32 Bootloader 原理**：程序最终都是二进制进片内 Flash，所以可以对 Flash 分区。以 STM32F103CB（128 页 × 1K）为例分三区：BootLoader 区（8K）、App1 区（28K，0x08002000）、App2 区/备份区（28K，0x08009000）。App2 区**最后 4 字节**（0x0801FFFC）写 `0xAAAAAAAA` 表示"有可用升级包"。
- **4.3 实战项目8-Bootloader**：需要 printf、Flash 读写、程序跳转（`MSR_MSP` 改栈顶 + `IAP_ExecuteApp` 跳复位向量）。`Start_BootLoader()` 读启动模式：正常就直接跳 App1，升级就把 App2 拷贝覆盖到 App1 再跳。**坑**：拷贝用 1K 栈，要把栈空间放大一倍，否则 printf 异常。
- **4.4 实战项目8-APP**：App 由 Bootloader 跳转而来，**必须先改中断向量表** `SCB->VTOR = FLASH_BASE | Application_1_Addr`，否则中断会跑飞；打印版本号区分 App 版本。
- **4.5–4.7 服务器与模组**：ML307（4G Cat.1）走 AT 指令连 ThingsBoard / xthings.cloud（MQTT，端口 1883）。订阅三个下行主题（命令 / OTA 属性 / OTA 文件块），发布三个上行主题（遥测 / 命令回复 / OTA 请求块）。
- **OTA 拉取固件流程**（`MQTT_OTA_GetFW`）：擦 App2 → 逐块（256 字节）请求 `v2/fw/request` → 收 `v2/fw/response` → 增量算 CRC32 → 写 Flash → 全收完比对服务器下发的 checksum → 成功则写 `0xAAAAAAAA` 标志 + 软复位。
- **4.8–4.10 收尾**：APP1.2 加状态指示灯（1s 周期，500ms 亮/灭）；生产环节要提取完整固件；改进思路：A/B 区轮换启动、用外部 SPI Flash 存固件减轻片内 Flash 压力。

## 我卡住/没懂的地方
- `SCB->VTOR` 偏移为什么必须是 App1 首地址？向量表重映射的底层机制还没完全吃透（和 [[中断NVIC]] 强相关）。
- CRC32 的 `swap_endian` 参数为什么有时要字节序翻转（Zlib 标准 vs 网络序）？
- CANOpen 的 SDO/PDO 概念只提了一嘴，没展开，暂时不管。
- 差分升级（delta update）教程只提了名词，没讲具体算法（bsdiff 之类），属于后续深挖点。

## 它背后的原理
- **为什么能远程升级**：因为 Flash 里代码就是可擦写的二进制，只要有一小段"永不更新的 Bootloader"负责把新程序搬进 App 区，就能做到不接下载线升级。
- **为什么要双分区（App1 + App2 备份）**：升级中途断电/失败，App1 还是旧的能跑，下次启动重来，避免变砖。这就是"回滚"思想的硬件落地。
- **为什么靠 3.5 字节空闲判断帧边界**：串口没有帧头帧尾，靠定时器超时来切分报文，这是 Modbus RTU 的精髓。
- **为什么 App 要重映射向量表**：Cortex-M 复位后默认从 0x08000000 取向量，但 App 实际在 0x08002000，不挪 VTOR 中断向量地址全错。

## 我能复用/改编的点
- 直接套用 `boot.h` 里的分区宏（`BootLoader_Size / Application_Size / Application_1_Addr / Application_2_Addr`），按自己芯片 Flash 大小改即可。
- `MoveCode`（擦→拷→擦源）这套"双备份搬运"逻辑可以复用到任何需要固件备份的场景。
- `IAP_ExecuteApp` 跳转模板（校验栈顶 `0x2FFE0000==0x20000000` → 设 MSP → 跳复位向量）是标准做法，背下来。
- Modbus 寄存器模型（线圈/保持寄存器）可以直接拿来当"设备内部状态表"用，云平台和本地共用一套地址。
