# 二维码识别

> 基于 STM32F429 + OV5642 摄像头的二维码识别：DCMI 把图像经 DMA 搬进外部 SDRAM 帧缓冲，调用 QR-Core 解码库完成"采集→预处理→定位→解码"，识别结果经串口上报 PC。核心价值是"在单片机侧跑通机器视觉的端到端流水线"。

## 1. 需求拆解
- 必须实现：
  - 摄像头(OV5642)出图，DCMI + DMA 把整帧搬进外部 SDRAM 帧缓冲（`0xD0500000`）。
  - MCU 循环调用解码库 `QR_decoder()`，从帧缓冲识别二维码，最多同时 3 个。
  - 解码结果（类型名 + 数据）经 [[UART]](USART1) 上报上位机；识别到时蜂鸣器响一声。
  - LCD 实时显示画面并叠加扫描框，方便对准。
- 可选实现：
  - 同时兼容 OV2640 / OV7670 / MT9D111（代码里按 ID 自动识别初始化）。
  - FATFS 把图像/结果存 SD 卡。
- 硬约束（供电/尺寸/成本/通信）：
  - 主控 STM32F429（Cortex-M4，带 DCMI 与 SDRAM 控制器，且性能足以跑解码）。
  - 图像分辨率高、单帧数据量大，必须外挂 SDRAM 作帧缓冲，不能塞片内 SRAM。
  - 摄像头配置走 SCCB（类 [[I²C]] 的双向串行总线），非标准 I²C 控制器，代码用 GPIO 模拟。
  - 解码库以 `QR-Core.lib` 二进制提供，源码不可见，对外仅 `QR_Decoder.h` 几个 API。

## 2. 功能框图
```
   OV5642 摄像头
   (SCCB配置 PB6/PB7, DCMI 取图)
        │ DCMI(8bit)+PIXCLK/HSYNC/VSYNC
        ▼
   ┌──────────── STM32F429 ────────────┐
   │  DCMI 外设                        │
   │    │ DMA2                         │
   │    ▼                              │
   │  外部SDRAM 帧缓冲 0xD0500000      │
   │    │  get_image()                 │
   │    ▼                              │
   │  QR_decoder()  ──调用──▶ QR-Core.lib │
   │    │  decoded_buf[3][512]         │
   │    ▼                              │
   │  解析: 类型长度+类型名+数据长度+数据 │
   │    │                              │
   │    ├─▶ USART1 上报 PC             │
   │    ├─▶ 蜂鸣器(BEEP) 提示           │
   │    └─▶ LCD 显示画面+扫描框         │
   └───────────────────────────────────┘
```

## 3. 器件选型
| 模块 | 型号 | 选型理由 | 替代 |
| --- | --- | --- | --- |
| 主控 MCU | STM32F429 | 带 DCMI 摄像头接口、外部 SDRAM 控制器、M4 性能跑解码 | STM32F4 其他带 DCMI 型号 |
| 摄像头 | OV5642 (也支持 OV2640/OV7670/MT9D111) | 500W 像素、资料多、SCCB 易驱 | OV2640（200W，更省资源） |
| 帧缓冲 | 外部 SDRAM | 一帧 RGB 数据远超片内 SRAM，必须外挂 | 大容量 PSRAM |
| 解码库 | QR-Core.lib | 现成二维码识别算法，免去自研 | 自研 [[二维码识别]] 算法 |
| 输出 | USART1 + LCD | 串口上报 PC、LCD 现场显示 | 仅串口 |

## 4. 原理图推导（逐个模块，讲清为何需要每个元件）
- **OV5642 与 SCCB（PB6=SIC 时钟、PB7=SID 数据）**：摄像头内部几十个寄存器要配（分辨率/格式/时钟），用 SCCB 总线写。SCCB 与 [[I²C]] 几乎同协议但无地址应答细节差异，故代码用 GPIO 模拟 `sccb_bus`（开漏+上拉），不占用真正 I²C 控制器，灵活。
- **DCMI 接口**：OV5642 并行输出 8 位像素 + PIXCLK(PA6)/HSYNC(PH8)/VSYNC(PI4/PI5)，STM32F4 的 DCMI 外设专吃这种"带同步信号的并行视频流"。为何用 DCMI 而非 GPIO 软采？逐像素时钟达 MHz 级，只有硬件外设 + [[DMA]] 才跟得上。
- **DMA2 → 外部 SDRAM（0xD0500000）**：DCMI 每来一个像素就触发 DMA 把数据直接搬进 SDRAM 帧缓冲，CPU 不参与搬运，避免丢帧。帧缓冲地址固定，解码库直接读。
- **外部 SDRAM**：一帧 QVGA/RGB 就是上百 KB，片内 SRAM 装不下，故板载 SDRAM（经 FMC/SDRAM 控制器），帧缓冲落在这里。
- **QR_decoder() / QR-Core.lib**：解码库从帧缓冲取图，完成预处理(灰度/二值化)→定位(找定位角/对齐图案)→解码(纠错+比特流→数据)。输出 `decoded_buf[QR_SYMBOL_NUM][QR_SYMBOL_SIZE]`（3×512），每组格式为"类型长度(1B)+类型名+数据长度(2B 大端)+数据"。
- **USART1 上报**：识别到后 `USART1_Send_Data` 把"类型:数据\r\n"发给 PC 串口助手；同时 BEEP(GPIO) 响一声做现场提示。
- **LCD**：LTDC 控制器驱动 RGB LCD，画实时画面与扫描框，降低对准难度。

## 5. 布局布线要点
- **DCMI 等长/抗噪**：8 位数据 + 3 条同步线同组走线，避免长度差导致采样错位；远离电源与时钟源，必要时加 [[去耦电容]]。
- **SDRAM 走线**：SDRAM 总线多、速率高，需 [[时钟树]]/SDRAM 时序约束与阻抗控制，否则帧缓冲偶发坏点→解码失败。
- **SCCB 上拉**：PB6/PB7 需 [[上拉电阻与下拉电阻]]（代码里 `GPIO_PuPd_UP`），否则配置摄像头读不到 ACK。
- **摄像头时钟**：OV5642 需外部 MCLK（由 MCU 某 PWM/时钟输出提供），频率要落在 datasheet 范围。
- **电源**：摄像头与 SDRAM 电流不小，分区 [[去耦电容]] + 低噪声 [[线性电源LDO]] 有利于图像质量。
- **存储带宽**：DCMI-DMA 与 LCD-DMA、CPU 抢总线，注意 [[DMA]] 仲裁与突发传输配置。

## 6. 检查清单
- [ ] SCCB — PB6/PB7 已上拉，摄像头 ID 能正确读出(0x5642/0x2642/0x7673)
- [ ] DCMI — 像素/同步引脚复用正确，DMA2 把帧搬进 SDRAM 地址 0xD0500000 无误
- [ ] SDRAM — 控制器时序配置正确，帧缓冲读写稳定(可先跑显存测试)
- [ ] 解码 — `QR_decoder()` 返回数量与 `decoded_buf` 解析逻辑（类型/数据长度大端）正确
- [ ] 输出 — USART1 波特率与上位机一致；BEEP/LCD 提示正常
- [ ] 镜头 — 对焦(`ov5642_auto_focus`)完成，扫描框内二维码清晰、对比度够
- [ ] 电源 — 摄像头/SDRAM 去耦与储能充足，整板无复位

## 7. 复盘
- **企业/项目为什么这么设计**：把"图像采集(DCMI+DMA)"与"算法(QR-Core.lib)"解耦——硬件负责高速搬数，软核负责识别，工程上各司其职、便于替换摄像头或升级算法。
- **为什么必须外挂 SDRAM**：机器视觉的第一道门槛就是"一帧放哪"，片上资源不够，外挂帧缓冲是刚需。
- **为什么 SCCB 用 GPIO 模拟**：SCCB 与 I²C 微差，且摄像头配置只在初始化做一次，GPIO 模拟最省外设、最稳。
