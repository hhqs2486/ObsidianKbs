# 微服务架构

## 一句话定义
微服务架构是一种"把单体系统按业务边界拆成一组小而专、独立部署、通过契约(网络)协作的服务"的架构方法论——强调的是"怎么拆、怎么管、怎么让这些服务一起好好工作"（区别于泛泛的 [[微服务]] 概念）。

## 它解决什么问题 / 为什么存在
单体改一处全发版、模块耦合、扩缩容只能整体扩。微服务架构给出一套组织方法：按业务域（Domain）拆分、数据自治、服务间用 API 契约通信、独立部署与扩容——也是 [[云原生]] 的应用结构基础。

## 核心原理（大二能懂的水平）
- 拆分原则：按"业务边界/领域"切（如用户、订单、支付各一服务），而非按技术层切；每个服务管自己的数据（数据自治，不共享库）。
- 通信：服务间用同步（HTTP/gRPC，[[东西向流量]]）或异步（消息）调用，靠 [[DNS与服务发现]] + [[Service]] 解耦地址。
- 治理需求随之而来：服务发现、[[负载均衡]]、配置外置（[[ConfigMap]]/[[Secret]]）、故障隔离（[[探针LivenessReadiness]]）、安全（mTLS）。
- 演化：容器网络（[[Calico]]/[[Flannel]]）解决"通不通"，[[Service Mesh]]（[[Istio]]）解决"怎么聪明/安全地通"——网络与 Mesh 是微服务架构的两层地基。
- 本书七牛案例正演示这一演化：从"端口映射+粗暴隔离"(Before) → "天然 Discovery/LB + 安全组 + 完整端口空间"(After)；FOP 架构从 Stage1 到 Stage4 逐步把 Discovery/LB 下沉、分离有状态/无状态。

## 关键参数 / 易错点
- 易错：拆太细 → 服务爆炸、调用链爆炸、排错难；拆太粗 → 退回单体。按"业务域+团队边界"拆。
- 易错：以为上了微服务就自动高可用/弹性——每个服务仍需 Deployment 多副本 + 探针 + 资源限制。
- 易错：服务间共享数据库（破坏自治）→ 应各管各的数据，用 API 交互。
- 分布式事务/一致性比单体复杂，要接受"最终一致"。

## 类比（帮助理解）
像"把一家啥都做的大超市（单体），拆成美食城档口（微服务架构）：每个档口管自己进货记账（数据自治）、用对讲机协作（API）、各自排队扩容；再配总服务台(Discovery/LB)和安保(安全组/Mesh)。"

## 设计时怎么用（反推思维）
> 做"多团队并行、模块流量不均、要不停机迭代"的系统时，我会按业务域拆微服务，每个服务独立镜像+Deployment+Service，配置外置，并用 Calico 做网络隔离、Istio 做服务间治理，形成"容器网络→Service Mesh"双层。

## 典型应用 / 我在哪见过
- 电商、文件处理（本书七牛 FOP/UFOP）、云平台；与 [[Kubernetes]] + [[容器编排]] 天然契合。
