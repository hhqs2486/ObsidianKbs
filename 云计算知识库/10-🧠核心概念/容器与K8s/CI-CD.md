# CI/CD

## 一句话定义
CI/CD = **持续集成（Continuous Integration，频繁合并代码并自动构建测试）** + **持续交付/部署（Continuous Delivery/Deployment，自动把通过测试的应用发布到环境）**。在 K8s 世界里，它就是把「代码 → 镜像 → 部署到集群」做成自动化流水线。

## 它解决什么问题 / 为什么存在
手动构建、手动打标签、手动 `kubectl apply` 又慢又易错，还容易把未扫描的镜像、有漏洞的配置推上生产。CI/CD 把「构建、漏洞扫描、签名、部署、回滚」串成一条可重复的自动化链条，既快又稳，也是第12章安全的落地抓手。

## 核心原理（大二能懂的水平）
- **CI（持续集成）**：开发者 push 代码 → 自动拉取、编译、跑单测；通过才允许合入。
- **CD（持续交付/部署）**：合入后自动构建 [[容器]] 镜像 → 推到镜像库 → 经 [[Helm]] 或 `kubectl apply` 部署到 K8s。
- 第12章给出的「镜像晋升流水线」关键安全环节：①用**已验证基础镜像**；②镜像**漏洞扫描**（扫出严重漏洞就让流水线失败、隔离镜像）；③**镜像签名 + 验签**；④**配置即代码**（审查 Dockerfile 与 K8s YAML）；⑤对镜像库/repo 配 RBAC 控制 push/pull。
- 与 [[滚动更新与回滚]] 配合：CD 触发升级，出问题一键回滚。

## 关键参数 / 易错点
- **易错**：只扫代码不扫配置（Dockerfile/YAML），结果「一次构建到处运行」把配置漏洞放大到成千实例（IBM 私钥打包进镜像的真实教训，第12章）。
- **易错**：CI 用的高权限账号/SA 不设最小权限，一旦泄露等于集群沦陷——接 [[RBAC]]。
- **易错**：扫描引擎是「已知漏洞库」比对，可能有误报，流水线要留「人工标记误报」环节，别一刀切卡死。

## 类比（帮助理解）
CI/CD 像「工厂自动装配线」：代码进一端（提交），经过质检（构建/测试/扫描）、贴标（镜像签名），成品从另一端自动上架到货架（集群部署）；哪道工序亮红灯，整条线停（构建失败），而不是带病出厂。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY。
做需要「频繁发版且要保证生产安全」的系统时，我会搭一条 CI/CD：push→构建→漏洞扫描→签名→自动部署到预发→人工/自动晋级生产，并把 [[ConfigMap]]/[[Secret]] 与镜像解耦、用 [[Helm]] 做版本化发布，出事靠 [[滚动更新与回滚]] 回退。
