# 集群联邦KubeFed

## 一句话定义
> Kubernetes Federation v2（KubeFed）：用 **CRD** 把多个独立 K8s 集群"联合"成一个逻辑集群，统一分发与管理跨集群资源（如跨集群 Deployment、Service、配置）。

## 它解决什么问题 / 为什么存在
- 书第 16 章只给了"各集群独立 + 镜像仓库同步"的朴素多集群（16.3.5）。当集群数量变多、需要**用一套 API 把同一份应用/配置同时下发到 N 个集群**、并做跨集群故障转移时，逐集群 `kubectl apply` 就不可维护了——这就是集群联邦要解决的问题。
- 它是 [[多集群管理]] 的"进阶形态"：从"多套门户各管各的"升级到"一个控制面统管多集群"。

## 核心原理（大二能懂的水平）
- 联邦控制面（`kubefed-controller-manager`）监听一组 **Federation 类型 CRD**，例如 `FederatedDeployment`、`FederatedService`、`FederatedConfigMap`。
- 你在联邦层提交一个 `FederatedDeployment`，并在 `spec.placement` 里声明"下发到 clusterA、clusterB"；联邦控制器就把对应的普通 [[Deployment]] 同步到这些成员集群的 API Server。
- 底层完全依赖 [[Kubernetes]] 的 [[CRD与Operator]] 机制——联邦本身只是一组自定义资源 + 控制器，不改造成员集群。

## 关键参数 / 易错点
- `placement`：决定资源去哪些成员集群（按名称选择）。
- **成员集群的 API Server 仍然各自独立**：联邦不是"融成一个大集群"，而是"统一发令、各集群分别执行"。易错：以为联邦集群里 Pod 可以跨集群直连——跨集群网络仍需自己解决（多集群服务/全局 DNS）。
- 演进提示：KubeFed（Federation v2）后来被社区多集群方向（KEP-1645，如 Karmada、多集群服务 MCS）吸收演进；学习时把它当作"联邦思想"的参考实现即可。

## 类比（帮助理解）
- 联邦像"联合国"：各成员国（成员集群）**主权独立**（各有自己的 API Server 与政府），但有个总部统一协调跨国事务（把应用/策略下发到各国）。

## 设计时怎么用（反推思维）
> 做跨云/多地容灾时，我会用集群联邦统一下发同一份 [[Deployment]] 到 N 个集群，并配合全局流量调度做故障转移；对比书 16.3.5 的"镜像同步"朴素方案，联邦更适合"同一应用要稳定存在于多集群"的场景。

## 典型应用 / 我在哪见过
- 跨地域容灾、混合云统一应用分发、多集群配置/策略统一治理。
- 对照：书 16.3.5 的金融容器云用"镜像同步"而非联邦——说明联邦是比该书实践更进一步的方案。
