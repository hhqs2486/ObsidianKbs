# 镜像仓库（Image Registry）

## 一句话定义
集中存储、分发容器镜像的服务，相当于「容器镜像的 Git 仓库 + 应用商店」，K8s 拉起 [[Pod]] 时就是来这里取镜像。

## 它解决什么问题
没有镜像仓库，镜像只能在本机 `docker save/load` 拷来拷去，无法在集群多节点间一致分发、无法做版本管理、无法控制谁能拉/推。镜像仓库统一解决「存、发、权限、版本」。

## 核心原理（大二能懂）
- 镜像按 `仓库地址/项目/镜像名:标签` 寻址，如 `harbor.example.com/library/nginx:1.25`。
- 推送：`docker push`；拉取：`docker pull` / K8s 的 `image:` 字段。
- 分级：公共仓（Docker Hub）+ 私有仓（企业内网，如 Harbor、云厂商 OCR）。
- 类比：镜像仓库像「手机 App 的应用商店」，开发者上传（push）、手机下载安装（pull）。

## 关键参数 / 易错点
- `imagePullPolicy`：Always/Never/IfNotPresent，影响是否每次都拉。
- 私有仓要配 `imagePullSecrets`（仓库登录凭据，本质是 [[Secret]]），否则 K8s 拉不了。
- 易错：标签用 `latest` 导致版本不清、回滚困难；生产应锁具体版本/`digest`。
- 镜像仓库是 [[CI-CD]] 流水线的核心枢纽：构建完 push 进来，集群再 pull 走。

## 一个生活类比
镜像仓库 = 中央厨房的「成品菜冷库」：厨师（CI）做好菜（镜像）存进去，各家门店（K8s 节点）按需取走上桌（跑容器）。

## 设计时怎么用（反推思维）
- 需求「公司内网部署一套 K8s，镜像不能出公网」→ 反推：自建私有镜像仓库（Harbor）+ 配 imagePullSecrets + 流水线 push 到内网。
- 需求「多环境一致」→ 反推：同一镜像 digest 在 dev/test/prod 共用，靠仓库保证不可变。

## 典型应用
- Harbor（带权限/漏洞扫描/复制）、云厂商容器镜像服务、Docker Hub。
- [[OpenShift]] 的内部 Registry、[[镜像仓库]] 与 [[Source-to-Image]] 配合自动构建。
