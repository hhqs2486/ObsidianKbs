# 应用包管理

## 一句话定义
> 应用包管理是把 K8s 上的应用当作"软件包"来安装 / 升级 / 删除 / 分发的一套方法论；[[Helm]] 就是 K8s 上的包管理器（类比 apt / Homebrew）。

## 它解决什么问题 / 为什么存在
- [[Kubernetes]] 像一个操作系统，但原生只认 YAML 清单，没有"装一个 WordPress"这种一键语义；用户要从零写 YAML、自己管版本。
- 应用包管理补足"查找 → 安装 → 升级 → 删除 → 配置"的软件包语义，让部署应用像装软件一样。

## 核心原理（大二能懂的水平）
- Helm 借鉴操作系统包管理器：仓库搜索、install / upgrade / delete、配置覆盖、查看已装内容。
- Helm 设计三目标（本书 1.2）：① 从零到 K8s（5 分钟装好应用）；② 提供类 OS 的包管理系统；③ 强调安全 / 可重用 / 可配置。
- 与"配置管理"的区别：包管理只做 install / upgrade / delete 三个动作，不长期管状态（所谓 "day-two ops"）；Puppet / Ansible / [[Helmfile]] / Flux / Reckoner 才补配置管理。

## 关键参数 / 易错点
- K8s 与 OS 不同：支持同应用多实例、有 [[Namespace]]——这正是 Helm 需要"release 名"且"区分 namespace"的根本原因（同一个 chart 可装出多个实例）。
- Helm 不是配置管理工具（但常被当）；长期状态管理交给 Helmfile / Flux 等。
- 安全三要素：验证来源（provenance / PGP）、可重用（chart + 配置可重复）、可配置（install/upgrade 时传参）。

## 类比（帮助理解）
- 像手机应用商店：搜索 → 安装 → 更新 → 卸载，背后是"包"在流转。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会把"部署"抽象成"装包"——先把应用做成 [[Helm Chart]]（包），再用 Helm 的 install / upgrade / rollback 管理其生命周期，而不是手工 `kubectl apply` 一堆 YAML。
