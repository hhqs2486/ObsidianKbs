# 自定义资源

## 一句话定义
> 自定义资源（Custom Resource，CR）是"用 CRD 注册后、存在于 K8s 里的用户自定义对象实例"——它是数据/状态，CRD 是它的类型定义。

## 它解决什么问题 / 为什么存在
- 原生资源表达不了你的业务概念（如 Tenant、Database），自定义资源让你能用同一套 K8s API/存储/工具链管理自己的对象，复用生态而非另起炉灶。

## 核心原理（大二能懂的水平）
- **CRD 定义"类型"，CR 是"该类型的实例"**（就像 Pod 是 `kind: Pod` 的实例）。
- 创建 CRD 后，你 `kubectl apply` 一个该 kind 的 YAML，APIServer 就把它存进 etcd，并支持完整的 List/Watch/版本转换（和内置资源一模一样）。
- 光有 CR 没有控制器，它只是"躺着的数据"——只有配上 [[CRD与Operator]] 里的控制器才会被真正"执行"。
- 可加 `status` 子资源、设定 `additionalPrinterColumns`（让 `kubectl get` 显示友好列）、`shortNames`。
- 与 ConfigMap 不同：CR 有强 schema 校验、有 API 版本、可被 Watch，适合表达"有结构、有生命周期"的领域对象。

## 关键参数 / 易错点
- CR 本身不做任何事，必须有控制器消费它（常见误区：以为建了 CRD 就自动生效）。
- schema 校验失败会直接拒写，注意字段类型/必填。
- 大对象会撑大 etcd；不要把 CR 当数据库塞海量数据。
- 删除 CRD 会级联删除该类型所有 CR（危险，需确认）。

## 类比（帮助理解）
- 像你给 Excel 加了一张"自定义表"（CRD 是表头，CR 是每一行数据）；但如果没有公式/宏去处理这些行，它们只是摆着。

## 设计时怎么用（反推思维）
> 做"平台需要持久化一类有结构、有状态的概念"需求时（如「租户」「应用模板」），我用 CR 承载它，复用 K8s 的 API/存储/RBAC，而不是另起一套数据库。

## 典型应用 / 我在哪见过
- 平台工程里的「Tenant」「Application」CR、各类 Operator 的领域对象。
