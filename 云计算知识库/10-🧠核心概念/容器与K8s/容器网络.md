# 容器网络

## 一句话定义
容器网络解决"容器（尤其是跨主机的容器）之间、容器与外部之间怎么互相找到并按 IP 通信"的问题，是容器能协同工作的地基。

## 它解决什么问题 / 为什么存在
容器比虚机更轻、生命周期更短、端点更多、关系更复杂（书里点明的四点），且每个容器职能更小、依赖更多——传统"一台虚机一个 IP"的网络模型直接套会崩。需要给每个 Pod 稳定可达的 IP，并跨主机互通。

## 核心原理（大二能懂的水平）
- K8s 网络模型（IP-per-Pod，扁平、跨节点不 NAT）是前提，由 [[CNI网络]] 插件落地。
- 单机内：容器通过 veth pair 接到 Linux bridge（docker0），靠 iptables NAT / 路由转发互通。
- 跨主机：Overlay（VXLAN 等隧道封装）或路由（BGP/host-gw 直路）两类思路。
- Docker Bridge 的局限（书里列）：重启 IP 变、IP 不能跨主机迁移、NAT 隐藏地址、NAT 性能损耗、Bridge 内难精细隔离、端口冲突。

## 关键参数 / 易错点
- Pod IP 会变（重建即换）→ 业务不能写死 IP，要靠 [[DNS与服务发现]] + [[Service]]。
- Overlay 有封包开销（VXLAN 约 10~30%），大流量用路由直路（BGP）。
- 网络策略（隔离）不是所有 CNI 都支持（见 [[Calico]] vs [[Flannel]]）。
- MTU 要留封装头空间，否则大包分片/超时。

## 类比（帮助理解）
像"大学宿舍楼内通话（单机 bridge）vs 跨校区打电话（需要运营商骨干网 = 跨主机网络方案）"；每间宿舍（容器）有个分机号（IP），但总机（Service/DNS）帮你转。

## 设计时怎么用（反推思维）
> 做微服务部署时，我会先定网络方案：需要 Pod 间强制隔离 + 性能 → 选 [[Calico]]（BGP + NetworkPolicy）；纯简单实验 → [[Flannel]]（VXLAN）。再上层用 Service Mesh 管服务间调用。

## 典型应用 / 我在哪见过
- Docker Bridge（单机）、Flannel/Calico/Weave（跨主机 CNI）。
- 本书"容器与网络"章对比 Docker Bridge / Flannel / Weave / Calico 的隔离粒度、地址管理、性能、控制/转发平面。
