# 无状态应用

## 一句话定义
> 运行实例不在本地持久化数据、任意副本对相同请求返回一致结果、可以被随意杀掉/重建/扩缩的应用，比如 Web 前端、API 服务、网关。

## 它解决什么问题 / 为什么存在
- 业务要应对流量高峰、要容错、要快速扩缩。如果每个实例都抱着自己的本地数据/会话，就扩不动、迁不动、挂了数据就没了。
- “无状态化”让“实例”变成可替换的标准件：任何副本都能顶上，副本 IP 变了用户也无感。

## 核心原理（大二能懂的水平）
- 把**可变状态外移**：用户会话存 [[微服务]] 共享的 Redis、文件存对象存储、业务数据存数据库；实例本身只跑代码。
- K8s 用 [[Deployment]] 管理副本数量、滚动更新与回滚；副本 IP 一变，由 [[Service]] 做负载均衡与服务发现来屏蔽，前端根本不感知后端换没换。

## 关键参数 / 易错点
- 用 [[Deployment]] 而不是裸 [[Pod]]；`replicas` 至少 >1，并配合 **podAntiAffinity**（反亲和性）打散到不同节点，避免单点。
- `readinessProbe`（就绪检查）+ `preStop` hook：保证滚动更新期间连接不丢、流量不打到没起来的 Pod。
- **别把用户会话写在容器本地磁盘/内存**——session 粘性会破坏横向扩缩；改用 Redis 或 token（JWT）。
- 扩缩可手动改 `replicas`，或上 HPA（HorizontalPodAutoscaler）自动水平伸缩。
- 易错：长连接服务如果不做“长连接转短连接”，HPA 自动扩容会失效（新 Pod 接不到连接）。

## 类比（帮助理解）
- 像快餐店柜员：任何柜员都能处理你的订单，换一个柜员你的体验不变。
- 对照 [[有状态应用]]：像你的私人银行经理，换人就接不上你的账户历史。

## 设计时怎么用（反推思维）
> 做 XX 系统时，如果需求是“高并发、要弹性、要灰度发布”，我会优先把应用拆成**无状态服务**：状态外置，用 [[Deployment]] + [[Service]] + HPA 管理；只有实在外置不了的核心数据组件，才降级为 [[有状态应用]]。

## 典型应用 / 我在哪见过
- Nginx、API 网关、Web 前端、Serverless 函数（如 Azure Functions）、绝大多数 [[微服务]]。
- 《Kubernetes 实践指南》里 nginx 示例就是用 readinessProbe + preStop 做平滑更新的典型无状态服务。
