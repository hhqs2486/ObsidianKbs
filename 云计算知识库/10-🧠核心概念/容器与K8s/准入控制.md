# 准入控制

## 一句话定义
> 准入控制（Admission Control）是 APIServer 在"请求通过认证和授权之后、写入 etcd 之前"执行的拦截器链，能校验甚至修改对象内容。

## 它解决什么问题 / 为什么存在
- 授权只判断"你有没有权限做这个动作"，但不判断"这个对象本身合不合规"（比如容器有没有跑 root、有没有超资源）。准入控制补上"内容合规 + 自动注入"这一层。

## 核心原理（大二能懂的水平）
- 两类插件：**Mutating（变更型）**先跑，可改对象（如注入 sidecar、补默认字段）；**Validating（校验型）**后跑，只能拒绝或放行。
- 内置插件举例：PodSecurity（强制安全上下文）、ResourceQuota（检查命名空间配额）、LimitRanger（补默认资源限制）、ServiceAccount（自动挂 SA）、NodeRestriction（限制节点只能改自己）。
- **动态准入 Webhook**：通过 MutatingAdmissionWebhook / ValidatingAdmissionWebhook 调用外部 HTTPS 服务做自定义校验/修改（Istio 注入、策略引擎 OPA/Gatekeeper 都靠它）。
- 由 APIServer 的 `--enable-admission-plugins` 开启，`--admission-control-config-file` 配参数。

## 关键参数 / 易错点
- 顺序重要：所有 Mutating 跑完才跑 Validating。
- Webhook 服务必须高可用，否则会阻塞所有相关写请求；`failurePolicy` 决定失败时拒绝还是放行。
- 有些插件（如 PodSecurity）是"软"的，需配合正确配置才生效，不是开了就万事大吉。
- 不要挂太多重量级 webhook，会增加 API 延迟、放大故障面。

## 类比（帮助理解）
- 像机场安检后的"海关申报"：你已通过身份与登机（认证授权），但行李内容还得过海关规则（准入），必要时海关还能让你把东西丢掉或补税（Mutating）。

## 设计时怎么用（反推思维）
> 做"集群强制规范"需求（如禁止特权容器、自动注入监控 sidecar、限制镜像仓库）时，我用动态准入 Webhook + 内置插件，把策略固化在 API 入口。

## 典型应用 / 我在哪见过
- Istio sidecar 自动注入、OPA/Gatekeeper 策略校验、Pod 安全基线（PodSecurity）。
