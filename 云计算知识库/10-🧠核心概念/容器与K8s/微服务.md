# 微服务

## 一句话定义
微服务是一种架构风格：把一个大系统拆成**许多小而专、各自独立部署、通过通信协作**的服务（如 Web 前端、购物车、鉴权、日志各一个服务），每个服务可由不同团队独立开发、发布、扩缩容。

## 它解决什么问题 / 为什么存在
单体应用改一处要整体发版、一个模块崩全盘崩、扩缩容只能整体扩。微服务把系统切成「高内聚低耦合」的小块：单个服务可独立迭代、独立扩容、故障隔离——这正是 [[云原生]] 应用能「自动扩缩容、故障自愈、在线升级」的结构基础。

## 核心原理（大二能懂的水平）
- 每个微服务通常打包成一个 [[容器]]，跑在一个 [[Pod]] 里，经 [[Deployment]] 管理、经 [[Service]] 暴露。
- 服务间通过网络调用互相协作——这就需要 [[DNS与服务发现]] 和 [[网络模型]] 支撑（Pod IP 会变，靠服务名找）。
- 拆分原则：一个容器做一个「需求点（concern）」，如「提供 Web 页」和「同步文件」拆两个容器/服务（第4章）。
- 微服务 + Kubernetes 的组合，正是书里说的「云原生微服务应用」。

## 关键参数 / 易错点
- **易错**：拆太细 → 服务爆炸、网络调用猛增、排错难；拆太粗 → 回到单体。按「业务边界/团队边界」拆，而非一味求小。
- **易错**：微服务间调用默认是未加密的明文网络流量，敏感场景要上服务网格/TLS（第2、12章提到）。
- **易错**：以为上了微服务就自动高可用——每个服务仍需配 [[探针LivenessReadiness]]、[[资源限制与QoS]]、多副本。

## 类比（帮助理解）
微服务像「美食城档口」：每个档口（服务）只卖一样（专），各自收银排队（独立扩缩容），一家关门（故障）不影响别家；顾客（请求）在档口间串着买。对比单体像「大食堂一个窗口啥都卖」，一个师傅请假整队瘫痪。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY。
做需要「多团队并行、部分模块流量洪峰、要不停机迭代」的系统时，我会按业务边界拆成微服务，每个服务独立镜像+Deployment+Service，配合服务发现与配置外置（[[ConfigMap]]/[[Secret]]），让每个服务能独立发版和扩缩容。

## 典型应用 / 我在哪见过
- 第1章：电商系统拆成 Web 前端/分类/购物车/鉴权/日志/持久化等多个微服务，各自独立扩缩容。
- 第2章：用足球队「教练(编排) + 各司其职球员」比喻微服务编排。
