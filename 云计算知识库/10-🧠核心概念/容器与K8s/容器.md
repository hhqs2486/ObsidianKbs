# 容器

## 一句话定义
> 容器是把应用和它依赖的运行环境一起打包成的、轻量、隔离的可执行单元（本质是被 Linux 命名空间/控制组隔离的进程）。

## 它解决什么问题 / 为什么存在
- "在我机器上能跑"的问题：开发、测试、生产环境不一致导致部署失败。容器把代码+依赖+配置打包成镜像，到处运行一致。
- 比虚拟机更轻：不用每个应用带一个完整操作系统，启动快、资源占用小。

## 核心原理（大二能懂的水平）
- 容器利用 Linux 的 Namespace（隔离：网络、进程、文件系统等，像"各自一个小房间"）和 Cgroup（限制：能用多少 CPU/内存）。
- 镜像是容器的"模板"，容器是镜像运行起来的实例。
- 在 K8s 里，容器并不直接被调度，而是被包在 [[Pod]] 里由 [[kubelet]] 管理；容器的网络/存储通常来自 Pod 提供的底座。

## 关键参数 / 易错点
- 镜像标签：用 `镜像:标签` 指定版本，别总用 `latest`（不可控、难回滚）。
- `imagePullPolicy`：Always/Never/IfNotPresent。本地构建的镜像常设 IfNotPresent 或 Never。
- 易错：把持久数据写进容器文件系统——容器销毁数据就没了，要用 [[Volume]] / [[PV与PVC]]。
- 易错：一个容器只跑"一个主进程"最清晰；塞一堆后台进程反而难管理。

## 类比（帮助理解）
- 容器像"方便面杯"：面（应用）+ 调料（依赖）+ 杯子（隔离环境）一体，到哪用热水（运行时）都能泡出一样的面；杯子扔了里面东西也没了。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY。
- 要把一个 Spring Boot 服务标准化交付时，写 Dockerfile 把它打成镜像，再用 K8s 跑成容器，保证任意环境行为一致。

## 典型应用 / 我在哪见过
- 第11章把 Spring Boot 的 jar 写 Dockerfile 打成 demo 镜像，再由 Deployment 跑成容器；第2/3章安装时节点都要有 Docker 引擎。
