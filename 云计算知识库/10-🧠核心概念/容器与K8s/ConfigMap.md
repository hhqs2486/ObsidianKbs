# ConfigMap

## 一句话定义
ConfigMap（CM）是 Kubernetes 里用来**把应用的「配置」和「镜像」解耦**的 API 对象，本质是一个存「键值对/配置文件」的 map，运行时再注入到 [[Pod]] 的容器里。

## 它解决什么问题 / 为什么存在
以前把配置写死在镜像里：dev/test/prod 三个环境就要打三个镜像、存三个仓库，改个拼写错误都要重新打包+滚动升级，而且生产镜像里塞着密码谁都能看到。ConfigMap 让**一份通用镜像跑所有环境，只在部署时喂不同的配置**——镜像可复用、易测试、改配置不用动镜像。

## 核心原理（大二能懂的水平）
- ConfigMap 是 core API 组里稳定的 v1 对象，没有 spec/status，只有 `data`（一组 key:value）。
- 数据注入容器的三种途径：①环境变量（`env.valueFrom.configMapKeyRef`）；②容器启动命令参数；③挂成一个**卷**（卷里的每个 key 变成一个文件）。
- 前两种是「静态」的：运行时改了 ConfigMap，已经在跑的容器**不会**自动更新；**卷方式会热更新**，所以最灵活，最推荐。

## 关键参数 / 易错点
- `kubectl create configmap <名> --from-literal k=v`（字面值）或 `--from-file 文件`（key 用文件名，value 用文件内容）。
- 声明式写 `kind: ConfigMap` + `data:` 块；多行配置用 `key: |`（管道符）原样保留。
- **易错**：ConfigMap 不加密、不隐蔽，**绝不能放密码/密钥**——那种东西归 [[Secret]]。
- **易错**：环境变量方式下改 CM 不会生效到运行中的 Pod，排错时别以为改了就行。

## 类比（帮助理解）
ConfigMap 像「便利贴」：把应用写成一张通用便签纸，旁边贴一张便利贴写「当前环境该连哪个数据库、开多大缓存」。换房间（环境）就换一张便利贴，纸不用重印。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY。
做多环境部署的系统时，我会把**所有非敏感配置**（端口、特性开关、配置文件如 nginx.conf）抽成 ConfigMap，做到「一份镜像，三套配置」，改配置零重建、零发版。

## 典型应用 / 我在哪见过
- 第9章实战：用 `multimap`（given/family）注入环境变量；用 `test.conf` 整个配置文件经**卷**挂到 `/etc/name`。
- 典型：Web 服务配置、数据库地址、功能开关、日志级别。
