# 多阶段构建

## 一句话定义
> 多阶段构建（multi-stage build）是 [[Dockerfile]] 的一种写法：在一个 Dockerfile 里用多个 `FROM` 起「阶段」，前面阶段负责编译构建，最后阶段只把需要的产物 `COPY --from=` 拷进一个极简运行时镜像，从而**让最终镜像大幅瘦身**。

## 它解决什么问题 / 为什么存在
- 一个 Java 应用如果「在 Maven 镜像里编译 + 跑」，最终镜像会带上整个 JDK、Maven、源码、构建缓存——几百 MB 甚至上 GB。
- 但运行时其实只需要 JRE + 一个 jar。多阶段构建把「构建环境」和「运行环境」分开，最终镜像只留运行时所需。

## 核心原理（大二能懂的水平）
- 用 `FROM ... AS builder` 给阶段命名；后面阶段用 `COPY --from=builder /app/target/*.jar /app.jar` 只取产物。
- 典型两段：
  1. 构建阶段：`FROM maven:3.5.0-jdk-8-alpine AS builder` + `RUN mvn clean package`
  2. 运行阶段：`FROM openjdk:8-jre-alpine` + `COPY --from=builder ...` + `ENTRYPOINT java -jar`
- `scratch` 是空镜像，常用于多阶段构建最终只放纯静态二进制（如 Go 编译出的单文件）。
- 还可以三段：git 克隆阶段 → maven 构建阶段 → jre 运行阶段（用 ARG 传 git 地址自动拉代码构建）。

## 关键参数 / 易错点
- `AS <name>` 给阶段起名，`COPY --from=<name|阶段序号>` 取文件；不命名可用 `--from=0`。
- 最终镜像大小 ≈ 运行阶段基础镜像 + 产物；选 `openjdk:8-jre-alpine` / `slim` 等小底包。
- 配合：合并 RUN 减少层数、同一条 RUN 内清理 apt 缓存、用 `.dockerignore` 排除无关上下文、`--no-cache` 强制重构建。
- 时区问题：`RUN ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime`。

## 类比（帮助理解）
- 像「盖楼」：第一阶段是「工地 + 塔吊 + 水泥厂」（构建环境），盖好后只把「建好的楼」（jar）搬进第二阶段「精装现房」（jre 镜像）；你交付的房子不附带塔吊和水泥厂。

## 设计时怎么用（反推思维）
> 做「把后端服务做成小镜像上 [[Kubernetes]]」时，我会一律用多阶段构建：编译在 builder 阶段，运行阶段只留 JRE+jar，让镜像从 1GB 降到几十 MB，拉取快、攻击面小、符合 [[云原生]] 轻量理念。

## 典型应用 / 我在哪见过
- Java / Go / 前端等「需编译、运行时轻」的语言；CI 里直接 `docker build` 出可运行镜像。
- 见过：《Docker实战(图解)》ch04 第11节 multi-stage builds + 第12节镜像瘦身实践（maven→jre-alpine 完整示例、git 克隆三段式）。
