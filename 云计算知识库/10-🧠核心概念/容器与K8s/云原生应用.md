# 云原生应用

## 一句话定义
> 为云环境“出生即设计”的应用：以容器打包、以微服务拆分、以声明式 API 在 [[Kubernetes]] 上运行，借助弹性与自动化来应对不确定的负载。

## 它解决什么问题 / 为什么存在
- 传统应用“搬上云”只是换了个机房（原样迁移，IaaS 只做资源平移），没解决弹性、容错、发布频率的本质问题。
- 云原生让应用**天生**能利用云的弹性与分布式能力：流量来了自动扩、挂了自动拉、发布可灰度可回滚。

## 核心原理（大二能懂的水平）
- 三大支柱：
  1. **容器化**——以 [[容器云平台]]/K8s 作为可移植层（一次构建，多处运行）。
  2. **微服务化**——服务边界清晰、可独立扩缩、独立发布。
  3. **声明式运维**——用 YAML 描述“期望状态”，K8s 的控制器持续把“实际状态”调谐到“期望状态”。
- 再叠加 DevOps/[[CI-CD]]、服务网格（如 [[Istio]]）、可观测性等能力，形成完整闭环。

## 关键参数 / 易错点
- “云原生”是**架构思维**不是技术堆砌：先问“这个需求能不能弹性扩缩、能不能滚动发布、故障能否自愈”。
- 容器只是起点，真正的收益来自**声明式 API + 控制器模式**（期望状态 vs 实际状态），而不是单纯把应用塞进容器。
- **PaaS 化**（见 [[PaaS平台]]、[[容器云平台]]）是把这些能力封装成“应用级”平台，让开发只关心代码、不关心集群。
- 注意**可移植性**：遵循 CNCF 标准，避免被单一厂商锁定（[[多集群管理]] 也是为此）。

## 类比（帮助理解）
- 像乐高：每个微服务是标准积木（容器），按图纸（声明式 YAML）拼装，少一块 K8s 就自动补一块（调谐）。
- 传统应用像整体浇铸的雕塑，搬动和修补都很贵——这就是“伪云原生”（只搬不改造）的代价。

## 设计时怎么用（反推思维）
> 做 XX 系统时，如果需求是“快速迭代、弹性应对流量、多环境一致部署”，我会按云原生思路落地：容器化打包 → 拆微服务 → 上 [[Kubernetes]] 用 [[Deployment]]/[[Service]] 管理 → 接 [[CI-CD]] 与 [[PaaS平台]]；并明确区分哪些组件做成 [[无状态应用]]、哪些必须是 [[有状态应用]]。

## 典型应用 / 我在哪见过
- 基于 K8s 的 PaaS：OpenShift、腾讯云 CCS、华为云 CCE/CCI、Azure AKS。
- Serverless（如 Azure Functions）、微服务中台、云化中间件（DDM/DCS/DMS）。
- 《Kubernetes PaaS 冲击波》通篇论述：容器 + K8s 的新型 PaaS 正成为云计算主流。
