# 多集群管理

## 一句话定义
> 同时管理**多个 Kubernetes 集群**（跨地域 / 跨云 / 开发测试生产隔离），实现统一的应用分发、全局视图、故障转移与资源调度。

## 它解决什么问题 / 为什么存在
- 单集群有规模上限、单一故障域、就近访问延迟、合规与隔离（生产/测试必须分开）等诉求，一个集群装不下整个企业。
- 书第 16 章 16.3.5 **部署架构**给出的朴素多集群方案：按区域分成**开发测试区、准生产区、生产区**，各区域相互隔离、各部署一套容器平台，区域间交互主要通过**镜像仓库同步镜像**。这就是一种最务实的多集群管理。

## 核心原理（大二能懂的水平）
- 多集群管理的两种成熟度：
  1. **各集群独立 + 镜像同步**（书 16.3.5 的做法）：集群间不强耦合，只靠镜像仓库传递交付物，简单但运维要在多套门户间切换。
  2. **统一控制面 / 集群联邦**：用一套控制面把应用和配置下发到多个成员集群（见 [[集群联邦KubeFed]]），获得全局视图与跨集群调度。
- 无论哪种，成员集群底层仍是独立的 [[Kubernetes]]，靠 [[高可用集群]] 保证单集群可靠，靠网络隔离/镜像同步保证跨集群边界。

## 关键参数 / 易错点
- 集群间**网络隔离**与**镜像同步方向**（书 16.3.5 图 16-9 镜像同步方向要设计清楚，否则环境串味）。
- 跨集群**服务发现 / 全局 DNS**、故障转移策略。
- 易错：把"多集群"理解成"把单集群节点数翻倍"——集群是故障域边界，翻倍只是单集群变大，跨集群的意义（隔离/就近/容灾）没解决。

## 类比（帮助理解）
- 一家公司在多个城市都有分公司（每个分公司 = 一个集群）。多集群管理就是**集团总部**：统一派活（应用下发）、统一看报表（全局监控）、某地出事把活转给别地（故障转移）。

## 设计时怎么用（反推思维）
> 做金融/大型企业容器云时，我会按"**多套平台 + 镜像仓库作唯一交付通道**"起步（书 16.3.5）：先满足区域隔离与合规，等业务真需要跨集群统一调度时再上 [[集群联邦KubeFed]]，而不是一上来就追求联邦复杂度。

## 典型应用 / 我在哪见过
- 书 16.3.5 金融容器云"开发测试区 / 准生产区 / 生产区"三套隔离平台。
- 业内：跨 AZ 容灾、混合云（私有云 + 公有云突发扩容）、多租户分集群都是多集群场景。
