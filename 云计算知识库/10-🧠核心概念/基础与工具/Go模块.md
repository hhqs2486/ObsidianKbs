# Go模块（Go Modules）

## 一句话定义
> Go Modules 是 Go 官方的依赖管理方案，用 `go.mod` 锁定「依赖谁、哪个版本」，解决「项目搬到别处编译不过 / 依赖版本漂移」的问题。

## 它解决什么问题 / 为什么存在
- 早期 GOPATH 模式下所有项目共用一份代码，版本无法隔离；第三方工具（glide / dep / gb）碎片化。
- Modules 让每个项目自带版本清单，实现**可复现构建（reproducible build）**：换机器、换时间，构建结果一致。

## 核心原理（大二能懂的水平）
- `go.mod` 记录 module 路径、Go 版本、`require` 依赖（含精确版本号，如 `v1.2.3`）。
- `go.sum` 记录依赖内容的哈希校验值，防依赖被篡改。
- 版本语义：语义化版本 `vMAJOR.MINOR.PATCH`；**v2 及以上必须在路径带 `/v2` 后缀**（不兼容变更）。
- `go get` 拉取、`go mod tidy` 清理未用依赖、`go mod verify` 校验完整性。

## 关键参数 / 易错点
- `go mod init <module>` 初始化；`replace` 指令可指向私有 / fork 源（企业内网常用）。
- 国内需设 `GOPROXY`（如 goproxy.cn）加速；私有库设 `GOPRIVATE` 跳过校验。
- 易错：忘了 `go mod tidy` 导致 `go.mod` 冗余；`v2+` 不写 `/v2` 后缀会冲突。
- 主版本升级（v1→v2）是「不兼容变更」，路径必须带版本。

## 类比（帮助理解）
- `go.mod` 像「食谱的原料清单（品牌 + 批次号）」，`go.sum` 像「每样原料的防伪码」；换厨房（换机器）按清单买同批次，味道（构建结果）一致。

## 设计时怎么用（反推思维）
> - 需求「团队 CI 可复现构建、可审计依赖」→ 反推：用 Go Modules + `go mod verify`，接入 [[CI-CD]] 流水线做门禁。
> - 需求「引用私有库」→ 反推：`go.mod` 里 `replace` + `GOPRIVATE` 指向内网仓库（配合 [[Git]]）。

## 典型应用 / 我在哪见过
- 所有现代 Go 项目；与 [[Git]] 仓库、[[CI-CD]] 流水线配合形成「提交即构建」的研发闭环。
