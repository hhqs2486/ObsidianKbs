# 依赖注入

## 一句话定义
> 依赖注入（Dependency Injection, DI）是实现控制反转（IoC）的具体手段——由容器在运行时把「被依赖的对象」主动送进调用方，而不是调用方自己去 `new`。

## 它解决什么问题 / 为什么存在
- 调用方不需要知道依赖「怎么创建、从哪来」，只声明「我要什么类型」，从而获得解耦、可测试（可注入 Mock）、可替换实现的好处。
- 没有 DI 时，对象内部硬编码 `new` 具体类（书里 `FXNewsProvider` 直接 `new DowJonesNewsListener`），换新闻源就要改源码、无法单测。

## 核心原理（大二能懂的水平）
- Martin Fowler 总结三种注入方式（《Spring的IoC容器》第 2 章 2.2 节）：
  1. **构造方法注入（constructor injection）**：在构造参数里声明依赖，对象建好即可用；但依赖多了构造参数会很长。
  2. **setter 方法注入（setter injection）**：通过 `setXxx()` 注入，构造后可补，更灵活、可继承、能设默认值。
  3. **接口注入（interface injection）**：实现特定接口来接收依赖，侵入性强，已基本退役。
- Spring 主要用前两种，配合 `@Autowired` / `@Inject` 或 XML 配置完成装配。DI 是 IoC 的一种实现方式（书里将 IoC 与 DI 等同看待）。

## 关键参数 / 易错点
- 构造器注入适合「必填、不可变」依赖；setter 注入适合「可选」依赖。
- **循环依赖**是经典坑：A 注入 B、B 又注入 A。Spring 用三级缓存解决单例的循环依赖，但**构造器注入无法解决循环依赖**（会直接报错），需改回 setter 或重构。
- 不要把 DI 和 [[Spring IoC]] 割裂理解：DI 是 IoC 的实现方式，不是两个独立概念。

## 类比（帮助理解）
- 酒吧点酒：你只说「来杯 Tsingdao」（声明依赖），服务生（容器）把酒送过来（注入），你完全不用自己去酿酒、去取酒。

## 设计时怎么用（反推思维）
> 设计类时，对「会被替换 / 需要单测」的依赖一律用接口 + 注入点暴露，绝不在类内部 `new` 具体实现；必填依赖用构造器注入，可选依赖用 setter。这样换实现、写 Mock 测试都零改业务代码。

## 典型应用 / 我在哪见过
- [[Spring IoC]] 容器靠 DI 完成对象装配；单元测试里注入 `MockNewsListener` 验证「取新闻失败」分支（书第 2 章示例）。
- 几乎所有 Java 后端框架（Spring / Jakarta CDI / Guice）都采用 DI。
