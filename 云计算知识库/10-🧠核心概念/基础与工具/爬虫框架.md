# 爬虫框架

## 一句话定义
> 把"下载→调度→解析→存储"这套通用流程**预先封装好的爬虫开发脚手架/库**，让开发者只写"抓什么、怎么解析"。

## 它解决什么问题 / 为什么存在
- 自己从 HttpClient 手搓：要手写 URL 队列、Visited 去重、超时重试、并发控制、入库管道……样板代码极多、易错。
- 框架把这些**通用逻辑沉淀为组件**，开发者专注业务：定义 Spider（解析规则）和 Pipeline（清洗入库）即可。
- 一句话：**降低写一个"能跑、能扩展"的爬虫的门槛**。

## 核心原理（大二能懂的水平）
框架通常是一条组件化的流水线（以 Scrapy 为典型）：
- **Scheduler（调度器）**：管理 TODO/Visited 队列（对应手搓爬虫的 `LinkQueue`）。
- **Downloader（下载器）**：发 HTTP 请求、处理重试/代理/超时。
- **Spider（爬虫）**：拿到 Response，用 [[网页解析]] 抽字段、产出 Item 和新 Request。
- **Pipeline（管道）**：清洗、去重、入库（关系库 / key-value / 消息队列）。
- 并发靠**线程池或异步事件循环**（Scrapy 基于 Twisted 异步）实现高吞吐。

## 关键参数 / 易错点
- **并发数** `CONCURRENT_REQUESTS`：太高易触发 [[反爬虫]]，太低太慢。
- **下载延迟** `DOWNLOAD_DELAY`：礼貌限速，别打挂目标站。
- **重试 / 超时 / 代理池 / UA 池**：工程必需，框架一般提供中间件配置。
- **遵守 robots.txt**（`ROBOTSTXT_OBEY`）。
- 易错：**在 Spider 里写阻塞 IO**（如下载大文件、慢查询），会卡死异步事件循环——耗时操作放 Pipeline 或独立线程。

## 类比（帮助理解）
> 像"全自动采摘流水线"——你只需告诉机器摘哪种果子、果子长啥样（写 Spider），机器自动走遍果园（调度）、装筐（下载）、分拣（解析）、运走入库（Pipeline）。

## 设计时怎么用（反推思维）
> 做分布式采集系统时，我会用**爬虫框架（如 [[Scrapy]]）搭单体采集器**，再用 [[微服务]] 部署多个实例、用 [[Kubernetes]] 按抓取压力横向扩容；框架负责"单体内能跑"，编排负责"多实例协同"。

## 典型应用 / 我在哪见过
- Python：[[Scrapy]]、PySpider；Java：WebMagic、Nutch（分布式）；Go：Colly。
