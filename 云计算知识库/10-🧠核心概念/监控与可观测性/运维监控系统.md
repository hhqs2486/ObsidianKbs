# 运维监控系统

## 一句话定义
> 运维监控系统 = 对服务器、网络、[[虚拟机]]、应用持续采集指标并告警的平台（如 Zabbix / Nagios / Cacti / Open-Falcon），目标「故障早发现、根因快定位」。

## 它解决什么问题 / 为什么存在
- 机器 / 服务不会主动喊疼。没有监控，故障靠用户投诉才发现，定位如盲人摸象。
- 监控系统把「系统健康」变成可视、可告警的信号，是 [[可观测性]] 的基石之一（见 [[Zabbix]]）。

## 核心原理（大二能懂的水平）
- **采集**：agent（Zabbix agent / falcon-agent）或 SNMP / 主动 push，拉 CPU / 内存 / 磁盘 / 网络 / 端口。
- **存储**：时序 / 关系存储，RRDtool 等轮询归档。
- **告警**：阈值触发 → 邮件 / 短信 / Webhook；支持维护期、告警抑制。
- **展示**：Dashboard（Cacti / Zabbix 图形）。
- 代表：Zabbix（企业级、自带 Java / VMware / 硬件监控）、Nagios（状态 / 日志 / 告警老牌）、Open-Falcon（小米开源，Go 写、水平扩展）、Icinga（Nagios 分支）、Cacti（RRDtool 图形化）。

## 关键参数 / 易错点
- Zabbix 可每分钟 300 万次检查；Open-Falcon 单 graph 撑 200 万 metric / 分钟。
- 易错：只监控「活没活」（up / down）忽略「慢不慢」（延迟 / 饱和度）；告警风暴无分级。
- 与 [[Prometheus]] 互补：传统监控偏「主机 / 网络 + 静态阈值」；Prometheus 偏「云原生 / 容器 + 多维标签 + PromQL」。

## 类比（帮助理解）
- 运维监控系统像「大楼的烟感和体温计」：体温计（指标）持续测，超阈值（火警）立刻响；但要知道「为什么着火」还需结合日志 / 链路（[[可观测性]] 三支柱：指标 / 日志 / 链路）。

## 设计时怎么用（反推思维）
> - 需求「服务器宕机 5 分钟内告警」→ 反推：Zabbix + agent 采存活 / 资源，阈值告警。
> - 需求「K8s 集群可观测」→ 反推：[[Prometheus]] 采容器指标 + 本类系统采宿主机，共构 [[可观测性]]；集群内用法见 [[监控Kubernetes集群]]。

## 典型应用 / 我在哪见过
