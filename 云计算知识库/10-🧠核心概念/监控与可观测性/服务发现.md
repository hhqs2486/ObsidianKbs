# 服务发现

## 一句话定义
服务发现是 Prometheus 自动探测、登记"当前有哪些抓取目标（target）"的机制，让监控能跟上传云/容器环境里目标的频繁创建与销毁，而不必手写静态 IP 列表。

## 它解决什么问题 / 为什么存在
静态配置（`static_configs`）在主机少时尚可，但在动态、规模化的[[容器]]/[[Kubernetes]]环境里完全不可扩展——新实例上线你根本来不及改配置。服务发现把"目标清单"外部化、自动化。

## 核心原理（大二能懂的水平）
- 抓取生命周期第一步就是服务发现：返回**目标列表 + 元数据标签（以 `__meta_*` 开头）**。
- 三类机制：
  - **基于文件**：JSON/YAML 目标文件，由配置管理（Puppet/Ansible/Chef）或 CMDB 生成，Prometheus 按 `refresh_interval` 重载（如 `file_sd_configs`）。
  - **基于 API/平台**：直接查平台（EC2、Consul、[[Kubernetes]] `kubernetes_sd_configs`、GCE）返回目标。
  - **基于 DNS**：查 SRV/A/AAAA 记录返回目标（如 `_alertmanager._tcp.example.com`）。
- 抓前 `relabel_configs` 用 `__meta_*` 丰富标签（如把 EC2 tag 写成 instance 名），这是把"发现信息"变成"指标维度"的关键。

## 关键参数 / 易错点
- `__meta_*` 标签在 relabel 后会被丢弃，不会出现在 Web UI。
- kubernetes_sd_configs 的 `role` 决定发现什么：`endpoints`/`node`/`pod`/`service`/`ingress`。
- 注解（如 `prometheus.io/scrape`）经服务发现变成 `__meta_kubernetes_service_annotation_prometheus_io_scrape`，再经 relabel 决定是否抓取。
- `labelmap` 动作可把 K8s 元数据标签复制成普通标签。

## 类比（帮助理解）
服务发现像"公司前台自动更新员工通讯录"——新人入职自动入册、离职自动划掉，不用你每次手动改纸质名单。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY。
部署监控时，我会优先用平台原生服务发现（[[Kubernetes]] 用 `kubernetes_sd_configs` + 注解），让"新服务零配置被纳入监控"，而非维护易过期的静态 IP 表。

## 典型应用 / 我在哪见过
- 第5章：文件/EC2/DNS 三种 SD 示例与 relabel。
- 第12章：用 `kubernetes_sd_configs`(role=endpoints) + `prometheus.io/scrape` 注解自动发现 Node Exporter、Kube-state-metrics、API Server。
