# 日志收集与监控

## 一句话定义
> 日志（Log）是**可观测性三大支柱之一**（指标 Metrics / 日志 Logs / 链路 Traces）：记录系统、应用、网络设备运行时产生的离散事件文本，用来回答"**当时到底发生了什么具体错误**"。

## 它解决什么问题 / 为什么存在
- [[Prometheus]] 这类指标监控只能看"趋势和阈值"（CPU 高了、QPS 跌了），但看不出"为什么"。日志能还原事故现场的具体报错、堆栈、调用上下文。
- 课件里把"日志监控"列为监控种类里的**重头戏**（Splunk、ELK），往往要单独设计和搭建，全部种类的日志都要采集（syslog、业务软件日志、网络设备日志、用户行为日志）。
- 与指标互补、不替代：指标用于告警和宏观趋势，日志用于排查根因和审计。

## 核心原理（大二能懂的水平）
- **采集 → 传输 → 存储 → 检索/可视化** 四段式管道。
- **采集位置**：
  - Agent 常驻（如 Filebeat）：装在被采集机，tail 日志文件推走。
  - Sidecar：每个 Pod 旁挂一个日志容器，读主容器 stdout。
  - **DaemonSet**：K8s 里最常用，每节点跑一个采集器，读 `/var/log/containers/*.log` 与 `/var/log/pods/`。
- **主流技术栈**：
  - **ELK**：Elasticsearch（存储+检索）+ Logstash（清洗转换）+ Kibana（可视化），常配 Filebeat 采、Kafka/Zookeeper 做缓冲。
  - **EFK**：ElasticSearch + **Fluentd**（替代 Logstash 做采集清洗）+ Kibana。
  - **轻量云原生栈**：**Loki + Promtail + Grafana**——Loki 只索引标签不索引全文，成本低，和 Prometheus 同生态， Grafana 统一看指标和日志。

## 关键参数 / 易错点
- **日志量巨大**：必须做轮转（logrotate）、采样、冷温热分层，否则 ES 成本爆炸。
- **结构化日志（JSON）**远优于纯文本：字段可被检索、聚合；写日志时带上 `trace_id` 才能和链路追踪打通。
- **敏感信息脱敏**：密码、token、身份证不能进日志。
- **易错**：把日志监控和指标监控混为一谈——二者职责不同，应并列建设。
- **易错**：只采应用日志忘了采集系统/网络/中间件日志，排查时缺拼图。

## 类比（帮助理解）
指标像"体温计"（知道发烧了），日志像"病历本"（知道得的什么病、哪一步出错）。可观测性 = 体温计 + 病历本 + CT（链路）三件套齐全。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY。
做需要**快速定位线上故障根因**的系统时，我会搭一套日志管道：容器用 DaemonSet 采日志 → Kafka 缓冲 → ES/Loki 存储 → Kibana/Grafana 检索；并强制要求业务日志结构化、带 `trace_id` 与指标监控联动。
