# Zabbix

## 一句话定义
> Zabbix = 企业级开源监控解决方案：通过从服务器、[[虚拟机]]、网络设备采集数据，提供实时监控、自动发现、拓扑映射与可扩展告警，每分钟可做 300 万次检查。

## 它解决什么问题 / 为什么存在
- 中大型 IT 基础设施（服务器 / 网络 / VM / 应用）需要一套「开箱即用、集中、可扩展」的监控，而非零散脚本。
- Zabbix 用统一平台覆盖采集 → 存储 → 告警 → 展示全链路，是 [[运维监控系统]] 的代表作。

## 核心原理（大二能懂的水平）
- **架构**：Zabbix Server（核心，存数据 + 算告警）+ 数据库 + Zabbix Agent（装在被监控机，被动 / 主动上报）+ Web 前端（Dashboard）。
- **采集**：Agent、SNMP、IPMI、JMX（内置 Java 应用服务器监控）、VMware 监控。
- **能力**：自动发现（auto-discovery）、网络拓扑映射、模板化监控项、触发器（trigger）告警、动作（action）通知。
- **扩展**：proxy 做分布式监控，适合多机房 / 大规模。

## 关键参数 / 易错点
- 性能：Server 每分钟 300 万次检查；大集群用 proxy 分压、调数据库（历史表分区）。
- 易错：监控项过多拖垮 Server；触发器阈值拍脑袋无分级；agent 防火墙端口（10050 / 10051）未放。
- 与 [[Prometheus]] 取舍：Zabbix 偏传统主机 / 网络、模板化、上手快；Prometheus 偏云原生 / 多维 / 需自搭生态。

## 类比（帮助理解）
- Zabbix 像「医院中央监护仪」：每台床（服务器）插传感器（agent）实时传体征，中央屏（Server + Web）统一显示，异常自动呼叫（告警），还能自动画出病房布局（拓扑）。

## 设计时怎么用（反推思维）
> - 需求「统一监控几百台物理机 + VM，出拓扑图」→ 反推：Zabbix Server + Agent + 自动发现 + 模板，配 proxy 分压。
> - 需求「K8s 内部 Pod 级监控」→ 反推：Zabbix 管宿主机，Pod 级交给 [[Prometheus]] / [[监控Kubernetes集群]]。
