# 告警规则

## 一句话定义
告警规则是写在 Prometheus 规则文件里的 YAML 表达式：当某个[[PromQL]]查询结果满足阈值/条件并持续一段时间，就生成一条告警，推给[[Alertmanager]]。

## 它解决什么问题 / 为什么存在
光有指标只能"人去看"，告警让系统在异常时**主动通知人**。但告警也是双刃剑——错了就"狼来了"。规则的质量直接决定告警疲劳与否。

## 核心原理（大二能懂的水平）
- 规则结构：`alert`(名) / `expr`(PromQL 条件) / `for`(持续多久才 Firing) / `labels`(附加标签，如 severity) / `annotations`(描述/链接等上下文，支持 Go 模板 `{{$labels.x}}`、`{{$value}}`)。
- 状态机：**Inactive → Pending（`for` 计时中）→ Firing（通知发出）**。带 `for` 的规则至少需两个评估周期才触发，防抖动。
- 评估频率由 `evaluation_interval` 控制；Pending/Firing 期间 Prometheus 会自动生成 `ALERTS` 指标。
- 好告警三原则：**对症状而非原因告警**、正确优先级、带上下文。

## 关键参数 / 易错点
- `for` 子句不能太长也不能太短（本书用 60s~数分钟），用于过滤瞬时抖动。
- `up == 0` 监控抓取失败；目标彻底消失用 `absent(up{job="x"})` 检测（否则无指标可比较）。
- 磁盘耗尽预测用 `predict_linear(node_filesystem_free_bytes[1h], 4*3600) < 0`。
- 通知模板要"给人看"：含实例、阈值、runbook 链接，别只发"磁盘 91%"。

## 类比（帮助理解）
告警规则像"给系统装的烟雾报警器"——平时静默，只有真冒烟（且持续冒一会儿）才响；装太多误报的报警器，人最后会拔电池（告警疲劳）。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY。
设计告警时，我会先列"用户可感知的症状"（高延迟/错误率/不可用），用[[指标Metric]]+PromQL 表达，再用 `for` 去抖、`severity` 分级、模板补上下文，最后交给 Alertmanager 按标签路由。

## 典型应用 / 我在哪见过
- 第6章：HighNodeCPU（CPU>80% 持续 60 分）、磁盘 4h 耗尽、节点服务宕机、Prometheus 找不到 Alertmanager。
- 第12/13章：Kubernetes 部署副本未更新、Pod 重启过多、API p99 延迟、MySQL 慢查询、Redis 命中率低。
