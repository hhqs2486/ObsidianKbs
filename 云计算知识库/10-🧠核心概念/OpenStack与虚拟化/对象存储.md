# 对象存储

## 一句话定义
> 对象存储是以"对象（数据+元数据+全局唯一 ID）"为最小单元、用 REST（S3/Swift 兼容）接口存取的存储形态：无目录层级、不挂载、靠 HTTP 直读，适合海量非结构化数据。

## 它解决什么问题 / 为什么存在
- 图片、视频、备份、日志这类"一次写多次读、量大、要能 HTTP 直链"的数据，用块/文件系统都很别扭。对象存储用扁平命名空间+HTTP 接口天然适配，且易水平扩展。

## 核心原理（大二能懂的水平）
- Ceph 通过 **RGW（RADOS Gateway，`radosgw`）** 提供 S3/Swift 兼容的对象接口；RGW 本身是 Ceph 的一种客户端，把对象请求翻译成对 [[RADOS]] 对象的读写（第一部分 5.1 提到 `radosgw` 是客户端，不单独列为守护进程类型）。
- 与 [[RBD]]/[[CephFS]] 一样，对象最终落在 [[Ceph OSD]]；区别只在入口协议（HTTP REST vs 块设备 vs POSIX 文件系统）。

## 关键参数 / 易错点
- 接口兼容 S3 与 [[Swift]]：[[OpenStack]] 里 Swift 是另一套对象存储，Ceph 的 RGW 可让 Ceph "伪装成" Swift/S3，便于替换。
- 对象名+存储池即可定位（同 [[RADOS]] 规则），无"文件夹"概念（逻辑前缀只是命名约定）。
- FileStore 时代 ext4 因 xattr 长度限制不支持长对象名，会破坏 RGW 需求；故推荐 xfs（第二部分 2.4）——这也催生了 [[BlueStore]] 直接管裸盘。

## 类比（帮助理解）
> 对象存储像"快递柜自助寄取"：每个包裹贴唯一单号(对象 ID)，你用手机(HTTP)随时寄/取，不用进仓库翻货架；仓库内部仍按 [[RADOS]] 编号规则存放。

## 设计时怎么用（反推思维）
> 应用要"海量文件+HTTP 直链+不限目录层级"(如用户头像、审计日志、镜像仓库) → 用对象存储(S3 接口)，让 Ceph RGW 当后端，或接 [[OpenStack]] 的 [[Swift]]。

## 典型应用 / 我在哪见过
- 第一部分 5.1（RGW/radosgw 被定义为 Ceph 客户端）；本书主线以 RBD 为重，对象接口仅在架构层提及，但它是 [[Ceph架构]] "三种接口"之一。

## 关联
- 前置知识：[[Ceph架构]] [[RADOS]] 分布式存储
- 相关：[[RBD]]（块，兄弟接口）[[CephFS]]（文件，兄弟接口）[[Ceph OSD]] [[BlueStore]] [[Swift]]（OpenStack 自带对象存储，对照）[[OpenStack]]
- 反例/误区：把对象存储当"网盘文件夹"用嵌套目录——它是扁平命名空间，深层"目录"只是 key 前缀。
