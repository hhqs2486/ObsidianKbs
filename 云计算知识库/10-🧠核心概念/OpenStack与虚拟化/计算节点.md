# 计算节点

## 一句话定义
> 计算节点（Compute Node）是 OpenStack 里真正"跑虚拟机"的机器：在本地用 [[虚拟化KVM]] 把 CPU/内存/磁盘虚拟成实例，并连上网络和存储。

## 它解决什么问题 / 为什么存在
- 云的算力最终要靠真实服务器提供。控制节点只"发指令"，计算节点负责"出力气"——创建/销毁/迁移虚拟机。
- 计算节点可以很多台、按需横向加，是集群里弹性最大的部分。

## 核心原理（大二能懂的水平）
- 计算节点上跑 `nova-compute`（听 [[Nova]] 调度指令）、`libvirtd` + KVM（真正造虚拟机）、以及 Neutron 的 `linuxbridge-agent`（给虚拟机接上虚拟网络）。
- 它**不连数据库**：nova.conf 里没有 `[database]`/`[api_database]`，只通过消息队列（RabbitMQ）和 API 跟控制节点通信（full.txt I 节明确区分）。
- 通过 `nova-manage cell_v2 discover_hosts` 把计算节点注册进 cell 数据库，控制节点才能把虚拟机调度过来（full.txt I 节 `openstack compute service list`）。

## 关键参数 / 易错点
- `[libvirt] virt_type=kvm`：确认 CPU 开了虚拟化（`egrep -c '(vmx|svm)' /proc/cpuinfo` 非 0）。
- 计算节点 nova.conf 与镜像/块存储走 VIP：`glance_api_servers=http://controller:9292`、`transport_url=rabbit://...@controller1:5672,controller2:5672,controller3:5672`。
- 装 `openstack-nova-compute` 时若报 `Requires: qemu-kvm-rhev`，要加 `[centos-qemu-ev]` yum 源（full.txt I 节坑）。
- 若用 Ceph 做后端，计算节点要装 `ceph-common`、把 `client.cinder` 密钥塞进 libvirt（full.txt L、N 节）。

## 类比（帮助理解）
> 计算节点像"车间里的工人"，总部(控制节点)派单，工人用机床(KVM)造产品(虚拟机)，造完通过物流(Neutron)发出去。

## 设计时怎么用（反推思维）
> 容量规划时，计算节点数量由"要跑多少虚拟机、多大规格"反推；它们应跨机架/主机房放，避免一台物理机故障带崩多台虚拟机。存储若用 Ceph，则计算节点无本地状态，方便故障迁移(live migration)。

## 典型应用 / 我在哪见过
- 本书 I、J、N 节：compute1(192.168.100.184) 跑 nova-compute + linuxbridge-agent + libvirtd，并通过 Ceph rbd 启动实例、做 live migration。
