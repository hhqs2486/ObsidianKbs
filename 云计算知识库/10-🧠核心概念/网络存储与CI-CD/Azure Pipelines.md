# Azure Pipelines

## 一句话定义
> Azure DevOps 里负责「把代码自动变成可交付产物」的子服务：提交代码后自动构建、测试，并一路部署到各环境。

## 它解决什么问题 / 为什么存在
- 手动编译、手动拷贝上线既慢又易错；多人协作时「在我机器上能跑」成为噩梦。Pipelines 把「构建 → 测试 → 发布」标准化、自动化、可重复。

## 核心原理（大二能懂的水平）
- 你写一个声明式的管道定义文件（YAML），描述「分几步、跑什么命令、在什么机器上跑」。
- 代码推到仓库（或开 PR）触发「触发器」→ 平台分配一台**代理(agent)**（微软托管或自托管）→ 按 阶段(stage) / 作业(job) / 步骤(step) 顺序执行 → 产出构建产物(artifact)并可继续部署。
- 两段核心能力：[[CI-CD|CI]]（自动合并并构建测试）与 CD（可靠地发布到多环境，见 [[持续交付]]）。

## 关键参数 / 易错点
- 定义文件默认名 `azure-pipelines.yml`，放在仓库根目录才会被自动拾取。
- 有「YAML 管道」（推荐，代码即配置，即 [[流水线即代码]]）与「经典管道」（图形化点选）两种；本书教程走 YAML。
- 代理类型：Microsoft 托管代理（免运维，但需组织有「Microsoft 托管并行作业」额度，免费层 1 并发 / 月 30 小时）vs 自托管代理。
- 阶段示例：「生成(Build)」→「部署(Deploy)」；阶段间可加审批门(approval gate)。
- 易错：并行作业额度不足导致排队；分支 / 路径过滤(PR 触发器)没配好会误触发或漏触发。

## 类比（帮助理解）
- 像工厂的「自动化装配线」：原料(代码)从一端进去，经过清洗(编译)、质检(测试)、包装(打包)，从另一端出来就是可上架的商品(部署包)。你只需写好「产线图纸」(YAML)，机器自动跑。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY：做多服务 Web 应用时，我会用 Azure Pipelines 给每个服务建一条「代码提交 → 自动测试 → 打包镜像 → 部署到 [[Kubernetes]]」的流水线，把「人肉上线」变成「推代码即上线」。

## 典型应用 / 我在哪见过
- 本书「创建第一个管道」：连 GitHub 仓库 → 向导生成 Maven 模板 → 保存 `azure-pipelines.yml` → 自动运行；支持 .NET / Go / Java / Node / Python / 容器。
- 多阶段管道(multi-stage pipeline)把「生成」与「部署」写成同一份 YAML 的不同 stage。
