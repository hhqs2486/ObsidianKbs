# Git（分布式版本控制）

## 一句话定义
最流行的分布式版本控制系统：记录文件的每一次改动历史，让多人协作开发、随时回退、并行分支互不干扰。

## 它解决什么问题
没有版本控制，代码只能靠「v1/v2/最终版/最终版2」手动拷，谁改了什么说不清、改坏了回不去、多人同时改必然冲突。Git 把「历史、分支、合并、协作」变成基础设施。

## 核心原理（大二能懂）
- 仓库（repository）存全部历史；每个人本地有一份完整拷贝（分布式）。
- 提交（commit）= 一次快照，带作者+说明；分支（branch）是独立的开发线，合并（merge）把分支汇回主干。
- 远程仓库（如 GitHub/GitLab）是团队共享的中心，push 上传、pull 下载。
- 类比：Git 像「带无限次撤销的共享文档」，每人能开一个「副本页（分支）」改，改完再合并回总文档。

## 关键参数 / 易错点
- `git clone` 拉全量历史；`git add` → `git commit` → `git push` 是标准上传三步。
- `git pull --rebase` 比 `git pull` 更干净（变基而非产生合并提交）。
- 易错：忘了 `git pull` 就 `git push` 导致冲突；`.gitignore` 没配把依赖/node_modules 也提交。
- Git 是 [[CI-CD]] 流水线的「触发器」：代码 push 即触发自动构建（如 [[Azure Pipelines]]）。

## 一个生活类比
Git = 多人合写一本小说：每个人都有完整草稿（本地仓库），各自在「支线剧情（分支）」上写，主编（merge）把支线合回正文，且每次修改都留痕可回退。

## 设计时怎么用（反推思维）
- 需求「团队并行开发不打架」→ 反推：主干保护性分支 + 功能分支 + PR 评审后合并。
- 需求「提交代码自动部署」→ 反推：Git 仓库接 CI/CD，push 触发流水线。

## 典型应用
- 所有现代软件协作的基石；K8s/YAML 配置也进 Git（GitOps）。
- 与 [[Azure DevOps]] Repos、[[制品仓库]] 配合形成研发闭环。
