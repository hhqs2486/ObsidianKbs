# 流水线即代码

## 一句话定义
> 把 CI/CD 流水线的定义写成受版本控制的代码文件（如 `azure-pipelines.yml`），而非在网页上鼠标点出来的配置。

## 它解决什么问题 / 为什么存在
- 图形界面点出来的流水线：难以复用、难 review、难回滚、容易「配置漂移」（线上跑的和大家以为的不一样）。把它写成代码，就能像管源码一样管流水线。

## 核心原理（大二能懂的水平）
- 管道是一份声明式文本，和源码一起进 [[Git]]。改流水线 = 提一个 PR，能被评审、有历史、可回滚。
- 对应通用 [[声明式API]] 思想：用声明描述「期望状态」（要几阶段、跑什么），由平台落实执行细节。
- 在 Azure 中的落地就是 [[Azure Pipelines]] 的 YAML 管道：文件 `azure-pipelines.yml` 描述 trigger / stage / job / step / task。

## 关键参数 / 易错点
- 关键字段：YAML 文件位置（仓库根）、`trigger` / `pr`（触发器）、`stages` / `jobs` / `steps`、`task`。
- 易错：文件名拼错或不在根目录 → 不被自动识别；把敏感信息(密钥)明文写进 YAML（应走变量 / 密钥库）；把本该进 [[制品仓库]] 的二进制塞进 Git。

## 类比（帮助理解）
- 像把「做菜步骤」写进菜谱文件交给厨房机器人，而不是每次口头指挥厨师——菜谱可复制、可改、可回顾版本。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY：做系统时，我会把所有环境构建与部署脚本都「代码化」入库，新成员 clone 下来就有完整交付能力，而不是靠老员工脑中的「上线秘籍」。

## 典型应用 / 我在哪见过
- 本书「创建第一个管道」：向导生成 `azure-pipelines.yml` 并 commit 到仓库根；之后在仓库里直接改这个文件就能改流水线。
- 多阶段管道、容器作业、YAML 架构参考都建立在「流水线即代码」之上。
