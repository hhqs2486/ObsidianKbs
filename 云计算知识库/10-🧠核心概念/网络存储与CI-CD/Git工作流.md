# Git工作流

## 一句话定义
> Git 工作流 = 团队围绕 [[Git]] 约定的一套「分支怎么开、怎么合并、怎么发布」的协作规则，让多人并行开发不打架。

## 它解决什么问题 / 为什么存在
- [[Git]] 只提供工具（branch / merge），不规定怎么用。没有工作流，人人随意推主干、冲突频发、发布不可控。
- 工作流把「开发纪律」固化下来，是协作与 [[CI-CD]] 的衔接点。

## 核心原理（大二能懂的水平）
- **主干保护**：main / master 受保护，只能经评审（PR / MR）合并。
- 常见模式（书里称「分支策略」）：
  - 主线分支开发（trunk-based）：短命分支，频繁合主干，CI 强。
  - 功能分支（feature branch）：每需求一分支，合并后删。
  - Git Flow：main + develop + feature / release / hotfix 多长线分支，适合版本化发布。
  - GitHub Flow：只有 main + 功能分支，简单，适合持续部署。
- **评审文化**：同伴评审（code review）保证质量；issue 跟踪任务。

## 关键参数 / 易错点
- 分支命名 / 生命周期约定（`feature/`、`release/`、`hotfix/`）。
- 易错：**长期分支不合并 → 合并地狱**；直接 push 主干；PR 太大不好审。
- 变基（rebase）保持线性历史；`merge --no-ff` 保留合并痕迹。
- 与 [[CI-CD]] 联动：push / PR 触发自动构建测试。

## 类比（帮助理解）
- Git 工作流像「工厂流水线规矩」：主干是总装线（不能乱改），每人从总装线拉一条支线（功能分支）做零件，质检（review + CI）合格才焊回总装线。

## 设计时怎么用（反推思维）
> - 需求「小团队快速迭代」→ 反推：GitHub Flow（main + 短功能分支 + CI）。
> - 需求「多版本并行发布（如 1.x / 2.x）」→ 反推：Git Flow（release / hotfix 分支）。

## 典型应用 / 我在哪见过
- 几乎所有软件团队；与 [[Git]] [[CI-CD]] [[持续交付]] 构成研发协作闭环。
