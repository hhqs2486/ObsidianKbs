# 持续交付

## 一句话定义
> 持续交付(CD) = 让软件随时处于「可可靠发布到生产」的状态：每次变更经自动流水线验证后，一键（或自动）部署到各环境。

## 它解决什么问题 / 为什么存在
- 发布曾是高风险大事件：上线前要熬夜手工操作、步骤靠人记、回滚靠运气。CD 把「发布」从惊吓变成日常，降低每次上线的风险与成本。

## 核心原理（大二能懂的水平）
- 在 [[CI-CD|CI]]（自动构建 + 测试）之后接上「发布流水线」：代码通过测试即进入可部署状态，流水线把产物推到 测试 / 预发 / 生产 等环境。
- 部署动作可由「审批工作流(approval gate)」把关：人到节点点确认，或半自动放行。这与「持续部署」(全自动上线，无需人工确认) 不同——CD 的最后一脚可以人工踩。

## 关键参数 / 易错点
- 关键对象：环境(env: staging / prod)、审批工作流、发布跟踪、部署自动化。
- 易错：把 CD 误当成「自动上线到生产」（那是持续部署）；没有自动化测试兜底就做 CD 很危险——流水线发的东西没人验过。
- 与 [[Azure Pipelines]] 的关系：Pipelines 的「部署」阶段 + 审批门就是 CD 的落地。

## 类比（帮助理解）
- 像餐厅出餐：菜品做好就摆在出餐口随时能端给客人，但最后「端上去」这一步由经理(审批)确认，保证端出去的一定是合格的菜。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY：做系统时，我会把「上线的每一步」都写成可重复流水线步骤，让发布不再是项目里程碑式的惊吓，而是随时能做的普通操作。

## 典型应用 / 我在哪见过
- 本书 Azure Pipelines 的「发布管道 / 发布管理 / 审批工作流」：从开发到生产跨环境发布，提升前加一层验证。
- 与 [[制品仓库]] 配合：部署环节只消费已验证的版本，杜绝「重新编译导致不一致」。
