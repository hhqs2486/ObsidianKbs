# 制品仓库

## 一句话定义
> 制品仓库（Azure Artifacts）= 团队统一的「包 / 依赖中转站」，存放 Maven / npm / NuGet / Python / 通用包，并直接喂给 [[Azure Pipelines]]。

## 它解决什么问题 / 为什么存在
- 依赖包散落各处、版本混乱、构建不可复现、公私源混杂。制品仓库让「同样的输入得到同样的产物」，是 reproducible build 的关键一环。

## 核心原理（大二能懂的水平）
- 提供一个「源(feed)」：上游接公共源（如 npmjs），下游给团队；构建时从 feed 拉依赖，把产出包 publish 回 feed。
- 它和 [[Git]] 分工：Git 管「源码文本」，制品仓库管「构建出的二进制包 / 依赖」。Pipelines 的「发布管道工件(publish artifacts)」就是往这里送。
- 每个组织免费 2 GiB 存储（本书定价章节数据）。

## 关键参数 / 易错点
- 关键对象：feed(源)、上游源(upstream)、视图(view)、权限(谁能推送 / 拉取)。
- 易错：权限没设好导致任何人可推送；把大二进制制品塞进 Git 仓库（应进制品仓库 / 对象存储）；忽视「上游源」配置导致私包覆盖公包。

## 类比（帮助理解）
- 像团队的「公共食材冷库」：大家从统一货架取标准食材，也把做好的半成品放回货架，给下一道工序用——保证每道菜用的都是同一批标准原料。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY：做系统时，我会把构建产物（如 jar / 镜像索引）发布到制品仓库，让部署环节只消费已验证的版本，杜绝「重新编译导致不一致」。

## 典型应用 / 我在哪见过
- 本书 Azure Artifacts：Maven / npm / Python / 通用包 / NuGet 包源；可接管道，也能在迁移到 Services 后直接可用（无需装扩展）。
- 与 [[持续交付]] 配合：部署阶段从 feed 取固定版本，实现可回溯发布。

## 关联
- 前置知识：[[Azure Pipelines]]、[[Azure DevOps]]
- 相关：[[CI-CD]]、[[Git]]
- 反例/误区：[[Git]] 管源码，二进制制品进制品仓库，别混用（Git 不适合放大文件）
