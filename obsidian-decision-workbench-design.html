Obsidian 决策工作台插件设计方案

将 Obsidian 从静态笔记仓库升级为动态决策工作台

插件名称: decision-workbench
版本: v1.0.0 设计稿
兼容: Obsidian 1.4+
技术栈: TypeScript + Obsidian Plugin API

1. 设计目标

当前 Obsidian 是一个出色的笔记存储工具，但笔记和工作任务之间存在一道隐形的墙：你记下的知识不会自动参与你的工作决策流程。本插件的核心目标是打通这道墙，让笔记从「被动存储」变成「主动决策的参与方」。

五大核心需求映射

需求插件能力核心模块
知识库与工作任务流打通笔记 frontmatter 中的 task 字段自动同步到任务存储Note Extractor + Task Store
从笔记提取关键信息关联任务识别 - [ ] 待办、#decision 标签、callout 块并绑定到任务面板Note Extractor + Task Linker
任务看板视图联动展示自定义 View：Kanban 看板 + 笔记来源 + 进度条Board View
基于标签/链接生成决策建议标签聚类 + 链接路径推理 + 上下文聚合Decision Engine
界面与原生风格统一全量使用 Obsidian CSS 变量，自动跟随主题切换Theme Bridge

3. 数据模型设计

3.1 笔记侧数据模型 (Frontmatter)

插件不新建笔记文件，而是复用 Obsidian 原生 frontmatter，零侵入：

---
title: "电源模块设计方案"
tags:
  - PCB设计
  - 电源
  - 嵌入式
task:
  id: "task-001"                          # 自动生成，唯一标识
  status: "in-progress"                    # todo | in-progress | done
  priority: "high"                         # low | medium | high
  due: 2026-08-10
  parent: "task-000"                       # 父任务 ID (可选)
decision-suggestions:                      # 引擎自动写入
  - "电源模块与信号采样存在共享参考点，建议先完成电源布局"
  - "3 篇嵌入式笔记关联未链接，建议补充 [[电源模块设计笔记]]"
  generated: 2026-08-01T17:30:00
---

## 正文内容
- [ ] 确定 LM2596 输入输出电压范围
- [x] 绘制原理图初稿

> [!decision] 元器件选型决策
> 选用 LM2596 而非 XL4015，理由：纹波更低，datasheet 更完善

3.3 决策图谱模型 (Decision Graph)

决策图谱是一个内存中的有向图，记录笔记 → 任务 → 决策的关联关系，用于决策引擎的路径推理：

interface DecisionGraph {
  nodes: GraphNode[];        // 笔记节点 + 任务节点 + 决策节点
  edges: GraphEdge[];       // 有向边: links-to / depends-on / suggests
}

interface GraphNode {
  id: string;
  type: "note" | "task" | "decision";
  label: string;
  tags: string[];
  metadata: Record;
}

interface GraphEdge {
  from: string;
  to: string;
  type: "links-to" | "depends-on" | "suggests" | "extracted-from";
  weight: number;           // 关联强度 0-1
}

4. 核心功能详细设计

4.1 笔记信息提取器 (Note Extractor)

这是连接笔记和任务的桥梁模块。当笔记被保存或打开时，提取器自动扫描以下内容：

提取目标识别规则输出
待办事项正则匹配 /^- \[[ x]\] (.+)$/gmSubtask 数组
决策标记Callout 块 > [!decision]Decision 记录
关键信息Frontmatter task: 字段Task 元数据
标签分类Tags 数组 + 行内 #tag标签集合
链接关系Wikilink [[...]] 解析关联笔记路径
// 核心提取逻辑
class NoteExtractor {
  extract(noteFile: TFile): ExtractedData {
    const cache = this.app.metadataCache.getFileCache(noteFile);
    const content = this.app.vault.read(noteFile);

    return {
      // 从 frontmatter 提取任务元数据
      taskMeta: cache.frontmatter?.task ?? null,
      // 从正文提取待办
      subtasks: this.extractSubtasks(content),
      // 从 callout 提取决策
      decisions: this.extractDecisions(cache),
      // 从标签提取分类
      tags: cache.tags?.map(t => t.tag) ?? [],
      // 从 wikilink 提取关联
      links: cache.links?.map(l => l.link) ?? [],
    };
  }

  private extractSubtasks(content: string): Subtask[] {
    const regex = /^- \[([ x])\] (.+)$/gm;
    const tasks: Subtask[] = [];
    let match;
    while ((match = regex.exec(content)) !== null) {
      tasks.push({
        title: match[2],
        done: match[1] === "x",
      });
    }
    return tasks;
  }
}

4.2 任务关联器 (Task Linker)

关联器的核心是双向绑定：笔记 → 任务，任务 → 笔记。当提取器从笔记中识别出任务时，关联器负责：

  1. 匹配现有任务：通过 frontmatter 中的 task.id 查找已有任务，更新其状态
  2. 创建新任务：笔记中首次出现 task: 字段时，生成任务并回写 ID 到 frontmatter
  3. 关联笔记集合：根据标签重合度和 wikilink 关系，自动建议关联笔记
  4. 同步子任务：笔记正文中的 - [ ] 待办同步为任务子项
关联强度算法：两篇笔记的关联强度 = 标签 Jaccard 相似度 × 0.5 + 链接距离倒数 × 0.3 + 共同被引用次数 × 0.2。强度 > 0.3 的笔记自动出现在任务的「关联笔记」面板中。

4.4 决策建议引擎 (Decision Engine)

引擎以定时触发 + 手动触发两种方式运行，基于三类分析产出建议：

分析 1：标签聚类分析

对全库笔记按标签做层次聚类，发现标签高度相似但未互链的笔记群，建议补充链接。例如：3 篇嵌入式笔记都标了 #电源 和 #PCB 但彼此没有 [[wikilink]]，引擎建议创建连接。

分析 2：链接路径推理

在决策图谱中查找因果链路径：如果笔记 A links-to B，B links-to C，但 A 和 C 没有直接链接，且 A 和 C 标签相似度高于阈值，引擎建议补充 A→C 的直接链接，缩短知识检索路径。

分析 3：上下文聚合

当多个进行中任务共享相同的标签或关联笔记时，引擎推断它们可能存在依赖关系，建议调整执行顺序。例如：PCB 布局任务和信号采样任务都关联了同一篇「电源模块设计」笔记，引擎检测到电源与信号的共享参考点，建议先完成电源布局。

class DecisionEngine {
  async analyze(): Promise {
    const suggestions: Suggestion[] = [];

    // 1. 标签聚类分析
    suggestions.push(...this.analyzeTagClusters());

    // 2. 链接路径推理
    suggestions.push(...this.analyzeLinkPaths());

    // 3. 上下文聚合
    suggestions.push(...this.analyzeTaskContext());

    // 4. 回流写入 frontmatter
    await this.writeBack(suggestions);

    return suggestions;
  }

  private analyzeTagClusters(): Suggestion[] {
    const clusters = this.clusterByTags(this.allNotes);
    return clusters
      .filter(c => c.unlinkedPairs.length > 0)
      .map(c => ({
        type: "link-suggestion",
        title: `${c.notes.length} 篇笔记标签相似但未互链`,
        detail: c.unlinkedPairs.map(p => `建议补充 [[${p.from}]] → [[${p.to}]]`),
        confidence: c.similarity,
      }));
  }
}

8. 关键设计决策

为什么用 frontmatter 而不是独立数据库？

frontmatter 存储让任务数据随笔记走：笔记复制、同步、Git 版本控制时任务数据不丢。独立数据库（如 SQLite）虽然查询更快，但与 Obsidian 的文件优先哲学冲突。JSON Task Store 只存索引和跨笔记关联关系，真正的任务状态在 frontmatter 中。

为什么决策建议要回流写入笔记？

一次性消费的建议看过就忘。回流写入 frontmatter 后，建议成为笔记的一部分，可以被 Obsidian 搜索、图谱、Dataview 查询，形成知识自更新闭环——笔记不只是被读，也在被写。

为什么不用 Dataview 或 Kanban 插件？

Dataview 擅长查询展示但不做决策分析；Kanban 擅长拖拽但与笔记内容割裂。本插件的差异化在于笔记内容 → 任务 → 决策建议的完整闭环，以及基于图谱的自动决策推理能力，这是现有插件都没有覆盖的。

与 Dataview/Kanban 的兼容策略

插件输出的 frontmatter 字段遵循 Dataview 可查询格式，用户可以用 Dataview 查询任务。Kanban 用户的看板数据可通过设置页一键导入。插件不与现有生态竞争，而是在其上层补齐决策层。
