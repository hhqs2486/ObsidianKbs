# 并发爬虫

## 一句话定义
> 用多进程 / 多线程 / 异步协程或分布式，让爬虫同时发起大量请求以提升采集速度。

## 它解决什么问题 / 为什么存在
- 单线程顺序请求受网络延迟瓶颈，爬全站太慢；并发/分布式把"等待响应"的时间重叠起来，成倍提速。

## 核心原理（大二能懂的水平）
- 进程/线程并行：爬虫是 I/O 密集，等待网络时不占 CPU，故多线程/协程能有效并发（GIL 对 CPU 密集无效，但爬虫不卡在这）。
- 异步：`asyncio` + `aiohttp` 用协程在单线程内并发大量请求。
- 分布式：多台机器通过 Redis 共享「爬取队列」+「指纹去重集合」协同工作；去重靠 Request 指纹(如哈希)，超大规模用 Bloom Filter 省内存（有极低误判）。

## 关键参数 / 易错点
- 并发度过高会触发封 IP，必须配合限速与代理。
- GIL 下别指望多线程加速"计算"，爬虫受益的是"等待"。
- 去重集合随任务量膨胀会爆内存 → Bloom Filter 用少量位图换"可能误判但绝不漏判"。
- Scrapy-Redis 需独立 Redis 服务；注意请求优先级与失败重试。

## 类比（帮助理解）
- 一个人一页页抄 vs 一队人分头抄不同章节，整体快很多——但人太多会把图书馆（服务器）挤爆。

## 设计时怎么用（反推思维）
> 数据量大、站点多时，我先估目标规模与反爬强度：中小规模用 Scrapy 自带并发 + 限速；超大规模多机用 Scrapy-Redis 分布式；并始终把"限速 + 代理"放在设计里，别把对方服务器打挂。

## 典型应用 / 我在哪见过
- 全网商品比价、搜索引擎抓取、舆情全量采集。
