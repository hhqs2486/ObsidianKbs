# 分布式爬虫

## 一句话定义
> 多台机器/进程协同抓取，共享"待爬队列"和"去重集合"，把单机的 I/O 并发扩展到多机横向扩展。

## 它解决什么问题 / 为什么存在
- 单机并发到了带宽/连接上限仍太慢；面对海量目标（全网商品、全量舆情）必须多机并行。
- 分布式让"加机器就能加吞吐量"，但代价是协调与运维复杂度上升。

## 核心原理（大二能懂的水平）
- 核心思路：**中央调度**。用 Redis 当公共"任务队列"+"去重集合"，所有爬取节点(Slave)从同一 Redis 取任务、回报结果。
- Scrapy-Redis：替换 Scrapy 默认的 Scheduler 与 DupeFilter，让多个 Scrapy 进程共享队列与指纹去重，单机 Scrapy 代码几乎不用改就能多机跑。
- 请求指纹在 Redis 共享，保证多机不会重复抓同一页（见 [[URL去重]]）。

## 关键参数 / 易错点
- 需要独立且稳定的 Redis 服务与机器间网络；Redis 挂了整个集群停摆。
- 机器越多对目标站压力越大，必须配合 [[爬虫限速]] 与 [[代理IP池]]，否则很快被封。
- 任务分配不均会产生"热点"节点；断点恢复与进度监控要做。
- 跨机去重一致性：Bloom Filter / 指纹集合必须共享，别各机各存。

## 类比（帮助理解）
- 像多个分店共用一个总调度台派单：谁有空谁去取任务，且总台记录了"谁家已经去过"，避免分店重复跑同一家。

## 设计时怎么用（反推思维）
> 数据量超大、单机并发到顶仍慢时，我上 Scrapy-Redis 分布式：中央 Redis 存队列与去重，水平加机器；同时把 [[爬虫限速]] [[代理IP池]] [[URL去重]] 一起设计进去。中小规模其实先用单机 [[Scrapy]] 并发就够，别一上来就分布式。

## 典型应用 / 我在哪见过
- 搜索引擎全网抓取、电商全站商品比价、舆情全量采集；与 [[并发爬虫]] [[增量爬取]] 配合做长期值守。
