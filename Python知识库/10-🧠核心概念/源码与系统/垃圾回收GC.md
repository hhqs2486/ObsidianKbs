# 垃圾回收GC（循环引用回收）

## 一句话定义
CPython 的垃圾回收专指为弥补引用计数短板而引入的「标记-清除（Mark-Sweep）+ 分代收集（Generational）」机制，用来回收**容器对象之间的循环引用**；它只盯着可能产生环的 container 对象，与引用计数互补。

## 它解决什么问题 / 为什么存在
- [[引用计数]] 无法回收循环引用（A↔B 互相引用，计数永远不为 0）。GC 就是来「破环」的：定期从根集合出发做垃圾检测，把不可达的环清掉。

## 核心原理（大二能懂的水平）
- **两种互补技术**：
  - **标记-清除**：分两阶段。① 垃圾检测——从「根对象」（栈、全局变量等确定存活的）出发，沿引用边遍历，能到达的标记为存活，到达不了的就是要回收的；书里用「三色标记模型」描述这个过程。② 垃圾回收——把不可达对象真正释放。
  - **分代收集**：以空间换时间。假设「活得越久的对象越不太可能是垃圾」，把可收集对象按存活时间分到 **3 个代（generation 0/1/2）**。新对象进第 0 代；一次回收活下来的升入下一代。多数时候只扫第 0 代，只有第 0 代满或到阈值才向上扫，延迟了对老对象的扫描。
- **只管 container 对象**：像 int、字符串这种内部不可能引用别的对象，绝不会成环，GC 根本不跟踪它们；只有 list/dict/set/实例等「内部可持有对其他对象引用」的容器才会被 `_PyObject_GC_TRACK` 挂到一条「可收集对象链表」上。
- 触发方式：`gc.collect()` 手动触发，或达到每代阈值时自动触发。

## 关键参数 / 易错点
- **`__del__` 是坑**：如果循环引用的对象定义了 `__del__`，GC 无法安全决定析构顺序，会把这些对象标记为 `uncollectable`，造成**内存泄漏**。书里示例 `gc3.py` 直接演示了「别轻易启用 `__del__`」。
- 引用计数负责「实时、即时」回收，GC 负责「延迟、批量」破环——二者职责不同。
- 可通过 `gc.set_debug(...)`、`gc.DEBUG_LEAK` 等观察回收统计（如 `collecting generation 2...`）。
- 标记-清除的额外开销与「待扫描内存总量」相关，分代正是为了压低这个总量。

## 类比（帮助理解）
引用计数是「人数归零立刻清场」；GC 是「定期全楼巡检」：从大门（根对象）能走到的房间都算有人，走不到的（包括两间互相锁门、但外面谁也进不去的）就贴封条回收。分代像「越久没出过事的楼层越少查」，省巡检人力。

## 设计时怎么用（反推思维）
> 做长生命周期服务、缓存、图结构（容易互相引用）时，我会主动用 `weakref` 打破循环、避免在会被环引用的对象上定义 `__del__`，并在需要时显式 `gc.collect()` 或调阈值，防止内存悄悄涨上去。

## 典型应用 / 我在哪见过
- 调试内存泄漏：`objgraph`、`gc` 模块、`tracemalloc`。
- 理解为什么「两个对象互相引用却没人用」最终还是会被回收（靠 GC 而非引用计数）。
- 与 [[引用计数]] 是 CPython 内存管理双支柱；底层依赖 [[对象内存布局]] 的头部与 container 的 GC 跟踪链表；和 [[GIL深入]] 一样涉及运行时全局状态。
