# 自动化运维（IT自动化与配置管理）

## 一句话定义
自动化运维指用程序（而不是手工敲命令）批量完成服务器的配置、部署、监控、变更等重复劳动；在 Python 语境下，它把「SSH 登录 → 改配置 → 跑命令 → 重启服务」这套人工流程，变成可复用、可版本化、可审计的脚本与工具链。

## 它解决什么问题 / 为什么存在
- 手工管理一台服务器还行，管理成百上千台时：效率低、容易出错、过程不可复现、无法审计。
- 重复性的系统管理工作（装环境、发版、巡检）用程序「一次编写、多次运行」，既省时间又消除人为失误。书里原话：程序「不会情绪化、不会疲劳」，只要逻辑对就严格一致地执行。

## 核心原理（大二能懂的水平）
- **本地脚本 + 远程执行**：核心套路是用 `[[subprocess模块]]`/`[[os模块]]` 在本地跑 Shell 命令，或用 `paramiko`/`Fabric` 通过 **SSH** 在远程机器上跑命令——无需在远端装客户端（agentless）。
- **配置管理 / 编排**：更高一层是把「要什么状态」写成声明式配置，由引擎（如 Ansible）比对现状、补齐差异。Ansible 用 **YAML** 写 Playbook，靠 SSH 把模块拷到远端执行完即删，无守护进程。
- **并发批量**：对 N 台机器并行操作，落到 Python 就是 `[[并发编程]]`——I/O 密集的 SSH 用多线程/`[[threading模块]]` 或 `[[异步编程asyncio]]` 即可，CPU 密集才上 `[[multiprocessing模块]]`。
- **监控与采集**：用 `psutil` 这类库读 CPU/内存/磁盘，配合 `[[logging模块]]` 落日志，形成可观测性闭环。
- 与 Python 语言特性的关系：命令行参数用 `[[argparse模块]]`、配置文件用 `[[configparser模块]]`、文本处理用 `[[正则表达式]]`、文件操作用 `[[文件IO]]`+`[[上下文管理器]]`。

## 关键参数 / 易错点
- **幂等性**（idempotence）：一条运维操作跑一次和跑一百次结果应一致（如「确保装了 nginx」而非「执行 apt install nginx」）。写脚本时最容易忽略这点。
- **密钥 vs 密码**：生产环境用 SSH 密钥认证而非密码，且把私钥权限设为 600；把密码写进脚本/历史是安全大忌。
- **并发的故障放大**：批量并行时一台报错可能被掩盖，要有集中日志与「哪些成功/哪些失败」的回执（Ansible 的 log 集中存储即为此）。
- **不要在 GIL 上抱幻想**：纯 Python 的 CPU 密集批量任务受 `[[GIL深入]]` 限制，多机并行才是正解——这也正是「分布式运维」的意义。

## 类比（帮助理解）
把机房想成有 1000 个开关的房间。手工运维=你挨个跑过去拨开关；自动化运维=写一个「按一下总闸，所有该开的灯自动开」的控制器。Ansible 这类工具=你只描述「灯应该是亮的」，控制器自己去把没开的打开；Fabric=给你一套好用的长杆，你还是得一个个去拨，但省力多了。

## 设计时怎么用（反推思维）
> 做「要给一批机器装环境 / 发版 / 巡检」的需求时，我会先用 `subprocess`+SSH 验证单台流程，再上 Fabric/Ansible 做并发编排；凡是「确保某状态」的操作用幂等写法；所有动作走 `[[logging模块]]` 留痕，敏感信息走密钥不落盘。

## 典型应用 / 我在哪见过
- 批量发版、配置同步、机器扩容初始化、定时健康检查、日志集中采集。
- 工具生态：`[[包管理pip]]` 装 `fabric`/`ansible`/`paramiko`/`psutil`；Ansible 的 role 机制便于在 galaxy 上复用。
- 与 `[[并发编程]]`、`[[subprocess模块]]`、`[[os模块]]`、`网络编程`、`[[GIL深入]]` 强相关；是《Python Linux系统管理与自动化运维》《Python Unix和Linux系统管理指南》两本书的共同主线。
