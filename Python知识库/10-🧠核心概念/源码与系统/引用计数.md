# 引用计数

## 一句话定义
引用计数是 CPython 最基础的内存管理手段：每个对象头部有一个 `ob_refcnt`，每当多一个 `PyObject*` 指向它就 `Py_INCREF` 加 1，少一个就 `Py_DECREF` 减 1；减到 0 立即调用类型对象的 `tp_dealloc` 释放对象。

## 它解决什么问题 / 为什么存在
- C/C++ 里程序员手动管内存，极易内存泄漏和悬空指针。引用计数把「释放时机」自动化：对象没人用就立刻回收，垃圾回收的代价被**分摊到整个运行时**，响应性好。

## 核心原理（大二能懂的水平）
- 每个对象诞生时引用计数初始化为 1（`_Py_NewReference(op)` 把它设为 1）。
- 核心是两个宏：`Py_INCREF(op)` 就是 `op->ob_refcnt++`；`Py_DECREF(op)` 是 `if (--ob_refcnt != 0) ; else _Py_Dealloc(op)`——减到 0 才真正销毁。
- 销毁并不直接 `free`：类型对象的 `tp_dealloc` 被调用，通常把内存还回**对象池**而非还给系统堆，避免频繁 malloc/free 拖慢执行。
- 类型对象本身不参与引用计数规则（指向类型的指针不视为引用），类型对象永不被析构。
- 还有 NULL 安全的 `Py_XINCREF`/`Py_XDECREF`。

## 关键参数 / 易错点
- `ob_refcnt` 是 32 位整型，隐含假设「对同一个对象的引用数不会超过 int 上限」（恶意代码除外，正常不成立）。
- **致命弱点：循环引用**。A、B 互相引用时各自的计数都不为 0，但已没人外部使用，引用计数永远回收不了它们——这就是需要 [[垃圾回收GC]]（标记-清除 + 分代收集）来补刀的原因。
- 引用计数不是线程安全的：多线程下对同一个对象 `Py_INCREF` 也可能竞态——所以 [[GIL深入]] 在计数操作上起保护作用。
- 容器对象（list/dict/class 实例）内部持有对其他对象的引用，因此「创建/删除容器内元素」会触发元素对象的增减引用。

## 类比（帮助理解）
给每个对象挂一个「使用人数计数器」：每来一个人用（新增引用）人数 +1，走一个人（删除引用）人数 -1；人数变 0 说明没人要了，当场清场。但如果两间房互相上了对方的锁（循环引用），谁都以为还有人，就永远清不掉——得靠额外的巡检（GC）来破局。

## 设计时怎么用（反推思维）
> 写 C 扩展或在意内存生命周期时，我会严格遵守「拿到 PyObject* 就 INCREF、不再用就 DECREF」的配对纪律；在纯 Python 层，我会避免无意制造的循环引用（比如用 `weakref` 打破），减少 GC 负担。

## 典型应用 / 我在哪见过
- `del x`、`函数返回`、`变量重新绑定` 都会触发引用变化。
- `sys.getrefcount(obj)` 可看当前引用数（注意它自己也会 +1）。
- 是 [[对象内存布局]] 头部字段的直接应用；与 [[垃圾回收GC]] 构成 CPython 内存管理双支柱。
