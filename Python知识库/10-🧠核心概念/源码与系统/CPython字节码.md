# CPython字节码

## 一句话定义
CPython 字节码是 Python 源代码经编译后产生的、由 CPython 虚拟机（一个基于栈的解释器）逐条执行的底层指令序列，存储在 `PyCodeObject` 的 `co_code` 字段里。

## 它解决什么问题 / 为什么存在
- 直接解释源码太慢、且每次运行都要重新解析语法树。Python 选择「先编译成与平台无关的中间码（字节码），再由虚拟机解释执行」，兼顾了可移植性与执行效率。
- 分两步（编译→解释）也让 import 缓存（`.pyc`）和热路径优化成为可能。

## 核心原理（大二能懂的水平）
- `python foo.py` 时，编译器先把源码编译成 `PyCodeObject`（代码对象），其中 `co_code` 是一段「字节串」，每个字节是一个操作码（opcode），很多 opcode 后面还跟着参数（操作数）。
- 虚拟机用「求值循环」（`PyEval_EvalFrameDefault`）一条条取出 opcode → 查表执行对应动作。它本质是一个**栈式虚拟机**：指令从「值栈」上取操作数、把结果压回栈，不依赖寄存器。
- 用 `dis` 模块可以看到字节码：`import dis; dis.dis(f)`。例如 `a = 1 + 2` 大致会生成 `LOAD_CONST 1`、`LOAD_CONST 2`、`BINARY_ADD`、`STORE_NAME a`。
- 字节码与源码行的对应关系存在 `co_lnotab` 里，调试/报错时能告诉你「第几行对应哪个字节码偏移」。

## 关键参数 / 易错点
- 字节码是 **Python 版本相关** 的：不同 CPython 版本的 opcode 编号可能变化，所以 `.pyc` 文件头带版本魔法数，跨大版本通常不兼容。
- 字节码只是「中间表示」，真正的对象创建、加法等仍落在 C 函数上（如 `int_add`）。
- 不要误以为「字节码执行」就很快——它仍比编译型语言慢一个数量级，瓶颈在逐条解释 + 对象开销。
- `co_consts`/`co_names` 等常量表、名字表与 `co_code` 配合，opcode 里的参数多半是这些表的「下标」。

## 类比（帮助理解）
把 Python 源码想成 C 语言源文件，字节码就是「汇编/机器码」的中间层；CPython 虚拟机就是一颗只认这套精简指令集的 CPU。`dis` 就像反汇编器。

## 设计时怎么用（反推思维）
> 做「需要吃透执行过程」的系统（如写调试器、性能剖析器、代码混淆/保护、自己造一门 DSL 编译到 Python 字节码）时，我会先 `dis` 出目标函数的字节码，确认热点指令与栈行为，再决定能否用更少的字节码/用内置函数替代。

## 典型应用 / 我在哪见过
- `dis` 模块做教学与逆向分析；`compile()` + `exec()` 动态执行。
- 性能优化时对比不同写法的字节码长度（如 `x += 1` vs `x = x + 1`）。
- 与 [[帧栈frame]] 紧密耦合：字节码正是在 frame 的栈上被求值；也与 [[导入系统]] / [[import机制深入]] 相关（import 时加载/生成 `PyCodeObject`）；[[闭包]] 的 `co_cellvars`/`co_freevars` 也挂在代码对象上。
