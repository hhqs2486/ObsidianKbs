# 解释器启动流程

## 一句话定义
解释器启动流程指从进程拉起 CPython 到「你的代码开始跑」之间发生的内部步骤：初始化运行时、建立线程环境、创建内建/系统 module（`__builtin__`、`sys`、`__main__`）、设置模块搜索路径，最后激活虚拟机执行入口代码。

## 它解决什么问题 / 为什么存在
- 在执行任何用户代码前，解释器必须先把自己「组装」好：对象系统、类型系统、内建函数、导入机制、模块搜索路径都得就位，否则 `print`、`import` 都无从谈起。

## 核心原理（大二能懂的水平）
- 启动大体分三大段（书第13章）：
  1. **线程环境初始化**：建立多线程所需的数据结构；只有用到线程时才创建 [[GIL深入]]（`PyEval_InitThreads`）。
  2. **系统 module 初始化**：
     - 创建 `__builtin__` module（内建函数 `len`、`range` 等所在地）；
     - 创建 `sys` module，并设置**模块搜索路径**（即 `sys.path` 的来源）；
     - 创建 `__main__` module（你的程序入口）；
     - 设置 site-specific 的搜索路径（`site.py` 相关）。
  3. **激活 Python 虚拟机**：分交互式与脚本文件两种运行方式，最终「启动虚拟机」进入字节码执行；同时建立好各层**名字空间**（如 `__main__` 的全局名字空间）。
- 这些 module 在 C 层都是 `PyModuleObject`，通过 `PyImport_AddModule` 等塞进 `sys.modules` 这张「已导入模块总表」，后续 import 直接查表。

## 关键参数 / 易错点
- `sys.path` 不是凭空来的——它是启动时由「可执行文件所在目录 / 环境变量 PYTHONPATH / 标准库路径 / site 配置」拼出来的；理解这点才能解释「为什么有时 import 找不到模块」。
- 解释器是**单例运行时**：`Py_Initialize` / `Py_Finalize` 管整个进程的解释器生命周期。
- 从 Python 3.8+ 起有「多解释器」（`subinterpreter`），每个有独立 GIL 与状态，但启动主流程不变。
- 子解释器/嵌入场景（如把 Python 嵌进 C 程序）调用的就是这套初始化 API。

## 类比（帮助理解）
启动像开一家工厂：先通电通水（运行时/线程环境），再把公章、原料库、总调度室建好（`__builtin__`/`sys`/`__main__`），最后挂出「上班了」的牌子（激活虚拟机），流水线才转起来。

## 设计时怎么用（反推思维）
> 做「把 Python 嵌进宿主程序」「写启动脚本/入口」或排查「import 找不到包」时，我会先想清楚：搜索路径在哪设的、`sys.modules` 里有没有缓存、是不是还没初始化完就调用了 Python API。

## 典型应用 / 我在哪见过
- `python xxx.py` 与 `python -c`/`python -i` 的区别就在「激活虚拟机」这段。
- 排查 `ModuleNotFoundError`：本质是启动流程里 `sys.path` 没包含目标目录。
- 与 [[导入系统]] / [[import机制深入]]（import 发生在启动之后、且复用 `sys.modules`）、[[GIL深入]]（线程环境初始化）、[[模块与包]] 紧密相关。
