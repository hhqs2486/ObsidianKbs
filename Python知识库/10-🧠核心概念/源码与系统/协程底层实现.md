# 协程底层实现

## 一句话定义
协程（coroutine）在 CPython 里的底层本质是「一个挂着自己的 frame 的生成器对象」：它能在 `yield`/`await` 处**挂起**执行现场（保存 `PyFrameObject` 的值栈与指令位置），之后由 `send()`/`__next__()` 从断点**恢复**，从而用单线程实现「协作式多任务」。

> 说明：陈儒的《Python源码剖析》（基于 Python 2.5）主要在第8章 frame 与「`yield` 挂起帧」的机制上铺陈协程/生成器的基础；`async`/`await` 语法（Python 3.5+，底层 `PyCoroObject`）是后来的演进。本卡在 frame 机制（书中有据）之上，补充现代 CPython 的实现要点。

## 它解决什么问题 / 为什么存在
- 线程切换靠操作系统、代价高且受 [[GIL深入]] 限制；协程在用户态「自己让出/恢复」，切换几乎零成本，适合海量 I/O 并发（网络、异步 IO）而又不被 GIL 拖死。

## 核心原理（大二能懂的水平）
- **生成器是协程的雏形**：含 `yield` 的函数调用后返回一个 generator 对象（底层 `PyGenObject`）。`PyGenObject` 持有：
  - `gi_frame`：指向执行它的 `PyFrameObject`；
  - `gi_code`：对应的 `PyCodeObject`；
  - `gi_running`：是否正在运行。
- **挂起 = 保存帧**：执行到 `yield` 时，虚拟机把当前值栈顶记到 `f->f_stacktop`（书里原话：`f_stacktop` remains NULL unless yield suspends frame），然后带着返回值从帧返回；此时 frame 不被销毁，现场完整保留。
- **恢复 = 复用帧**：再次 `__next__()` / `send(v)` 时，把 `v` 作为 `yield` 表达式的值塞回那个 frame，从 `f_lasti` 指的下一条字节码继续跑。所以协程「记住了状态」，不像函数每次从头。
- **现代 async/await**：`async def` 函数返回 `coroutine` 对象（底层 `PyCoroObject`，结构与 `PyGenObject` 几乎一致，只是语义区分），`await` 在事件循环里驱动「挂起/恢复」；事件循环（如 `asyncio`）就是那个「调度协程让出/拿回控制权」的引擎。
- `WHY_YIELD` 是虚拟机里标记 `yield`  operator 的内部常量，对应「挂起帧」这一动作。

## 关键参数 / 易错点
- 协程的「并发」是**协作式**的：只有遇到 `await`/`yield` 才让出，若某协程里跑死循环不 `await`，会卡住整个事件循环。
- 生成器/`coroutine` 对象本身也是对象，受 [[引用计数]] / [[垃圾回收GC]] 管理；被引用就不会回收，断点现场随之保留。
- `send(None)` 等价于 `__next__()`；向刚启动的协程 `send` 非 None 值会报错。
- 协程 ≠ 线程并行：单线程下仍是交替执行，只是切换点由程序员/事件循环控制，且不受 GIL 的「多核退化」影响（因为是单线程）。

## 类比（帮助理解）
普通函数像「一口气跑完的跑步机」；协程像「随时能按下暂停、下次从暂停点接着跑的游戏存档」——frame 就是那张存档（值栈+进度）。事件循环像裁判，喊「该你跑了」(resume) 就接着跑，喊「让一让」(await) 就存档下场。

## 设计时怎么用（反推思维）
> 做高并发网络服务（海量连接、I/O 密集）时，我会用 `asyncio` + `async/await` 把阻塞点改成 `await`，用单线程协程扛并发，而不是开成千上万线程。需要手写微任务/调度时，我会从 `PyGenObject`/`PyCoroObject` 的「挂起-恢复」模型理解其行为。
