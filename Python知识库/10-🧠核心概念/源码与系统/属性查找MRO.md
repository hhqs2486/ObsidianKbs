# 属性查找MRO

## 一句话定义
属性查找 MRO（Method Resolution Order，方法解析顺序）是 Python 在「访问 `obj.x` / `Class.x`」时，沿着「实例 → 类 → 基类链」搜索名字的顺序规则；它决定了多重继承下到底先找到哪个属性/方法。

## 它解决什么问题 / 为什么存在
- 单继承时查找顺序显而易见；但 Python 支持**多重继承**，一个类可能有多条基类路径，必须有一个确定、稳定、可预测的顺序来解析「`x` 到底是谁的」，否则同名属性会模棱两可。

## 核心原理（大二能懂的水平）
- 访问属性走一套固定算法（书第12章给出的伪代码）：
  1. 先找「描述符」（`descriptor`）：看 `type(obj).__mro__` 上某个类是否把 `x` 定义成了带 `__get__`/`__set__` 的 descriptor，若有且是 data-descriptor 则优先走它。
  2. 否则在**实例自己的 `__dict__`** 里找。
  3. 再沿类的 MRO 链（类的 `__dict__`）找。
  4. 若是方法（普通函数），会包成绑定方法返回；若是 descriptor 则调用其 `__get__`。
- **MRO 怎么定**：Python 3 用 C3 线性化算法生成，存在类的 `__mro__`（元组）里，也可用 `Class.mro()` 查看。C3 保证「子类总在基类前、保持声明顺序、单调性」。
- 在类型对象创建时（`type.__new__`）就会计算并固定好 MRO；`super()` 本质上就是「按 MRO 从当前类的下一个类继续找」。

## 关键参数 / 易错点
- **描述符优先级**：data descriptor（`__get__`+`__set__`）优先级高于实例 `__dict__`；非 data descriptor 优先级低于实例 `__dict__`——这是属性查找里最容易踩的坑。
- MRO 不是随便排的：多重继承若出现无法用 C3 线性化的「钻石冲突」，会直接抛 `TypeError`（创建类时即失败）。
- `obj.x` 与 `Class.x` 不同：前者会从实例查起，后者只沿类的 MRO 查，不碰实例字典。
- 属性引用**不受 LEGB 规则**约束（那是名字引用的事），它只在「对象自身的字典 + 类/基类链」里找。

## 类比（帮助理解）
把类和基类想成一叠「说明书」，MRO 就是翻说明书的固定顺序：先翻实例自己贴的便签（实例 `__dict__`），再按既定顺序翻每一本类说明书；遇到是「带特殊夹子的页」（data descriptor）就优先用夹子那本。

## 设计时怎么用（反推思维）
> 设计带多重继承的框架（如 mixin）时，我会用 `Class.__mro__` 确认解析顺序，避免「同名方法被错误基类抢先」；需要拦截属性读写时，我会用 [[描述符协议底层]] 或重写 `__getattr__`/`__getattribute__` 而非依赖运气。

## 典型应用 / 我在哪见过
- `super()` 调用、mixin 组合、`@property` 本质是 descriptor（影响查找优先级）。
- 调试「为什么这个方法调到了意料之外的基类」。
- 与 [[描述符协议底层]]（查找算法的第一步）、[[继承]]、[[元类]]、[[类与对象]] 深度耦合；底层依赖 [[对象内存布局]] 的头部与 `tp_dict`。
