# 事件循环

## 一句话定义
> 事件循环是异步编程的“发动机”:一个不断从队列里取出函数、依次运行、遇到 I/O 就让出的**调度器**。谁在等 I/O,就把 CPU 让给别的任务,从而单线程内实现并发(见 [[异步编程asyncio]]、[[并发模型]])。

## 它解决什么问题 / 为什么存在
- 内核级的上下文切换(进程/线程切换)很重:要保存状态、丢弃 CPU 缓存、重新初始化。函数间切换也有开销,但远小于真正阻塞 I/O 的等待。
- 事件循环用“协作式让出”替代“被内核抢占”,在 I/O 等待期间持续跑别的代码,把浪费的等待时间利用起来。

## 核心原理(大二能懂的水平)
- 最朴素的事件循环就是“一个待运行函数的队列 + `while True`”:从队列取出函数执行,它运行完或主动让出,再取下一个(本书用 `Queue` 写了个玩具版)。
- 搭配**异步 I/O**:发起网络写/读时立即返回(非阻塞),等 I/O 完成的“事件”触发后,事件循环把对应回调/协程安排回队列继续执行。
- 两种驱动风格:
  - **回调式**:函数完成时被调用并传入结果,链条越套越长 → “回调地狱”(tornado 早期的写法)。
  - **future/协程式**:异步函数返回 future,用 `yield`/`await` 暂停等待值;配合生成器机制实现可暂停可恢复的函数([[协程]])。
- 具体实现:
  - `asyncio` 的事件循环:`get_event_loop()` + `run_until_complete()`,显式启动、掌控整体执行流。
  - `gevent` 的事件循环:平时代码同步跑,调用 `gevent.wait()`/`iwait()` 时才启动,只在并发任务期间运转。
  - `tornado` 的 IOLoop:常驻并掌控整个程序的执行流,不只是 I/O 部分。

## 关键参数 / 易错点
- 事件循环里**别放阻塞调用**(`time.sleep`、重 CPU 计算),否则整个循环卡住,所有协程一起干等。
- 并发任务数要节制:本书实验表明同一时刻 **~100 个**待处理连接最优;开太多会在循环里频繁切换,反而变慢(过载的事件循环性能下降对所有异步框架都成立)。
- 切换有开销,但相比把 I/O 等待时间利用起来,这点开销小得多——所以**并发在 I/O 密集时收益最大**。

## 类比(帮助理解)
- 事件循环像一个“主持人 + 任务便签板”:谁说“我在等水开( I/O )”就把他记下来去叫下一个上台;水开了(事件到)再把那人叫回来继续。全场就一个主持人(单线程),但没人闲着。

## 设计时怎么用(反推思维)
> 写 I/O 密集型服务(爬虫、API 聚合)时,我会用**事件循环**([[异步编程asyncio]])做调度,并配信号量把并发连接压在 ~100;绝不往循环里塞阻塞或 CPU 重活,重活交给 [[multiprocessing模块]] 或 [[Cython]]。

## 典型应用 / 我在哪见过
- 本书 ch08 的 gevent / tornado / asyncio 三套实现都围绕各自的事件循环;请求时间线显示并发把串行 50s 压到约 0.7s。
- Node.js、Tornado Web 服务器、任何 reactor/proactor 模式框架。
