# GIL影响

## 一句话定义
> GIL(全局解释器锁)对 Python 程序的影响是:**同一时刻只有一个线程能执行 Python 字节码**,无论机器有几个核心——它直接决定了“多线程能不能加速、什么场景才该用并发”。

## 它解决什么问题 / 为什么存在
- GIL 是 CPython 为了线程安全(对象引用计数)而设的一把全局锁;存在即意味着纯 Python 计算无法靠多线程吃满多核。
- 认清 GIL 的影响,才能正确选型:什么用 [[threading模块]]([[threading模块]])、什么必须上 [[multiprocessing模块]]([[multiprocessing模块]]) 或 [[Cython]]。

## 核心原理(大二能懂的水平)
- 本书类比:即使有 100 位提问者(100 核),GIL 规定一次只有 1 位能提问并收答——多核在跑 Python 字节码时基本帮不上忙。
- **对 CPU 密集型**:多线程无效,因为任意时刻只有一个核心在跑 Python 指令;瓶颈会落在必须单核执行的那段顺序代码上(阿姆达尔定律)。
- **对 I/O 密集型**:阻塞 I/O(网络/文件)会**释放 GIL**,所以多线程在等待期间别的线程能跑——多线程对此很有用(见 [[并发模型]]、[[异步编程asyncio]])。
- **绕过 GIL 的合法路线**:
  - `multiprocessing`:独立进程,无 GIL,真用多核(适合 CPU 密集)。
  - C 扩展 / `Cython` 的 `with nogil:` + `prange`(OpenMP)、`numexpr`、`Cython` 本身——在 C 层面并行。
  - 分布式/集群计算。
- GIL 只存在于 CPython / PyPy / Stackless;Jython、IronPython 没有。

## 关键参数 / 易错点
- 纯 Python 计算**别指望多线程提速**——这是铁律;上 [[multiprocessing模块]] 或 C 扩展。
- 无限制开线程/进程会耗尽文件描述符/内存,永远用**池**(线程池/进程池)。
- 多线程共享内存 → 必须加锁防竞态;多进程不共享 → 必须 IPC([[multiprocessing模块]])。
- 即使对 I/O 有用,也别在异步事件循环([[事件循环]])里塞阻塞/CPU 重活,否则全体卡死。

## 类比(帮助理解)
- GIL 像“厨房只有一把公共菜刀”:同一时刻只能一人用。切菜(I/O 等待、等水开)时把刀让出去,别人能用;但两个人同时剁馅(纯计算)还是只能轮流来——想真并行就多开几个厨房([[multiprocessing模块]])或换电动绞肉机([[Cython]])。

## 设计时怎么用(反推思维)
> 评估“这段慢代码该不该并发”时,我会先看它是 CPU 密集还是 I/O 密集:CPU 密集且受 [[全局解释器锁代价|GIL 代价]] 限制 → 用 `multiprocessing.Pool` 或把热点丢给 [[Cython]](`nogil` 并行);I/O 密集 → `asyncio`/线程池即可。
