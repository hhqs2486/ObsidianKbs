# 分布式计算

## 一句话定义
> 分布式计算是把一个任务和数据**分散到多台计算机（集群）上协同完成**，用网络通信替代单机内存/总线，从而突破单机内存与算力的上限，处理超大数据集与超大规模模拟。

## 它解决什么问题 / 为什么存在
- 单机内存装不下、单机 CPU 算不动：每天生成的大数据、科学计算（分子/气候/量子模拟）需要成百上千台机器一起算。
- 相比多核并行（见 [[并发模型]]、[[multiprocessing模块]]），分布式解决的是**跨机器的横向扩展**——节点可以上千台，而非一个盒子里的几个核。
- 代价是网络比 CPU 慢几个数量级，且节点会故障，所以分布式系统必须自己处理**通信开销**和**容错**。

## 核心原理（大二能懂的水平）
- **两种内存视角**：共享内存（UMA/NUMA，见 [[并发编程]] 的线程模型）vs 分布式内存（每节点私有内存，靠消息传递通信）。分布式计算主要走后者。
- **MapReduce 模型**（Google 2004，Hadoop 基石）：把计算拆成两步——
  - `Map`：对每个数据分片做变换，产出 `(键, 值)`；
  - `Reduce`：把同键的数据聚合。中间的“分组搬运”叫 **shuffle**，是主要通信开销。
  - 典型例子：单词计数、蒙特卡洛估算 π。
- **Dask**（Python 原生）：用**有向无环图 DAG** 表示任务，调度器把任务分到线程/进程/多机；`dask.array`（类 NumPy，分块 chunk）、`dask.bag`（MapReduce 式）、`dask.dataframe`（分布式 Pandas）；`dask.distributed` 提供 Client + 调度器 + 工作进程，结果可缓存、可容错。
- **PySpark**（Apache Spark 的 Python API）：核心数据结构是 **RDD（弹性分布式数据集）**，切片并行；`map`/`reduceByKey`/`groupBy` 算子；`DataFrame`/`SparkSQL` 走 Scala 执行避免 Python 序列化开销。集成 HDFS/Hadoop 生态。
- **MPI / mpi4py**（学术超算主流）：多个进程跑同一脚本，靠 `comm` 通信；`Get_rank`/`Get_size`、点对点（`Send`/`Recv`）、聚合通信（`bcast`/`scatter`/`gather`/`Alltoall`/`Reduce`）；适合数千个几乎不互发数据的进程。
- **容错与数据本地性**：优先在本地处理数据、不到万不得已不传输；复制保证节点故障不中断；Dask/Spark 调度器能跟踪结果、按需重算。

## 关键参数 / 易错点
- **网络远慢于 CPU**：分布式提速的前提是“通信时间 ≪ 计算时间”。任务分片（chunk/partition）要够大，否则通信开销反噬收益。
- **序列化开销**：PySpark 在 Python↔JVM 间多一层序列化，务必用高效结构、足够大的分片；用 `DataFrame`/`SparkSQL` 比直接 `groupBy` RDD 省序列化。
- **`groupBy` 内存爆炸**：先把全部分组收进内存再聚合，可能撑爆节点；改用 `reduceByKey`/`foldby`（可并行、不囤全量）。
- **Py4J / 进程间通信**：Spark 执行器内维护 Python 进程，多一层内存与错误报告复杂度。
- **不要为小数据上分布式**：单机 `multiprocessing`/Dask 线程调度器足矣；分布式只在“数据超内存/需成百上千核”时才划算。

## 类比（帮助理解）
- 一个工厂（单机）产能到顶后，改造成**多个分布在不同城市的工厂（节点）**，各自干一块、定期通过物流（网络/shuffle）汇总结果；只要物流成本低于多工厂带来的产能，整体就更快。若每件小活都来回发货（分片太小），反而被运费拖垮。

## 设计时怎么用（反推思维）
> 做“数据量超过单机内存 / 需要成百上千核”的批处理（日志分析、大规模模拟、ML 训练数据预处理）时，我会用 **分布式计算**：先用 Dask（单机开发、集群扩展无缝）或 PySpark（已有 Hadoop 生态）把任务表达成 DAG/RDD；严格避免 `groupBy` 囤全量，改用 `reduceByKey`；把分片调到“单任务计算时间明显大于网络往返”。纯数值超算则上 mpi4py。日常小任务别碰分布式，用 [[multiprocessing模块]] 即可。
