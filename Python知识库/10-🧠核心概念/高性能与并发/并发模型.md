# 并发模型

## 一句话定义
> 并发模型是「如何让多个任务在等待/计算时互不空等」的整套套路；本书把 I/O 密集型场景下的主流选择归为三类:**串行 + 异步事件驱动(gevent/tornado/asyncio)**、**多进程/多线程(见 [[并发编程]])**、以及把它们组合起来的**集群与工作队列**。

## 它解决什么问题 / 为什么存在
- 一次 I/O(读文件、写网络 socket)动辄毫秒级,期间 CPU 本可执行约 2400 万条指令——这段时间被白白“I/O 等待”掉。
- 串行程序每个请求都等前一个完成才发下一个,浪费全部等待时间;并发模型在等 A 的 I/O 时去推进 B、C,把空洞填满。
- 关键结论:**并发收益最大的地方是 I/O 密集型**,而不是 CPU 密集型(CPU 密集要靠 [[multiprocessing模块]]/[[Cython]]/绕过 [[GIL影响|GIL]] 才能提速)。

## 核心原理(大二能懂的水平)
- 串行模型:一行一行跑,遇到 `requests.get` 就卡住等响应,请求时间线互不重叠。
- 异步事件驱动模型:有一个**事件循环**([[事件循环]])统一管理“该运行谁”。发起 I/O 时立即返回(非阻塞),等 I/O 完成的“事件”触发后再回来收结果。全程单线程、单核,却把等待时间利用起来了。
- 异步的两种编程风格:
  - **回调(callback)**:把“拿到结果后做什么”作为函数传进去,层层嵌套 → 容易陷入“回调地狱”。
  - **future/协程**([[协程]]):异步函数返回一个“将来会有值”的承诺(yield/future),用 `yield from`(Py3)或 `await` 暂停等待,代码看起来接近串行,好懂好维护。
- 具体库对比(都解决同一问题,抽象层级不同):
  - **gevent**:对标准库 socket 打“猴子补丁”变异步,greenlet 协程在单线程事件循环里切换;代码最接近同步写法。
  - **tornado**:事件循环掌控整个程序的执行流,可手动调度任意任务;以回调起家,3.x 也支持协程;擅长 I/O 占比极高的 Web 服务。
  - **asyncio**(Python 3.4+ 标准库):定义协程、显式启动事件循环;统一了 gevent/tornado 的底层事件循环,且与标准库 API 一致,是 Python 异步的未来。
- 并发之外还有**并行模型**:把任务拆给多个进程/核心(见 [[并发编程]]、[[multiprocessing模块]])或分散到集群([[multiprocessing模块]]/工作队列),这是真正吃满多核的路子。

## 关键参数 / 易错点
- 同一时刻打开的连接数要“节流”:本书实验发现约 **100 个并发连接**最优——太少仍在空等,太多则事件循环上下文切换开销反噬。用**信号量(Semaphore)**限制同时发出的请求数。
- 异步只对 I/O 等待有效;若在等待期间还要做大量 CPU 计算,单线程异步帮不上忙,得把 CPU 重活丢给 [[multiprocessing模块]] 或 [[Cython]]。
- `requests` 是同步库,异步 HTTP 用 `aiohttp`/`grequests`;别在异步里用阻塞的 `time.sleep`。
- 远端服务若本身不支持并发连接(如某些配置下的 Redis),异步和串行性能一样。

## 类比(帮助理解)
- 串行=排队打水,前面人没接满你只能干等;异步事件驱动=你接水时桶放那儿接着,转身去帮别人接,水满了事件“叮”一声喊你回来。全程就你一个人(单线程),但没闲着。
- 信号量=只发 100 个水龙头钥匙,拿不到钥匙的人先排队,避免 500 人同时拧水龙头把水管压爆。

## 设计时怎么用(反推思维)
> 做“抓取上千个带延迟的网页 / 批量写数据库”这类 I/O 密集型系统时,我会用**并发模型**把串行请求改成异步交织:Python 3 直接用 `asyncio`+`aiohttp`(或历史代码用 gevent),并加信号量把并发控制在 ~100。若系统里同时有素数计算之类的 CPU 重活,则把重活拆出去用 [[multiprocessing模块]] 跑,不让它拖慢 I/O 提速。

## 典型应用 / 我在哪见过
- 本书 ch08 用“人为加延迟的 HTTP 爬虫”做实验:串行 500 次请求约 50 秒,gevent 并发约 **0.7 秒(≈69 倍提速)**;数据库写入场景异步批处理约 **13.5 倍提速**。
- Web 服务器(Tornado)、实时数据处理、微服务间 HTTP 通信。
