# 内存优化

## 一句话定义
> 内存优化是“用更少 RAM 装下同样(或近似)的数据”:通过更紧凑的数据结构(numpy/array/trie/概率结构)和惰性加载,避免撑爆内存、让数据更快在总线上移动、更多进缓存。

## 它解决什么问题 / 为什么存在
- 扩展时内存耗尽是突发性的“拦路虎”;用更少 RAM 意味着更少机器、更易规划容量。
- “数据有质量”:数据越多移动越慢。省内存 → 数据在总线跑得更快、更多进有限的 CPU 缓存 → 整体也更快。

## 核心原理(大二能懂的水平)
- **Python 对象开销高**:`list` 存的是对象引用而非拷贝。1 亿个整数对象约占 **2.3GB**(小整数还被缓存复用);而 `array.array('l', ...)` 把 1 亿个整数放进连续 RAM 块只占 **~760MB(省 1.5GB)**;`numpy` 同理且支持更多类型(complex128 每项 16 字节)。
- **连续内存块更快**:`array`/`numpy` 在连续 RAM 里存原生类型,编译器能用偏移量直接寻址,不必每次经慢速虚拟机回调;`list` 元素可散落各处,解引用更贵。
- **字符串存储**:Python 2.7 的 Unicode 对象格外费 RAM(≈4 倍于 bytes);升到 Python 3.3+(PEP 393 灵活 Unicode)ASCII 字符几乎免费。大量文本可用 **trie 树 / DAWG**(共享前缀后缀)压缩——本书把 1.1GB 词表压到 **254MB**(HAT trie),几乎不降速。
- **概率数据结构(以精度换空间)**:`HyperLogLog++` 用 2.56KB 即可近似计数到 ~79 亿(误差 1.6%);`Bloom Filter` 用可控假阳性率判断“是否见过”;`Morris 计数器` 1 字节可近似计数到 5e76。它们只存回答特定问题所需的少量信息。
- **通用窍门**:能不进 RAM 就不进——用生成器惰性加载、内存映射;数字数据首选 numpy;Python 2 用 `xrange` 而非 `range`(Py3 的 `range` 已是生成器)。

## 关键参数 / 易错点
- `sys.getsizeof` 只报父对象开销、不算容器内容,别轻信;更准的是 `memit`(实测进程增量)或 `asizeof`(遍历估算,较慢)。
- `array`/`numpy` 的元素解引用成 Python 对象时会“复活”开销——适合当存储/对外传数据,不适合在元素上反复做 Python 层运算。
- 概率结构有**假阳性率**(布隆过滤器无误判阴性、有可控误判阳性);超容量使用会全置 True 失效——用可扩展布隆过滤器应对未知规模数据流。
- 优化前务必 [[性能剖析cProfile|剖析]] + 单测守护:不同容器有不同构建时间/查询时间权衡,要在自己数据上实测。

## 类比(帮助理解)
- 普通 `list` 存字符串像“每个词单独写一张便签贴满整面墙”;trie 树像“把共享前缀的单词合并成一棵枝干”,墙只剩一小块。概率结构则像“只记‘大概见过没有’的备忘录”,不存原词本身。

## 设计时怎么用(反推思维)
> 做“海量日志/词表/计数”系统时,我会先 [[性能剖析cProfile|剖析]] 内存占用,数字用 `numpy`/`array` 替代 `list`,大量字符串用 trie/DAWG 压缩,只需近似答案(去重计数、存在性判断)的场景用 HyperLogLog/Bloom Filter 省下几个 GB。避免一次性把所有数据 `list` 加载进内存。

## 典型应用 / 我在哪见过
- 本书 ch11:1 亿整数 list 2.3GB vs array 760MB;维基 854 万词 set 1122MB / HAT trie 254MB;UK 邮编库用 marisa-trie 仅 30MB 服务全量查询。
- 大数据流计数、风控去重、内存受限的嵌入式/边缘设备。
