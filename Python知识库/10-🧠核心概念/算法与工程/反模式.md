# 反模式

## 一句话定义
> 反模式是「看起来能解问题、实际会带来麻烦」的糟糕设计套路——和正经设计模式相对，是**反面教材**，用来识别和规避常见坑。

## 它解决什么问题 / 为什么存在
- 很多坏设计一眼看不出问题，反而「大家都这么写」。给它们起名（如上帝类、意大利面条代码、复制粘贴编程），便于在 review 时一眼识别并 refactoring。
- 书里专章讲反模式，是为了「知道反面，才能用对正面模式」。

## 核心原理（大二能懂的水平）
- 反模式 = 坏解决方案的结构 + 它造成的后果 + 该怎么改（对应到正经模式）。
- 常见反模式举例：
  - 上帝类/大泥球：一个类/模块包揽一切 → 拆职责（用 [[外观模式]]/[[MVC模式]] 分层）。
  - 复制粘贴编程：重复代码 → 抽函数/[[模板方法模式]]。
  - 万能 if 分支切换 → 用 [[策略模式]]/[[状态模式]]。
  - 硬编码依赖、全局可变状态 → 用 [[单例模式]] 需谨慎、优先依赖注入。

## 关键参数 / 易错点
- 反模式不是「绝对错误」，在极小项目里有时可接受；关键是**意识到**这是技术债、知道代价。
- 别把「暂时能跑」当成「设计没问题」，等技术债滚大再改成本极高。

## 类比（帮助理解）
- 像「用胶带把家修一遍」：短期不漏了，但根本结构没解决，下次坏得更狠——反模式就是这种胶带式修法。

## 设计时怎么用（反推思维）
> 写代码时我会主动对照反模式清单：发现某个类越来越胖、分支越来越多，就立刻停手，改成对应的正经模式（拆类/[[策略模式]]/[[状态模式]]），别等技术债爆炸。

## 典型应用 / 我在哪见过
- Code Review、架构评审、遗留系统重构前的「坏味道」诊断。
