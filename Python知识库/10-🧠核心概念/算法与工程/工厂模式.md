# 工厂模式

## 一句话定义
> 工厂模式把「创建对象」这件事从业务代码里抽出来，交给一个专门的工厂函数/工厂类决定**到底 new 哪一个子类**，调用方只管要产品、不关心怎么造。

## 它解决什么问题 / 为什么存在
- 当一类对象有多个子类（如不同格式的连接器、不同数据库的引擎），如果到处写 `if type == 'a': A() elif ...`，新增类型就要改所有调用点。
- 工厂把「变的部分」集中到一处，调用方依赖抽象产品而非具体类，符合「对扩展开放、对修改关闭」。

## 核心原理（大二能懂的水平）
- 简单工厂：一个函数，按参数返回不同子类实例（最常用）。
- 工厂方法：父类定义 `create()` 接口，子类决定造哪种产品。
- 抽象工厂：造「一族」配套产品（如一套 Windows 风格控件 vs Mac 风格控件）。
- 通用示意（简单工厂，非本书代码）：
  ```python
  def create_shape(kind):
      if kind == 'circle': return Circle()
      if kind == 'square': return Square()
      raise ValueError(kind)
  ```

## 关键参数 / 易错点
- 别为了「模式」而工厂：只有**产品种类会变化 / 构造逻辑复杂**时才值得引入，否则一个 `MyClass()` 就够。
- 工厂返回的应是抽象基类/接口，调用方不要再做 `isinstance` 具体类型的判断。

## 类比（帮助理解）
- 就像点奶茶：你只说「要杯珍珠奶茶」，店员（工厂）决定用哪款杯子、哪种珍珠，你不用进后厨自己冲。

## 设计时怎么用（反推思维）
> 做「日志系统支持文件/控制台/网络多种输出」时，我会用 **工厂模式**：定义一个 `Logger` 抽象类，工厂按配置返回 `FileLogger`/`NetLogger`，业务代码只调用 `logger.log()`，以后加 `KafkaLogger` 只改工厂、不动业务。

## 典型应用 / 我在哪见过
- `django.db` 的连接创建、`collections` 风格的多后端封装、GUI 工具包的主题控件族。
