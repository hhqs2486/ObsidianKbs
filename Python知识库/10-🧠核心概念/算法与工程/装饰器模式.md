# 装饰器模式

## 一句话定义
> 装饰器模式在不改原对象代码的前提下，把新功能「一层层包」到对象外面——运行时动态叠加能力，比用继承堆子类灵活得多。

## 它解决什么问题 / 为什么存在
- 想给一个对象加日志、缓存、加密、权限……用继承就得为每种组合写一个子类（类爆炸）。
- 装饰器把「增强」做成可嵌套的包装：想要几种能力就包几层。

## 核心原理（大二能懂的水平）
- 组件（Component）定义接口；具体组件是被装饰的对象；装饰器（Decorator）实现同一接口，并**持有**一个被装饰组件，把调用转发出去、前后加料。
- Python 的 `@decorator` 语法糖（`[[装饰器]]`）正是此模式的语言级实现，但模式本身可用于类、不仅限于函数。
- 通用示意（对象装饰器，非本书代码）：
  ```python
  class Coffee:
      def cost(self): return 10
  class Milk(Coffee):
      def __init__(self, c): self.c = c
      def cost(self): return self.c.cost() + 3
  ```

## 关键参数 / 易错点
- 装饰器必须实现被装饰对象的同一接口，调用方才无感知——别偷偷改签名。
- 包太多层会难以调试（调用栈深）；函数装饰器记得用 `functools.wraps` 保元数据（见 [[装饰器]]）。

## 类比（帮助理解）
- 像给蛋糕加配料：原味蛋糕（组件）不变，外面抹奶油、再撒巧克力（装饰器），每一层都还是「蛋糕」、能吃，叠加顺序随意。

## 设计时怎么用（反推思维）
> 做「给 API 处理器动态加鉴权、限流、日志」时，我会用 **装饰器模式**（配合 Python `[[装饰器]]`）：`AuthHandler(LogHandler(handler))`，要哪层加哪层，不写一堆继承子类。

## 典型应用 / 我在哪见过
- Python 的 `@decorator`、HTTP 中间件链、Java I/O 流（`BufferedReader` 包 `FileReader`）。
