# 适配器模式

## 一句话定义
> 适配器模式像「转换插头」：把一个接口**包装成**调用方期望的另一个接口，让原本不兼容的两个类能一起工作，而不必改动它们的源码。

## 它解决什么问题 / 为什么存在
- 你有个老模块/第三方库，接口是 `old_api()`，但你的新代码只认 `new_api()`。改两边都不现实。
- 适配器在中间做「翻译」，把调用转接到旧实现上。

## 核心原理（大二能懂的水平）
- 类适配器：继承旧类 + 实现新接口（Python 可多继承）。
- 对象适配器：持有旧对象引用，新接口方法内部调用旧对象（更常用、更灵活）。
- 通用示意（对象适配器，非本书代码）：
  ```python
  class NewApi:
      def request(self): ...
  class Adapter(NewApi):
      def __init__(self, old): self.old = old
      def request(self): return self.old.old_api()
  ```

## 关键参数 / 易错点
- 适配器只做接口转换，**别在里面加业务逻辑**，否则就变成「伪装的业务类」。
- 接口差异太大时，强行适配代码会很丑——考虑是否该换个实现。

## 类比（帮助理解）
- 像出国带的「插头转换器」：电器（旧接口）和国标插座（新接口）本不兼容，转换器在中间翻译一下就通了。

## 设计时怎么用（反推思维）
> 做「系统要同时接入旧的 XML 接口和新的 JSON 接口」时，我会用 **适配器模式**：给旧 XML 客户端包一层 `JsonClient` 适配器，上层代码统一按 JSON 接口调用，旧系统一行不动。

## 典型应用 / 我在哪见过
- `requests` 对 `urllib` 的封装思路、ORM 把不同数据库驱动统一成同一 API、各种 SDK 兼容层。
