# WebSocket

## 一句话定义
> WebSocket 是一种「在单个 TCP 连接上建立全双工、长连接」的应用层协议：握手借用了 HTTP（一次 Upgrade 请求），之后客户端和服务器就能随时互相推送消息，不再是一问一答。

## 它解决什么问题 / 为什么存在
- 普通 [[HTTP客户端]] 是「请求-响应」模型：服务器不能主动找客户端，要实时更新只能靠「客户端轮询」（浪费流量、延迟高）或「长轮询」（挂一个连接等消息）。
- 聊天、在线协作、行情推送、游戏同步这类场景需要「服务器想发就发」。WebSocket 在 [[TCP协议]] 之上建一条持久双向通道，双方平等地随时发帧，延迟低、开销小。

## 核心原理（大二能懂的水平）
- **握手阶段用 HTTP**：客户端发一个带 `Upgrade: websocket` + `Sec-WebSocket-Key` 的 HTTP 请求；服务器回 `101 Switching Protocols` 同意升级。这一下把「防火墙/代理认 HTTP」的好处也继承了。
- **之后脱离 HTTP 语义**：连接升级完成，双方按 WebSocket 帧格式通信——数据被切成带「操作码(opcode)、掩码、长度」的帧，可传文本(JSON)或二进制。
- **全双工**：服务器可主动 push，客户端也可随时发；一条连接长期复用，省去反复 TCP 握手/TLS 开销。
- **保活**：有 Ping/Pong 控制帧做心跳，检测死连接。
- **底层**：仍是单条 TCP 连接（有连接、有状态），所以它和 [[异步网络编程]]（事件循环扛海量长连接）是天作之合；常见实现 `websockets` / `socket.io`(带回退) / 框架集成(FastAPI/Channels)。

## 关键参数 / 易错点
- **它不是 HTTP 的替代品**：适合「需要服务器主动推」的实时场景；普通 REST 取数仍用 [[HTTP客户端]]。
- **需要 WS 服务端 + WS 客户端**，不能拿普通 HTTP 库（如 [[requests库]]）去连；要用 `websockets`/`aiohttp`/`socket.io` 等。
- **长连接要管理**：心跳、重连、连接数上限都得自己考虑；成千上万长连接尤其要吃 [[异步网络编程]]/[[select与poll与epoll]] 的红利。
- **鉴权/加密**：握手走的是 HTTP，可在 Upgrade 请求里带 Cookie/Token；生产用 `wss://`（WebSocket over TLS）。
- **代理/防火墙**：多数能透传 80/443 的 WS，但个别老旧中间件会砍掉 Upgrade，需要降级方案（如长轮询）。

## 类比（帮助理解）
- HTTP 像寄信：你写一封、对方回一封，对方不能主动寄给你。WebSocket 像接通的电话：拨通（HTTP 握手升级）后，俩人谁想说话随时说，不用每次重新拨号。

## 设计时怎么用（反推思维）
> 做「服务器要把新消息实时推给浏览器/客户端」的系统（聊天室、直播弹幕、行情、协作编辑、游戏状态同步）时，我会上 WebSocket 建长连接 + 心跳 + 自动重连；并在服务端用 [[异步网络编程]] 扛连接。若只是偶尔取数或单向拉取，退回普通 [[HTTP客户端]] 更简单。

## 典型应用 / 我在哪见过
- 网页聊天/客服、在线文档协作、加密货币/股票行情推送、多人小游戏、IoT 实时遥测。
