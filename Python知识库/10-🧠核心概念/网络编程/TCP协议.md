# TCP协议

## 一句话定义
> TCP（Transmission Control Protocol，传输控制协议）是构建在 IP 之上的「可靠字节流」协议：它保证数据按序、完整、不重复地到达对端，应用层只管「写流 / 读流」，底层丢包重传、排序、拥塞控制全由操作系统网络栈代劳。

## 它解决什么问题 / 为什么存在
- 真实网络会丢包、乱序、重复。[[UDP协议]] 把这些麻烦全甩给应用层；而绝大多数应用（网页、邮件、文件、SSH、聊天）只想「像读写本地管道一样」通信，不想自己处理这些。
- TCP 是互联网的「驮马」：HTTP、SMTP、FTP、SSH 等都跑在它上面。现代实现经过 30+ 年打磨，连很多消息队列也选 TCP。

## 核心原理（大二能懂的水平）
- **三次握手建连**：SYN → SYN-ACK → ACK。所以 `connect()` 在 TCP 里是一次真正的网络动作，可能失败（拒绝连接 / 主机不可达 / 收到 RST）。
- **序列号 + 确认 + 窗口**：每个字节都有序号，接收方据此排序、补缺；发送方未必「发一个等一个」，而是批量发一窗数据（「窗口」大小）；接收方用「流量控制」告知对方减速。
- **拥塞控制**：发现丢包就假设网络拥塞、自动降速——这是它相对 UDP 的文明之处，但也意味着无线丢包/路由重启后连接会「变龟速」一段时间。
- **两种 socket**：被动「监听 socket」（只 `accept` 新连接，本身不收发数据）+ 主动「已连接 socket」（绑定到某一对端）。一个连接由四元组唯一标识：`(本地IP,本地端口,对端IP,对端端口)`。所以一个 80 端口的服务器能同时服务上千客户端。
- 关闭：双方 FIN 握手；最后还有 TIME-WAIT（约 4 分钟）兜底，导致端口短时间内不可复用（见 [[socket编程]] 的 `SO_REUSEADDR`）。

## 关键参数 / 易错点
- **流没有消息边界**：`send('Hi')` 和 `send('there')` 对方可能一次 `recv` 拿到 `'Hithere'`，也可能分两次。定长消息要自己循环 `recv_all`；变长协议（如 HTTP）要先用头里的长度/分隔符判断「一条消息到哪结束」。
- **`send()` 可能只发一部分** → 用 `sendall()`；`recv(n)` 可能不足 n → 自己循环。
- **死锁**：两端都拼命 `send` 却都不 `recv`，缓冲区填满后双双阻塞。务必「一问一答、锁步」或在另一线程/用 [[select与poll与epoll]] 边读边写。
- **半关闭**：`shutdown(SHUT_WR)` 只关「写方向」、保留读，用来告诉对端「我发完了」而不必彻底 `close()`——配合「读到空串=EOF」使用。
- 大文本分块处理要注意 UTF-8 多字节字符可能被切开（`upper()` 没事，`title()` 会错）。

## 类比（帮助理解）
- TCP 像寄挂号信+自动补发：每封信编号，对方按顺序贴好；丢了的会重寄；你不用操心某封是不是掉路上了。UDP 则像随手撒传单，撒出去不管。

## 设计时怎么用（反推思维）
> 做「请求-响应、传文件、长连接会话」这类要可靠性的系统时，我默认选 TCP：开连接、用 `sendall` + `recv_all`（或基于分隔符的读取）、记得 `SO_REUSEADDR`、避免死锁。若连接数极大且多为短请求，再评估 [[UDP协议]] 或 [[异步网络编程]]（单进程扛上万连接）。

## 典型应用 / 我在哪见过
- Web（HTTP/HTTPS）、邮件收发（SMTP/POP/IMAP）、SSH、FTP、数据库驱动、几乎所有「要数据不丢」的通信。
