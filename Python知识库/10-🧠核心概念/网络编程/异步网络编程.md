# 异步网络编程

## 一句话定义
> 异步网络编程 = 在「单进程/单线程」里，用「事件循环 + 非阻塞 I/O」同时盯成百上千个 socket，谁就绪就处理谁，从而在不堆线程的前提下扛住海量并发连接。

## 它解决什么问题 / 为什么存在
- 一个连接开一个线程（多线程）在连接数到几千时就吃不消：线程栈、上下文切换、文件描述符都撑爆。
- 网络 I/O 大多时间在「等」——等对端回包。异步把「等」的时间让给别的连接：当 `recv` 会阻塞时，先去处理别的就绪 socket，数据到了再回来。
- 本质和 [[并发编程]] 是同一件事（协作式多任务），区别在这张卡聚焦「网络 socket」这一具体场景。

## 核心原理（大二能懂的水平）
- **事件驱动 / 事件循环（event loop）**：一个中心循环调用 `select()/poll()/epoll()`（见 [[select与poll与epoll]]）等待「哪些 fd 可读/可写」，返回后就挨个处理就绪的事件。书 ch07 用 `select.poll()` 写了能同时服务上百客户端的服务器。
- **非阻塞 socket**：`setblocking(False)` 后，`recv/send` 不会干等，而是「有数据就给、没数据就报错（EWOULDBLOCK）」——配合事件循环才知道何时再试。
- **half-open 的语义陷阱**：非阻塞下 `recv` 返回空串可能是「暂时没数据」而非「连接关闭」，判断 EOF 要靠别的方式（如对方 `shutdown`）。
- **历史方案**：书里用的是标准库 `asyncore`/`asynchat`（基于 select 的老框架，已过时）。现代 Python 用 `asyncio` 事件循环 + `async/await` 协程（属 [[并发编程]]），网络层配 `aiohttp`（requests 不支持 async）。
- 书特别澄清术语：「non-blocking（不阻塞进程）」与「asynchronous（异步）」常被混用；严格说 `poll()` 本身会阻塞，只是它让「单个连接」不必阻塞——别被名词绕晕。

## 关键参数 / 易错点
- **别自己造事件循环**：书明确建议——除非你要写新框架，否则直接用现成的（现代就是 asyncio/uvloop），不要手搓 `select/poll`。
- **回调地狱 vs 协程**：老式 asyncore 用回调，逻辑容易碎；`asyncio` 用 `await` 写起来像同步代码，可读性好得多。
- **阻塞调用会毁掉整个循环**：在事件循环里调用 `time.sleep`、同步重 I/O、CPU 重活，会卡住所有连接——重活要 `run_in_executor`（线程/进程池）丢出去。
- 与 [[并发编程]] 的关系：`requests` 不支持 `async/await`；异步 HTTP 要用 `aiohttp`/`httpx`。
- 多线程也能做并发网络（GIL 在 I/O 等待时会释放），但连接数极大时仍不如单线程事件循环省资源。

## 类比（帮助理解）
- 像餐厅一个服务员（单线程）同时管 20 桌：哪桌举菜单（socket 就绪）就去哪桌点单，没人点时她不干站而是去转下一桌；永远不在「等厨房出菜」时空转。多线程则是雇 20 个服务员，各管一桌——人多了成本高。

## 设计时怎么用（反推思维）
> 做「单服务要撑上万长连接（聊天、推送、代理）」或「海量并发 HTTP 抓取」时，我会选异步路线：用 `asyncio` + `aiohttp`（客户端）或 `asyncio` + `selectors`/uvloop（服务端），并警惕别在循环里塞阻塞调用。连接数不大、逻辑简单，用线程池（[[并发编程]]）反而更省心。

## 典型应用 / 我在哪见过
- 高并发 Web 服务器/网关、WebSocket 服务、爬虫并发抓取、IM、实时监控推流。
