# 物联网MQTT

## 一句话定义
> MQTT（Message Queuing Telemetry Transport）是一种为「设备弱、网络差、带宽小」场景设计的轻量级**发布/订阅**消息协议，物联网设备通过它把数据报到「 broker（代理）」，再由其他设备/云端去订阅，是「从芯片到云端」的关键传输层。

## 它解决什么问题 / 为什么存在
- 物联网里成千上万设备不可能互相记住对方 IP 直接点对点通信。MQTT 引入中间人 broker：设备只管「发到某个主题」和「订阅感兴趣的主题」，解耦了发送方和接收方。
- 协议头极小、走 TCP，适合树莓派、ESP32 这类资源受限设备在不稳定网络上可靠通信。

## 核心原理（大二能懂的水平）
- **三个角色**：发布者（设备上报）、订阅者（接收方）、broker（中转站，如 Mosquitto/EMQX）。
- **主题（Topic）**：形如 `home/livingroom/temp` 的分层字符串，用 `/` 分级，支持通配符（`+` 单层、`#` 多层）订阅。
- **发布/订阅解耦**：A 发 `home/temp`，B 只要订阅了这个主题就能收到，A 完全不知道 B 是谁——像在公告栏贴纸条，谁关心谁来取。
- **QoS 等级**：0（至多一次，最快可能丢）、1（至少一次，可能重复）、2（恰好一次，最稳最慢），按可靠性需求选。
- **遗嘱(LWT) 与 保留消息**：设备掉线时 broker 自动发「临终遗言」；保留消息让新订阅者立刻拿到最新值。

## 关键参数 / 易错点
- **主题是字符串不是队列**：设计主题层级要稳定、可扩展，别把变量塞进主题导致订阅爆炸。
- **QoS 不等于端到端可靠**：QoS 只保证到 broker 这一段，需结合业务确认。
- **安全问题**：默认端口 1883 不加密，生产环境要用 8883(TLS) + 账号认证，否则被偷窥/伪造。
- **保持连接**：客户端要按 keepalive 定时心跳，否则 broker 误判离线。
- **异步性质**：MQTT 客户端多为事件回调，配合 [[并发编程]]/[[协程]] 处理收发，避免阻塞。

## 类比（帮助理解）
- MQTT 像公司的「公告栏 + 订阅」系统：你（设备）把通知贴到某一栏（主题），所有订阅该栏的人自动收到；你不用认识他们，也不用管他们几点来看。

## 设计时怎么用（反推思维）
> 做「端云联动」物联网系统时，我会让树莓派把传感器读数 `publish` 到 `devices/<id>/telemetry`，云端服务订阅后存库/分析；反向控制则下发到 `devices/<id>/command`。配合 Python 的 `paho-mqtt` 异步客户端与 [[序列化(json与pickle)]](JSON 载荷) 使用。

## 典型应用 / 我在哪见过
- 智能家居设备上报状态、云端向设备下发指令、边缘网关汇聚多设备数据上云。
