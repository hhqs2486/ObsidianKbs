# 虚拟环境

## 一句话定义
> 虚拟环境（virtual environment）是在「应用层」把 Python 解释器和第三方包隔离出来的独立目录，让你的项目 A 用 1.x 版、项目 B 用 4.x 版，互不打架、也不污染系统 Python。

## 它解决什么问题 / 为什么存在
- 系统 Python 往往被操作系统自身依赖占用（apt/yum 装的包、系统服务）。直接用 `sudo pip install` 升级系统包，可能破坏系统服务。
- 不同项目依赖版本冲突：「X 要 1.x，Y 要 4.x」无法共存。
- 虚拟环境把「项目依赖」锁在自己目录里，可移植、可复现，还能轻松 `freeze` 出依赖清单。

## 核心原理（大二能懂的水平）
- 本质：复制/重定向一份 Python 解释器 + `site-packages`，靠改 `PATH`/环境变量让 `python`、`pip` 指向隔离目录（而非系统全局）。
- **`virtualenv`**：最老牌、跨版本（含 Py2）最常用的第三方工具。`virtualenv ENV` 建环境，`source ENV/bin/activate` 激活，`deactivate` 退出（Windows 用 `ENV\Scripts\activate.bat`）。
- **`venv`**：Python 3.3+ 标准库内置，推荐 3.4+ 用。`python -m venv ENV` 即可，结构与 virtualenv 几乎一样。书里建议「面向 3.4+ 默认选 venv，要兼容 Py2/多解释器才用 virtualenv」。
- **`buildout`**：声明式配置、可复现，但 2.0 后不再自带隔离，需配合 virtualenv 用。
- 重要实践：把依赖写进 `requirements.txt`，用 `pip install -r requirements.txt` 复现；`pip freeze` 可导出当前环境全部包（但会含仅测试用的包，别盲目照搬）。

## 关键参数 / 易错点
- ⚠️ virtualenv/venv **不可移植**：它依赖文件系统状态，换机器要重建，所以必须用 `requirements.txt` 锁定依赖。
- 激活只是改「当前 shell 会话」的环境变量；不激活就 `pip install` 会装回全局——常见坑。
- 别用 `sudo pip` 往系统 Python 塞项目包，危险。
- 系统级隔离（容器/Docker/虚拟机）是虚拟环境的补充，不是替代：小项目用 venv 足够，大型/需一致可复现的部署才上系统级隔离。

## 类比（帮助理解）
- 像给每个项目配「独立工具箱」：箱子里只放这个项目要的扳手螺丝刀，不会和别的项目/系统原装的工具混在一起。
- 像租的带家具公寓：你按需布置，退租（删环境）不影响整栋楼（系统）。

## 设计时怎么用（反推思维）
> 做「同时维护多个 Django/Flask 项目」的部署/开发时，我会用 **虚拟环境** 解决「A 项目依赖 Django 2、B 项目依赖 Django 4，且都不敢动系统 Python」的问题——每个项目一个 `venv` + 一份 `requirements.txt`，部署时按版本新建环境、锁依赖，CI/CD 里可完整复现，杜绝「在我机器上能跑」。

## 典型应用 / 我在哪见过
- 本地开发隔离、CI（tox 在不同虚拟环境跑测试）、服务器部署（每个版本一个隔离环境 + 符号链接切换）。
