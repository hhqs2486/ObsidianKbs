# 调试(pdb)

## 一句话定义
> `pdb` 是 Python 自带的「交互式命令行调试器」：能在程序运行到某行时**暂停**，让你一步步执行、查看/修改变量、观察调用栈，定位“为什么结果不对”。

## 它解决什么问题 / 为什么存在
- `print` 大法能看变量，但改完重跑、加一堆打印、看完又删，效率低；问题在深层循环或偶现时更抓瞎。
- 书里把调试当“工程基本功”：不下断点、不会单步，遇到复杂 bug 只能靠猜。`pdb` 让你**停在现场**看真实状态。

## 核心原理（大二能懂的水平）
- **设断点**：在代码里写 `import pdb; pdb.set_trace()`，运行到此行进入交互调试；或命令行 `python -m pdb script.py` 从头开始调。
- **常用命令**（交互提示符 `(Pdb)` 下）：
  - `n`（next）：执行下一行，不进函数内部。
  - `s`（step）：执行下一行，遇到函数调用**进入**函数。
  - `c`（continue）：跑到下一个断点 / 结束。
  - `l`（list）：列出当前附近代码。
  - `p 变量`：打印变量值（`pp` 美化打印）。
  - `q`（quit）：退出调试器。
  - `bt`：看调用栈。
- **查看/修改**：`p x` 看值，`x = 5` 直接在调试器里改，便于试验修复。
- **异常后看现场**：出错后用 `pdb.pm()` 可在最近异常处进入交互，查看当时的变量（事后调试）。

## 关键参数 / 易错点
- **`set_trace()` 忘了删**：提交代码前务必清掉，否则程序卡在断点等输入（CI/生产直接挂）。
- **只 `n` 不 `s`**：想看函数内部逻辑却一直 `next` 跳过了，该用 `s` 进去。
- **交互阻塞**：`pdb` 要占终端输入，跑在后台服务/管道里会卡住，远程环境改用日志或远程调试方案。
- **别在生产用**：调试器可改状态、阻塞进程，生产用结构化日志（见[[异常处理]]记录）替代。
- **`c` 之后回不到上一步**：pdb 是正向单步，想回去得重跑。

## 类比（帮助理解）
- `pdb` 像「给运行中的火车装了紧急刹车和瞭望窗」：平时飞驰（程序跑），你按刹车（`set_trace`）让它停在这节车厢，打开窗看乘客（`p 变量`）、甚至临时换个座位（`x=5`），再放它继续（`c`）。
- `n` vs `s` 像「过站不停车（next）」和「进站巡检（step）」。

## 设计时怎么用（反推思维）
> 做 XX 系统时，我会用它能解决 YY：
> 做「数据处理管道」时，我会反推“哪一步输出开始离谱”：在疑似出错的转换函数开头加 `import pdb; pdb.set_trace()`，运行后用 `n`/`s` 走到异常分支，用 `p row`/`p result` 看真实数据，定位是字段缺失还是类型错；确认后删断点、补上[[异常处理]]与单测。一句话：**先锁定‘正常与异常的分界点’→ 在那设断点单步 + 打印变量，现场看真实状态，比盲加 print 快；修完一定删断点**。

## 典型应用 / 我在哪见过
- 与[[异常处理]]：pdb 常在 except 里 `pdb.set_trace()` 看异常现场；异常日志是生产替代。
- 与[[单元测试(unittest)]]: 单测失败时用 pdb 进断言处查原因。
- 与[[函数基础]]：step 进入函数内部观察参数传递。
