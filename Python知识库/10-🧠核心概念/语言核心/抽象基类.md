# 抽象基类

## 一句话定义
> 抽象基类（Abstract Base Class, ABC）是一种「只定义接口契约、不能直接实例化」的父类——它规定子类**必须实现哪些方法**，用来在继承体系里强约束「长什么样」，而不是「怎么实现」。

## 它解决什么问题 / 为什么存在
- 没有抽象基类时，若想强制子类实现某方法，只能靠「约定」；忘了实现，运行期才报错，且报错点远离定义处。
- ABC 把「必须实现」这件事前移到类定义阶段/实例化阶段，让接口契约显式、可检查。

## 核心原理（大二能懂的水平）
- 现代 Python 用 `abc` 模块：`from abc import ABC, abstractmethod`，把方法标成 `@abstractmethod`，含抽象方法的类不可直接实例化，子类必须实现全部抽象方法才能实例化。
- 它常配合 `isinstance` 检查使用——这正是书里建议「只有配合抽象基类时才推荐用类型检查」的场景。
- **本书（第2版，2006）的局限**：彼时 Python 尚未把 `abc` 模块作为标准实践。书中在讲「不支持纯虚函数（C++）或抽象方法（Java）」时给出的替代方案是：**在基类方法里直接 `raise NotImplementedError`**，从而获得类似「强制子类实现」的效果（第13章 13.3.2）。所以本书只从思想层面触及「抽象方法」，并未介绍现代 `abc` 模块——现代 `abc` 是该思想的正式语言级实现。

## 关键参数 / 易错点
- 仅 `raise NotImplementedError` 是「运行时才发现问题」，且忘了重写也不一定会立刻触发（只有调到该方法时才报错）；`abc` 模块能在**实例化时**就拦截，更安全。
- 抽象基类 ≠ 普通父类：含未实现抽象方法的 ABC 不能 `new`，必须先被子类补齐。
- 不要为了「复用代码」而滥用 ABC——ABC 旨在定义接口，而非堆实现；实现复用更适合用 [[继承]] 或 [[元类]] 注册。

## 类比（帮助理解）
- 像「设备接口标准」：USB 标准只规定「必须有这几根针脚（抽象方法）」，具体主板怎么布线（实现）各家不同；不合规的插头插不进（实例化被拒）。
- 像「招聘 JD」：只写「必须会 Python 和 SQL（抽象方法）」，简历没这两项直接筛掉（实例化失败）。

## 设计时怎么用（反推思维）
> 做「多种存储后端（本地/云/S3）统一接口」系统时，我会用 **抽象基类** 解决「团队每人写一个 Storage 子类，但有人漏写 `upload()` 导致线上才崩」的问题——定义 `class Storage(ABC)` 并 `@abstractmethod def upload()/download()`，谁没实现就在实例化阶段直接报错，把问题挡在开发期。

## 典型应用 / 我在哪见过
- 现代：`collections.abc`（Iterable/Sequence/Mapping 等）、自定义插件接口、框架的 Handler 基类。
