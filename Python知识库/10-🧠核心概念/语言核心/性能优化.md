# 性能优化

## 一句话定义
> 性能优化是「在代码正确、可读的前提下，定位并消除瓶颈（CPU/内存/网络）以提升速度或降资源」的一套原则与工具链，核心是「先测量、再优化、别过早」。

## 它解决什么问题 / 为什么存在
- 「过早优化是万恶之源」（Knuth）。没测就猜着改，往往改了不相关的地方，还把代码搞乱。
- 优化有成本：可能牺牲可读性、引入 bug。所以要按原则来——先工作、再谈快。

## 核心原理（大二能懂的水平）
- **三条铁律**：① 首先要能工作；② 从用户角度考虑（用户真的觉得慢吗？）；③ 保持代码可读可维护（优化到 90% 就停，剩下 10% 若让代码面目全非就换方案）。
- **优化策略**：先排除「外部罪魁」（数据库/网络慢）、再考虑扩展硬件、最后写带速度目标的测试（TDD 式）。
- **找瓶颈（分析）**：
  - CPU：`cProfile`/`profile`（确定性分析器）宏观分析；`timeit` 微观测小片段；`flake8+mccabe` 测循环复杂度。
  - 内存：`objgraph` 画引用图找泄漏；注意「引用未释放」比 C 式内存泄漏更常见；`gc` 模块处理循环引用。
  - 网络：`wireshark`/`ntop` 看流量与带宽。
- **降复杂度**：用**大 O 记法**判断算法随输入增长的趋势（O(1)<O(n)<O(n²)<O(n!)）；选对数据结构——列表查找 O(n)、集合/字典 O(1)；`bisect` 二分、`collections.deque`（两端插入 O(1)）、`defaultdict`、`namedtuple`。
- **架构权衡**：用启发式/近似算法换速度、任务队列（Celery/RQ）延迟处理、概率型结构（HyperLogLog/Bloom 过滤器）换精度。
- **缓存**：确定性函数用 `functools.lru_cache`（记忆化 memoize，如斐波那契从 O(2ⁿ) 降到 O(n)）；非确定性结果加过期；分布式的用 Redis/Memcached 共享。

## 关键参数 / 易错点
- 别信「直觉哪慢」——一定要 profile，瓶颈常在想不到的地方。
- `timeit` 结果受机器影响，小片段要多次取平均；别被它的微优化假象带偏（书里举了字符串拼接被误测的例子）。
- 缓存只适合「确定性 or 短时有效」的结果；非确定性缓存要设过期，否则返回旧值。
- 复杂度是「最坏情况」指标；实际常看平均/均摊复杂度（如 list.append 均摊 O(1)）。
- 优化别牺牲可读性到不可维护——「先使其工作，再使其正确，最后使其快」（Kent Beck）。

## 类比（帮助理解）
- 像给车减重提速：先确保车能开（正确）、确认司机真觉得肉（用户角度）、再拆不必要装备；别为了轻 1% 把方向盘焊死（可读性）。
- 像医生看病：先化验（profile）找到病灶，再下药，不能凭感觉乱开刀。

## 设计时怎么用（反推思维）
> 做「响应慢的后台接口」系统时，我会用 **性能优化** 的方法论解决「盲目重构反而更慢」的问题——先 `cProfile` 跑出火焰图定位真正热点（常是某条慢 SQL 或重复计算），针对性加 `lru_cache` 或换 `set` 替代列表 `in` 查询，用 `timeit` 验证收益，绝不提前把清爽代码改成看不懂的「优化版」。

## 典型应用 / 我在哪见过
- `cProfile` 定位慢函数、`functools.lru_cache` 加速递归/重复计算、`collections.deque` 做高效队列、Celery 异步化、Redis 做共享缓存。
