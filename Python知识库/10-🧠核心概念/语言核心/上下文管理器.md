# 上下文管理器

## 一句话定义
> 上下文管理器是实现了「`__enter__` / `__exit__`」协议的对象，配合 `with` 语句，保证「进入代码块前准备资源、无论是否异常离开时都清理资源」。

## 它解决什么问题 / 为什么存在
- 很多操作需要「成对」的 setup/teardown：打开文件要关、加锁要释放、改环境变量要还原。`try...finally` 能写，但每个地方都写一遍又臭又长。
- `with` 把这套模板收敛成：`with X as x: 干活`，让「清理逻辑」跟着资源走，永远不会忘。

## 核心原理（大二能懂的水平）
- 协议两个方法：`__enter__(self)` 返回的值绑定到 `as` 变量；`__exit__(self, exc_type, exc_val, tb)` 在代码块结束时调用。
- `__exit__` 三个参数：代码块没出错时全是 `None`；出错时填入异常信息。返回 `True` 可「吞掉」异常（一般别这么干），正常应只做清理、不返回值。
- 多管理器可并列：`with A() as a, B() as b:` 等价于嵌套。
- 函数写法更省事：`from contextlib import contextmanager`，用 `@contextmanager` + 一个 `yield` 把 `__enter__`（yield 前）和 `__exit__`（yield 后）写在一个生成器里（见 [[高级迭代器]] 的生成器）。
- `contextlib` 还提供：`closing()`（退出时调 `.close()`）、`suppress(*异常)`（压制指定异常）、`redirect_stdout/stderr`。
- 兼容 `with` 的还有 `threading` 的 `Lock/RLock/Condition/Semaphore/BoundedSemaphore`。

## 关键参数 / 易错点
- `__exit__` 返回 `True` 会抑制异常——除非你真的想吞掉，否则别返回真值，否则 bug 被藏起来。
- 用 `@contextmanager` 写的函数，若 `yield` 后可能抛异常，要在 `except` 里处理后再 `raise`，否则资源清理不干净。
- `with` 不是「自动事务」，它只保证 `__exit__` 被调用，异常仍会向上抛（除非你显式吞掉）。

## 类比（帮助理解）
- 像借书：`with 图书馆借书 as 书:` ——进门登记（enter）、你看书（块内）、还书出门（exit），哪怕看到一半停电（异常）也得还书。
- 像手术室：`with 无菌环境:` ——进门前消毒、出来后脱衣，中途出意外也得走完撤离流程。

## 设计时怎么用（反推思维）
> 做「数据库/文件批处理」系统时，我会用 **上下文管理器** 解决「忘记 close 导致连接泄漏、异常时锁没释放」的问题——写 `with db.transaction() as tx:` 和 `with open(path) as f:`，块结束自动提交/回滚、自动关文件，业务代码里完全不出现 finally。
