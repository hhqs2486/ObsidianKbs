# Qt事件循环

## 一句话定义
Qt 事件循环（Event Loop）是每一个 PyQt/PySide 桌面程序背后那段「常驻死循环」：它不停从事件队列里取出事件（点击、按键、定时器、重绘请求…）并分发给对应控件处理，程序靠它活着、也靠它退出。

## 它解决什么问题 / 为什么存在
- 命令行程序是「启动→算完→退出」的直线流程；GUI 程序相反——启动后**一直挂着等用户操作**，不知用户何时点按钮、何时关窗口。
- 事件循环把「等待用户输入 / 系统通知」统一成「队列 + 分发」模型，让一个线程就能同时响应鼠标、键盘、定时器、网络、重绘，而不用为每个来源开一个堵塞的等待。

## 核心原理（大二能懂的水平）
- 每个 PyQt GUI 程序**必须**先建一个 `QApplication` 对象（`app = QApplication(sys.argv)`），它持有全局信息和**事件队列**。
- 调用 `app.exec_()`（PyQt 用 `exec_` 避免和 Python 内置 `exec` 冲突）才**真正启动**事件循环。伪代码就是：
  ```python
  while True:
      event = getNextEvent()
      if event == Terminate: break
      processEvent(event)
  ```
- 控件调用 `show()` **不会立刻画出来**，只是往队列里塞一个「重绘事件」；循环轮到它才真正上屏。
- 用户点按钮 → Qt 生成事件入队 → 循环取出 → 分发给控件 → 控件可能发信号（见 [[信号与槽]]）→ 槽被调用。
- 定时器到点在队列里生成 timeout 事件；窗口被别的程序挡住又露出来也会生成重绘事件。
- 调用 `app.quit()`（或关主窗口）往队列塞终止事件，循环退出、程序干净结束。

## 关键参数 / 易错点
- **忘记 `app.exec_()`**：窗口一闪而过或直接退出，因为循环根本没启动。
- **在槽 / 事件处理里跑重活**：循环被你占着，后续事件排不上队，界面「假死」卡住。耗时任务要丢到子线程（见 [[并发编程]]），子线程通过信号把结果抛回主线程更新界面。
- `QApplication` **全局唯一**，且必须在创建任何控件之前建。
- 事件循环是「单线程顺序处理」：一个事件没处理完，下一个就等着——所以处理要快。
- 底层事件（按键坐标等）和高级信号槽是两套机制：信号槽是高层（本书第 4 章），直接重写事件处理函数（如 `mousePressEvent`、`paintEvent`）是低层（本书第 10 章）。

## 类比（帮助理解）
事件循环像餐厅前台：客人（事件）在排队，前台（循环）挨个叫号，把「点单」交给对应服务员（控件/槽）处理。前台一天不上班（没调 exec_），整个餐厅就不动；某个服务员拖着不走（处理函数卡住），后面的客人都得干等——所以服务员动作要快，大活交给后厨（子线程）。

## 设计时怎么用（反推思维）
> 写 GUI 程序时我会记住：主线程只做「收事件 + 更新界面」这一件快事；任何超过几十毫秒的计算、文件 IO、网络请求都放进子线程，算完用信号回传主线程刷新控件，绝不让事件循环堵塞。
