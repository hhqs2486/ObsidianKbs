# REST API设计

## 一句话定义
> REST 是一种用 HTTP 动词（GET/POST/PUT/DELETE）操作"资源"的 API 设计风格；**RESTful API** 即用名词 URL 表示资源、用方法表示动作、用 JSON 交换数据。

## 它解决什么问题 / 为什么存在
- 前后端分离、多端（Web/iOS/Android/小程序）共用一套后端时，需要一个统一、无状态、可缓存的接口约定。REST 用大家都会的 HTTP 语义把接口标准化。

## 核心原理（大二能懂的水平）
- **资源用名词 URL**：`/users`、`/users/1`（别写 `/getUser` 这种动词式）。
- **方法表动作**：GET 查、POST 建、PUT/PATCH 改、DELETE 删。
- **状态码表结果**：200 成功、201 已创建、404 找不到、401 未登录、500 服务器错。
- **无状态**：每次请求自带凭证（token/Cookie），服务端不依赖上一次请求记忆（见 [[会话Session与Cookie]]）。
- 载体通常是 JSON，由视图（如 [[Flask]] 的 `jsonify`、[[Django框架]] 的 `JsonResponse`）返回。

## 关键参数 / 易错点
- 把动词塞进 URL（如 `/deleteUser`）违反 REST，应 `DELETE /users/1`。
- 状态码乱用（成功也返回 200 但 body 里写 error）让前端无法依赖 HTTP 语义。
- 忽略**无状态**：在服务器存"当前用户第几步"会让多端/扩展出问题。
- 别忘了分页、过滤、版本管理（`/api/v1/...`）。

## 类比（帮助理解）
- 像图书馆借阅：书（资源）摆在书架上用编号找，借/还/查（GET/POST/DELETE）是动作，而不是"叫管理员来借书"这种过程式口令。

## 设计时怎么用（反推思维）
> 做前后端分离或要被多端调用的后端时，我会按"资源名词 + HTTP 方法 + 标准状态码"设计接口，并用 [[路由(Web)]] 把 URL 映射到对应视图。

## 典型应用 / 我在哪见过
- 移动 App 后端、单页应用（SPA）接口、开放平台 API、微服务间通信。
