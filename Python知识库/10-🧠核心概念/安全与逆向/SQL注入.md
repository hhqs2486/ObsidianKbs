# SQL注入

## 一句话定义
> SQL 注入（SQL Injection）是**把恶意的 SQL 片段混进正常查询，让数据库执行了本不该执行的命令**，属于最经典的 Web 漏洞之一。

## 它解决什么问题 / 为什么存在
- 它“解决”的是攻击者的需求：绕过登录、拖库（盗走全表数据）、甚至执行系统命令。对防御方，理解它才能根除。
- 根因：把用户输入**当代码拼进 SQL 字符串**，而不是当“数据”。

## 核心原理（大二能懂的水平）
- 正常：`SELECT * FROM user WHERE name='小明'`。如果输入名是 `小明' OR '1'='1`，拼出来变成 `... WHERE name='小明' OR '1'='1'`，条件永远真，直接登录成功。
- 还有联合查询拖库、报错注入、盲注（看页面差异猜数据）。Python 后端用字符串拼接 SQL 就中招。
- 防御：用**参数化查询（占位符）**，让用户输入永远是数据不是代码；配合输入校验、最小权限账号。

## 关键参数 / 易错点
- 易错点：用字符串格式化（`f"SELECT ... {user}"`）拼 SQL —— 大忌。
- 易错点：以为“过滤掉单引号”就安全，攻击者可用编码/宽字节绕过；正解是参数化，不是黑名单。
- 易错点：只防登录框，别的接口（搜索、排序参数）同样能注入。

## 类比（帮助理解）
- 像填表时你不填“姓名”，而填“姓名，并且顺便把整本花名册复印给我”——如果工作人员傻傻照抄，就被你带跑了。

## 设计时怎么用（反推思维）
> 写任何查库代码，我强制用参数化（如 `cursor.execute("SELECT ... WHERE id=%s", (uid,))`），绝不拼用户输入；结合 [[正则表达式]] 做格式校验、按 [[认证授权]] 给数据库账号最小权限，从源头堵死注入（见 [[网络安全]]）。
