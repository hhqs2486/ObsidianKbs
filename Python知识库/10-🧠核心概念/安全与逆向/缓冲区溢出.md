# 缓冲区溢出

## 一句话定义
> 缓冲区溢出（Buffer Overflow）是**往一块固定大小的内存（缓冲区）里塞了超出它容量的数据，多余的部分覆盖到旁边内存**，常被用来劫持程序执行流。

## 它解决什么问题 / 为什么存在
- 对攻击者：溢出后能覆盖“返回地址”，让程序跳到攻击者放的恶意代码（shellcode），完成 [[漏洞利用]] 拿权限。
- 对防御方：理解它才能写安全代码、开防护（栈保护/ASLR/DEP）。多出现在 C/C++，Python 本身有边界检查少中招，但调用 C 扩展/解析二进制时要当心。

## 核心原理（大二能懂的水平）
- 函数调用时，返回地址、局部变量都摆在栈上。如果你有个 `char buf[8]`，却复制了 100 字节，超出的 92 字节会一路往后踩，把“返回地址”改成恶意地址。
- 类比：信箱只能塞 8 封信，你硬塞 100 封，多出的从信箱口溢出来，盖住了隔壁“回家路线指示牌”，邮差照着被改过的牌子走，走到了坏人家里。
- 现代系统用 ASLR（地址随机化）、DEP（不可执行栈）、栈 canary 来抬门槛。

## 关键参数 / 易错点
- 易错点：以为“高级语言就安全”——Python 字符串不会溢出，但 `ctypes` 调 C、解析网络包、写 C 扩展时仍可能触发。
- 易错点：offset（覆盖到返回地址需要的字节数）算错，exploit 就崩；这正是 [[逆向工程]] 要找的。
- 易错点：开防护后旧 exploit 失效，需信息泄露绕过 ASLR。

## 类比（帮助理解）
- 见“信箱溢满盖住指示牌”那段；核心就是“数据越界踩坏了控制信息”。

## 设计时怎么用（反推思维）
> 用 Python 解析外部二进制/调 C 库时，我严格按长度读取（用 [[标准库]] 的 `struct` 按格式解包），绝不信任来源长度；写 C 扩展则用安全函数、开编译期防护，避免成为溢出入口。
