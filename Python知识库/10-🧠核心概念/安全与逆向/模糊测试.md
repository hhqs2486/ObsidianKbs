# 模糊测试

## 一句话定义
> 模糊测试（Fuzzing）是**向程序狂甩大量畸形/随机的输入，看它会不会崩、会不会出异常行为**，从而自动发现隐藏的漏洞（尤其是内存破坏类）。

## 它解决什么问题 / 为什么存在
- 人工审计太慢，很多崩溃路径想不到。Fuzzing 用“机器暴力 + 监控”把“它会不会崩”跑出来，是发现 [[缓冲区溢出]]、解析器漏洞最高效的方法之一。
- 本书第 8、9、10 章用 Python 框架（含 Sulley、面向 Windows 驱动的 fuzzing）搭自动化 fuzzer，把崩溃自动归类。

## 核心原理（大二能懂的水平）
- 准备被测目标的“输入格式模板”，然后不断生成“合法但被故意改坏”的样例喂进去，同时用 [[调试器]] 盯着：一旦目标崩溃（异常被捕获），记录当时的输入——这个输入就是可复现的 bug 证据。
- 智能 fuzzing：不是纯随机，而是按格式结构变异（比如只改某字段长度），命中率更高。
- 类比：像质检员不停把“形状怪异的零件”塞进机器，看哪次机器卡死；卡死时的那个怪零件，就是定位缺陷的线索。

## 关键参数 / 易错点
- 易错点：没有“看门狗”（监控崩溃的机制）等于白跑——必须接调试器捕获异常并保存现场（见 [[漏洞利用]] 复现）。
- 易错点：输入太随机打不到深层逻辑，要做基于结构的变异。
- 易错点：只测“崩了没”，忽略“没崩但行为异常”（逻辑漏洞），需配合断言/校验。

## 类比（帮助理解）
- 见“质检员塞怪零件”。核心：用海量异常输入暴露隐藏崩溃。

## 设计时怎么用（反推思维）
> 写解析外部数据的代码（协议/文件格式）时，我会把 fuzzing 当成回归测试：用 Python 生成畸形样例持续喂给解析函数，配 [[调试器]] 捕获崩溃，保证“畸形输入只报错不崩溃”；这比上线后被打穿便宜得多。
