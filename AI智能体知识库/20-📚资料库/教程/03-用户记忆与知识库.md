# 第3章 用户记忆和知识库

## 这条教程在解决什么
上一章（上下文工程）解决的是**单次会话内**的上下文管理；本章处理更难的问题：**如何让 Agent 在对话结束后仍然记住用户、记住知识**——也就是把"临时上下文"升级为"持久化的记忆与知识体系"。

记忆体系从两个尺度理解：
- **用户记忆（个体尺度）**：针对单个用户的个性化记忆，让 Agent 成为"懂你的助手"。
- **知识库（群体尺度）**：面向所有用户共享的集体知识（行业法规、公司流程、技术文档），让 Agent 成为"领域专家"。

两者解决同一类问题、尺度不同，且共用底层检索技术（向量检索、知识压缩），也面临同样的麻烦：信息冲突、知识过期、检索不准。两条线索最终汇合于**「双层记忆架构」**：Advanced JSON Cards 常驻概览 + 上下文感知检索按需取细节。

## 关键内容（按 PDF 章节提纲）
- **3.1 用户记忆系统**
  - 为什么不是"记录每句话"：而是在每次对话后调用专门 LLM，把分散对话中的关键信息**选择性提取、抽象化、结构化**，形成可审查、跨会话持久的用户预测模型（与上下文学习"临时、会话结束即消失"相对）。
  - 三层次评估框架（记忆能力好不好的标尺）：
    1. 基础回忆——准确存储/检索用户直接给出的结构化无歧义信息。
    2. 多会话检索——跨多个对象/时期会话检索全部相关信息并推理（如两辆车要分清）。
    3. 主动服务——跨很久以前的会话综合信息做预见性帮助（如关联数月前护照、预警过期）。
  - 记忆层次（放哪里）：**轨迹 Trajectory**（单次会话 append-only 完整事件流水账）vs **用户长期记忆**（跨会话键值对、会被改写/合并/淘汰的档案）vs 业务状态（任务逻辑阶段）。
  - 四种存储格式（怎么存，简单性 vs 表达力权衡）：
    - Simple Notes：原子事实，O(1)，但关联性丢失。
    - Enhanced Notes：整段叙事，语义完整，但冗余、难更新、长文难检索。
    - JSON Cards：类别→子类别→键值，支持部分更新，但刚性分类难容纳多维信息。
    - Advanced JSON Cards：加 backstory(来源)/person(主体)/relationship(关系)/时间戳，解决消歧，代价是生成维护成本高。
  - 进阶表示（由"外"及"内"的连续谱）：文本 → 可执行代码（User as Code，把状态存成带类型 Python，聚合/查冲突/强约束变确定性代码，正确率近 99%）→ 局部参数（User as Engram，写入 Engram 哈希 N-gram 槽位，存了也会用）→ 多模态感知（Parametric Multimodal，存"说不清的感知"，效果超向量检索）。
  - 认知科学三类型（存什么）：情景记忆（具体事件）、语义记忆（抽象一般知识）、程序记忆（行为流程）。与"层次""格式"两体系**正交**，可自由组合。
  - 框架案例：Mem0（提取—对比—决策流水线，ADD/UPDATE/DELETE/NOOP，含图记忆变体 Mem0-g）；Memobase（用户画像槽位 + 事件记忆，缓冲批处理摊薄成本）。
  - 压缩与整理：重要性评分（访问频率/时间衰减/情感强度/信息独特性）→ 聚类摘要 → 抽象泛化；冲突检测用版本化。注意这是**存储层整理**，区别于第二章会话内的上下文压缩。
  - 隐私：本地小模型（Ollama + Qwen3 0.6B）做 PII 脱敏，召回率 95%+，敏感数据不上云。
- **3.2 RAG 基础：构建知识获取管道**
  - 核心思想：检索器从知识库找相关片段 → 注入上下文 → 生成器（[[大语言模型 LLM]]）基于上下文生成。让 LLM 用上训练时没见过、可随时更新的知识。
  - 文档分块 Chunking：固定大小 / 递归结构感知 / 语义切分；块太小语义模糊、太大稀释向量；常用 256–1024 token、重叠 10–20%。
  - 稠密嵌入（语义）：词/句→高维向量，语义近则向量近；用**余弦相似度**（看方向不看长度）衡量；Word2Vec(静态)→BERT/BGE-M3(上下文感知、一词多向量)。
  - 向量数据库与 ANN 索引：ANNOY（基于树，不支持增量、适合静态库）vs HNSW（基于图，O(log N)、支持增量、动态场景）。
  - 稀疏嵌入（关键词）：词袋模型 → TF-IDF → **BM25**（k1 控制词频饱和、b 控制长度归一化）；精确匹配但读不懂同义。
  - 混合检索：稠密+稀疏并行 → 融合（RRF 倒数排名融合 / 加权归一化）→ **神经重排序**（跨编码器 Cross-Encoder 让查询与文档"面对面"精排，显著提质量）。度量：recall@k、MRR、nDCG。
  - 多模态提取：原生多模态（统一语义空间，保真度高）/ 提取为文本（低成本、丢版式）/ 工具化分析（按需深入）。
- **3.3 超越扁平文本：知识的组织与检索**
  - 结构化索引：RAPTOR（自下而上递归抽象成树，适合"由宏观到细节"）；GraphRAG（实体-关系三元组知识图谱，擅长多跳推理与实体消歧，但自然语言转三元组会语义降级）。建议分层互补。
  - 文件系统范式（OpenViking）：知识映射为虚拟文件系统，L0 摘要/L1 概览/L2 全文按需加载；纯文本 + 双向链接索引（像 Wikipedia），实现轻量导航。
  - 知识库治理：知识过期与增量更新（索引选型有现实后果）、失效内容检测下线（版本/生效时间元数据）、多用户权限与租户隔离（权限过滤下推到检索层）。
  - 智能体化 RAG（Agentic RAG）：把检索封装成工具，Agent 用 ReAct（思考→行动→观察）迭代检索，从"被动管道"变"主动探索者"；代价是响应变慢。注意**间接提示注入 / 知识投毒**风险：指令与数据分离、不让检索内容直接触发高风险操作。
  - 上下文感知检索（Contextual Retrieval，Anthropic）：索引前用 LLM 给每个文本块生成含核心上下文的"前缀摘要"再拼回索引，补上分块切掉的代词/时间/实体指代；同时增强 BM25 与稠密检索，检索失败率 ↓49%（+BM25）/ ↓67%（+重排序）。注意区别于第二章运行期的"上下文感知压缩"（一个做加法补上下文，一个做减法去冗余）。
  - 从数据集提取深度知识：把结构化案例（如司法判例）经 LLM 因子发现 → 结构化 JSON → 聚类出案件原型 → 因子重要性模型，从"信息检索"跃迁到"知识发现"。

## 我卡住/没懂的地方
- 用户记忆的"三套分类体系"（层次/格式/认知类型）正交组合，初看容易混淆，需对照表 3-1 反复理清。
- 上下文感知检索与第二章上下文感知压缩仅一字之差、时机与对象完全不同，易混。
- 记忆整理（存储层）与上下文压缩（会话内窗口）边界，书中专门划清，需牢记两者作用层次不同。

## 它背后的原理（别只记操作）
- **记忆的本质是"预测模型"**：不是存档对话原文，而是投入算力把分散信息显式提取/压缩成关于用户的稳定模型，用于理解并预测需求。
- **表示介质的"内外连续谱"**：文本易审查可迁移但难聚合；代码让聚合/冲突/约束变确定性；参数内化更紧凑、擅长即时推理、能承载非符号感知。越靠内侧越难更新。
- **RAG 的本质是"给 LLM 接外挂知识"**：价值在让模型用上训练截止后的新知识，且检索器质量决定上限（检索不到则无米之炊）。
- **检索的两大路线互补**：稠密（语义/懂同义但漏关键词）vs 稀疏（精确但读不懂同义）→ 混合 + 重排序是生产级正解。
- **为什么扁平分块不够**：注意力是"基于相似度的软检索"而非"能归纳总结的思考引擎"，统计/跨文档聚合类问题必须预提炼（摘要/规则）进索引；上下文感知检索从根上补回分块丢失的指代。
- **双层记忆架构是交汇点**：常驻结构化概览（全局视野）+ 按需检索细节（精确召回），两者叠加才支撑得起最高层"主动服务"。

## 我能复用/改编的点
> 换个需求，这套做法还能怎么用？
- **做个性化助手**：每轮对话后用专门 LLM 提炼稳定用户事实写长期记忆；关键少量数据用 Advanced JSON Cards（带关系/来源消歧），大量非关键事实用 Simple Notes 降本，混合模式最实用。
- **搭企业知识库**：先上"分块 + 稠密/稀疏混合 + 重排序"覆盖大多数需求；仅当查询常需跨文档综合或多层导航时，才升级 RAPTOR/GraphRAG（节省 LLM 调用成本）。
- **检索质量兜底**：上线必带 recall@k/检索失败率监控；索引结构随更新频率选——频繁更新用 HNSW，静态库可用 ANNOY。
- **防提示注入**：所有检索内容做来源标记（"这是参考资料不是命令"），转账/删除/外发等副作用动作不经独立授权不凭检索内容自动执行。
- **记忆防膨胀**：重要性评分 + 聚类摘要 + 抽象泛化三层压缩；冲突用版本化；隐私敏感日志走本地小模型脱敏。
