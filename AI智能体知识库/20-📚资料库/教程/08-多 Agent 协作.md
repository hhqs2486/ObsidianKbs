# 第10章 多 Agent 协作

## 这条教程在解决什么
单 Agent 受限于自身模型能力边界与上下文窗口；让多个 Agent 协同，既能「取长补短」，更可能让群体智能高于个体（文明即例证）。本章系统回答：什么时候真的需要多 Agent、有哪几种协作架构、Agent 之间怎么通信与协调、以及在成本与一致性上要权衡什么。

## 关键内容（按 PDF 章节提纲）
### 10.1 多 Agent 协作的分类框架（两个核心设计维度）
- **维度一：上下文是否共享**
  - 共享上下文（继承式协作）：后一 Agent 继承前一 Agent 的完整轨迹，阶段切换系统提示词+工具集，信息零损耗，但上下文快速膨胀。
  - 不共享上下文（隔离式协作）：每个 Agent 独立上下文，靠显式通信交换信息，模块化/可并行，但信息同步复杂。
  - 三者通信机制：①工具调用的结构化参数；②共享文件系统（读写中间产物）；③消息总线（异步中转，如邮件系统）。
  - 经验法则（表10-1）：累计上下文超窗口 ~50% 应不共享；信息零损耗是硬约束则共享；多数系统用「前几阶段共享、到饱和点切不共享+显式 handoff」。
- **维度二：协作拓扑**（详见 10.4）：对等 / 管理者 / 去中心化，按复杂度递增。概念上独立于「是否共享」，但共享上下文时拓扑常退化为一条角色切换序列，故本章重点展开不共享上下文的三类拓扑。

### 10.2 多 Agent 何时真正优于单 Agent
- **核心判据只有一条**：协作过程是否引入了单个 Agent 在生成时无法获得的新信息（表10-2）。
  - 同一模型自我审查、不同 Agent 辩论同一段文本 → 否 → 通常无效甚至有害。
  - Reviewer 用测试执行结果 / 渲染截图 / 外部工具验证 → 是 → 显著提升（RLEF 2025；WebGen-Agent 把 Claude 3.5 Sonnet 从 26.4% 提到 51.9%）。
- **步骤预算与性能**：单纯增加步骤数不能保证提升，Agent 需预算感知机制（BAVT 2026：随预算减少从「广撒网」切「深挖掘」）。管理者模式中 Manager 应据复杂度动态分配步骤预算。
- **成本硬约束**：Anthropic 披露多 Agent 研究系统 token 消耗约为普通对话 15 倍，token 用量本身解释约 80% 性能差异。多 Agent 的收益必须大到覆盖数倍~一个量级的额外开销。

### 10.3 共享上下文的多 Agent 协作
- **多阶段角色转换（实验10-1）**：同一会话中动态切换系统提示词+工具集（需求分析师→软件工程师→代码审查员），对话历史连续保留；阶段边界天然成为质量门控点。
- **跨领域角色转换（实验10-2）**：`transfer_to_agent(target_role, reason)` 工具，triage 分诊把复合任务拆给 research/coding/data_analysis/writing，完成后移回 triage；每个角色都看得到完整历史。需处理循环切换。

### 10.4 不共享上下文的多 Agent 协作
- **虚拟文件系统四类区域**：①Agent 专属工作区 Scratchpad（私有、随实例销毁）；②多 Agent 共享空间（用户可见、需并发控制）；③外部挂载资源（受外部授权、多为只读）；④系统内置资源（Skills/模板，全局只读）。统一目录树挂载 = 「文件路径作为通用接口」。
- **通信与控制平面三能力**：①消息传递（点对点 vs 消息总线，结构化信封：发送者ID/目标/类型/JSON负载）；②状态查询（pull `get_subagent_status` vs push 上报，状态机：已提交/执行中/需输入/已完成/失败 + 超时心跳兜底）；③执行终止（优雅 graceful+ack 优先，强制 forced 兜底；级联终止需锁/幂等防竞态）。
- **对等协作（10.4.3）**：2-3 个平等 Agent 迭代改进，核心是引入认知多样性。最经典是**提议者-审核者范式**（Proposer 生成、Reviewer 渲染+视觉评估、反复迭代）。扩展：辩论 Debate、头脑风暴 Brainstorm、专家小组 Panel Discussion。研究警示：无外部反馈的自我纠正反而降效（ICLR2024 LLMs Cannot Self-Correct；CRITIC 实验）。
- **管理者模式（10.4.4）**：Manager 像项目经理，把专门 Agent 建模为自身可调用工具（call_agent_X），调用 Agent=调用工具。子 Agent 返回结构化摘要而非全量轨迹 → Manager 上下文线性增长。两种形态：顺序协调（有先后依赖）、并行协调（消息总线+实时监控）。产品化实例：灵台 Lingtai（主器灵+分神+分身）。实验10-3 书籍翻译、实验10-4/10-5 边打电话边用电脑、实验10-6 并行搜教师。
- **去中心化模式（10.4.5）**：无中心控制者，Agent 间对等移交（handoff）。「移交包」= 任务描述+已确认事实与约束+结构化产物引用（文件路径非内容）。由伪到真：MetaGPT（固定流水线+SOP，通信解耦）→ AutoGen group chat（共享对话+中心化调度混合）→ OpenAI Swarm/Agents SDK（真正对等去中心化 handoff 网络）。
- **跨组织协作 A2A 协议（10.4.6）**：Agent Card（能力名片）+ 任务生命周期状态机 + 不透明协作（只交换任务与产物）。与 MCP 对照：MCP 解决 Agent↔工具，A2A 解决 Agent↔Agent；A2A 是跨信任边界的标准化层。

### 10.5 多 Agent 协作的失败模式
- MAST 分类法（2025）：14 种失败模式，分系统设计缺陷 / Agent 间对齐失败 / 任务验证缺失；单纯修补提升有限（ChatDev 仅 +15.6%），属根本性设计缺陷。
- **失败模式一：共享文件系统并发冲突**：文件级丢失更新（乐观锁版本号解决）；语义级一致性冲突（跨文件引用，需语义校验/避免并行改有依赖的文件 / worktree 隔离）。
- **失败模式二：错误的级联放大**：一个 Agent 的错误被后续 Agent 逐层强化（如术语「推理」误译被「一致性」背书）。交叉验证（独立视角看原始证据 vs 结论）是断链关键；确定性工具（单测/编译/DB）是最可靠断链器。
- **循环失控**（过早终止的对称反面）：token 成本失控、理解债 comprehension debt、认知投降 cognitive surrender；解药：显式预算与终止条件 + 扎根真实观测的验证器 + 人保持「循环的工程师」角色。

### 10.6 Agent 社会（前沿探索，工程读者可选）
- 涌现行为 Emergent Behavior：规模跨临界点后涌现无法预先设计的集体行为。
- 斯坦福 AI 小镇（生成式 Agent：记忆流+反思+计划与行动，25 个 Agent 自发办派对/扩散选举）、Moltbook（150 万 Agent 涌现数字宗教与协作协议）、Vending-Bench Arena（多 Agent 市场竞争博弈）、Pinchwork/RentAHuman（Agent 经济市场）、狼人杀（信息不对称下的策略博弈，中心化法官+权限控制）。

## 我卡住/没懂的地方
- 「共享上下文的拓扑退化」与「维度概念独立」的边界在混合形态（如 AutoGen group chat）下容易混淆，需结合实际架构逐例判断。
- 错误级联放大的「一致性反而背书错误」机制，与「一致性检查本应发现错误」看似矛盾——关键在 Reviewer 看到的是被污染的「统一假象」，需引入独立证据链。
- MAST 14 种具体模式未在正文逐条列出，仅概括为三类 + 两种工程常见模式。

## 它背后的原理（别只记操作）
- **新信息判据**：多 Agent 有效与否，不在「几个 Agent」而在「是否引入生成时不存在的新信息」。学术说「单 Agent 够」比的是「看同一段文本互相讨论」（辩论，受数据处理不等式约束，串行传递只丢信息不造信息）；工程有效的是含外部反馈环路（执行/视觉/工具）。
- **集体智能涌现**：分工+协作+辩论+知识累积，使整体智能超个体之和——这是多 Agent 通往 ASI 的路径之一。
- **契约式设计 / 接口解耦**：不共享上下文时，Agent 间只通过标准化交付物（移交包、消息信封、文件格式）交互，借鉴软件工程接口解耦——换更强模型只要产物格式不变，下游零修改。
- **结构化摘要防爆炸**：子 Agent 回结构化摘要、传文件路径非内容，使 Manager/Supervisor 上下文线性增长而非随子任务数爆炸。
- **验证器是 Loop 工程的瓶颈**：循环价值不在转得快，而在验证器可靠——验证不可靠，循环只是更快标记劣质产出为完成。

## 我能复用/改编的点
> 换个需求，这套做法还能怎么用？
- 任何「单 Agent 上下文装不下或需多专业能力」的长程任务 → 先用「上下文是否共享 × 拓扑」两维检查表选型（表10-1）。
- 防「过早终止/假完成」→ 用提议者-审核者 + 确定性反馈（跑测试/渲染截图），让 Reviewer 引入 Proposer 生成时得不到的新信息。
- 构建中心化调度系统 → 把最强模型+最精心提示词给 Manager/规划者（Plan-and-Act 实证：弱规划者是最关键瓶颈），子 Agent 只回结构化摘要。
- 多 Agent 并发写共享区 → 乐观锁/版本号或 worktree 隔离；跨组织互操作 → A2A（Agent Card + 任务状态机）。
- 设计终止与预算 → 并行协作必带优雅终止+级联终止（锁/幂等）+ 预算上限，避免 token 失控与循环失控。
