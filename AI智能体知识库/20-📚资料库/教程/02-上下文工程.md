# 第2章 上下文工程

## 这条教程在解决什么
解决一个核心认知偏差：**Agent 的能力上限不取决于模型有多聪明，而取决于它在每个决策点能看到什么、以什么结构看到这些信息**。模型（[[大语言模型 LLM]]）的能力是通用的，但执行具体任务需要背景信息——产品架构、业务规则、内部约定——而这些模型并不知道。上下文工程（Context Engineering）就是系统化地设计、组织、提供这些背景信息，让模型的通用思考能力在具体任务中充分发挥。它既是技术问题，更是组织问题：团队若本身是"信息黑洞"，再好的 Agent 也无计可施。

## 关键内容（按 PDF 章节提纲）
### 2.1 上下文：决定 Agent 能力上限的关键
- 上下文 = 每次对话时 LLM 实际"看到"的全部信息（对话历史 + 系统指令 + 工具描述等）。
- 模型智力只是基础，**上下文质量才是真正上限**：中等模型 + 精心组织的上下文，常胜过顶级模型在信息匮乏下的盲目摸索。
- 翁家翌："人和模型一样，最重要的是 Context"；AI 短时间内无法取代人的最大原因也是 context——因为 AI 跟人不在同一个环境里。
- 构建 AI 原生团队首先是一场文档化运动，而非部署新工具（Linux 内核式的透明、文档驱动文化天然对 AI 友好）。

### 2.2 Agent 如何调用大模型：API 的上下文结构
- 消息四种角色：`system`（开发者写的最高优先级指令）、`user`（终端用户输入）、`assistant`（模型回复含工具调用）、`tool`（工具结果，靠 `tool_call_id` 关联）。
- 每次调用**无状态**：模型不在服务端"记忆"，Agent 框架必须每轮把完整 `messages` 列表重发。
- 多轮工具调用 = ReAct 循环的 API 层实现：请求 → 工具调用 → 执行 → 送回结果 → 再请求，直到模型不再返回 `tool_calls`。
- 上下文构成（图2-4）：**静态前缀**（System Prompt + Tool Definitions，每轮不变） + **轨迹**（对话历史，随交互增长）。这个"静态前缀 + 轨迹"结构是 KV Cache、上下文压缩等技术的基础。

### 2.3 KV Cache 友好的上下文设计
- KV Cache：把已算过的 K/V 向量缓存，新 token 直接复用，避免重算整个前缀。前提：**前缀完全不变**，改一个字节整段失效。
- 三条核心结论：① System Prompt 和工具定义一旦确定就不要改；② 动态信息（时间戳、用户状态）追加到末尾而非修改前缀；③ 用标准 API 格式（role-content），不要自行拼字符串（会破坏 CoT 保留与缓存）。
- **Prompt 缓存**（Prompt Cache）：API 服务层跨请求的前缀缓存（KV Cache 是模型内部单次请求内）。OpenAI 自动前缀缓存，Anthropic 需显式 `cache_control` 断点。经济影响更大，直接影响计费。
- 缓存是**架构约束**：Claude Code 把 Prompt Cache 经济性前置为设计约束——提示词排列顺序先由缓存边界决定；子 Agent 必须与父 Agent 字节级对齐以命中缓存。

### 2.4 提示工程：优化系统提示词（System Prompt）
- System Prompt 是 Agent 的"员工手册"（身份、规则、约束、流程）。检验标准：聪明新员工读完还不知道怎么做，Agent 也一样不知道。
- 关键维度：
  - **语气风格**：大写"NEVER"比"please avoid"更能引起注意，保留给关键约束。
  - **结构化提示**：XML 标签订语义（`<working_directory>`），Markdown 管组织，双层配合。
  - **流程驱动 vs 规则堆砌**：SOP 流程优于上百条零散规则（消融实验：打乱组织结构成功率降 30%+）。
  - **业务规则细化**：产品经理定规则，工程师只编码；不给模型在业务规则上的自由裁量权（例：砍价 Agent 计费模式必须明确到可执行程度）。
- **Few-shot**（2.4.5）：当期望输出难用规则描述（文案风格、报告格式）时，给 2-3 个高质量示例胜过等量抽象规则；但示例放前缀区，确定后应保持字节级稳定，否则缓存持续失效；2-3 个覆盖边界的示例胜过 10 个雷同的。

### 2.5 动态提示词与 Agent Skills
- 痛点：把所有场景塞进一个 System Prompt → 浪费 token + 注意力被稀释（"上下文腐化"）。
- Skills = 领域能力可组合单元，渐进式披露：① 元数据（name+description，数百 token，常驻）② 核心流程（按需加载为 tool result）③ 细则（子文档）。
- 放置位置权衡：方式三（生产实现）= 元数据注入上下文**末尾**的 user-role meta 消息（`emit-once`、永久命中缓存），完整内容经专用 Skill 工具按需加载——既保缓存又保指令遵循。

### 2.6 Agent 状态栏（Agent Status Bar）
- 问题：模型"检索"强但"归纳"弱——上下文窗口是"只有一半的检索引擎"，缺提炼层。隐式状态（打了几次电话）散在轨迹里，模型每次都要现算一遍，易错且慢。
- 状态栏 = Harness 在上下文**末尾**注入的结构化元信息（任务进度 TODO、工具计数、当前时间、环境状态）。它是"提前算好的状态"，以极低成本呈现需扫描数千 token 才得到的信息。
- 理论：上下文蒸馏（Context Distillation）。弱模型准确率涨 40-54 个百分点；强模型思考 token 砍掉八九成。但必须**用代码维护、别用 LLM 维护**；且状态栏是有损投影，删原文前需确认覆盖了所有会被问到的问题。
- 位置：API 层面作为 `user` 角色消息追加到末尾（借用 user 消息槽位），紧邻生成位置获最高注意力，且追加不破坏前缀缓存。

### 2.7 上下文压缩策略
- 两个动机：① 长度/成本约束（窗口撑满会失败）② **提升思考质量**——总结后的知识比原始形式更利于"检索"。
- 核心机制："上下文学习本质是**检索而非推理**"。长上下文导致**上下文腐化（Context Rot）**——装得下但找不到（区别于溢出），因为注意力被稀释、"Lost in the Middle"位置偏好、大海捞针。
- 压缩 vs KV Cache：压缩发生在两次 API 调用之间、只替换对话历史中的 tool results，静态前缀不动；替换点之后缓存失效但之前有效。权衡：频繁压缩破坏缓存，最好在接近阈值时**批量压缩**。
- 六种策略对比（实验2-9）：无压缩 → 溢出失败；个体/组合摘要 → 信息碎片化；**上下文感知压缩**（带 query+context，token 减 77% 最优）；带引用的感知；自适应窗口（接近 80% 才压）。
- 生产级分层压缩五层：工具结果预算控制 → 噪声直接删除 → API 层微压缩 → 归档式摘要 → 全量压缩（带熔断器）。
- 设计原则：信息价值非均匀、语义完整性（时间/公司名不可丢）、任务相关性、压缩即理解。保留优先级：架构决策/约束不可摘要，UUID/hash/URL 等标识符必须原样保留。
- 隔离优于压缩：子 Agent 上下文隔离——让海量中间信息根本不进主上下文（子 Agent 只回传几百 token 结论）。

## 我卡住/没懂的地方
- 2.3.5 的"KV Cache 可编辑、可组合"是作者 2026 年论文的前沿延伸（笔记思路），与生产系统的"前缀改一个字节全废"铁律相悖——需明确区分"研究选读"与"当前应遵守的工程默认"。
- 2.6.5 的"时间感三轴"（urgency/persistence/vigilance）较新，且强调"只给读数不够、必须配操作手册"——这与状态栏"用代码维护"的边界如何取舍，需在实践中体会。

## 它背后的原理（别只记操作）
- **注意力机制 & KV Cache**：每个新 token 的 Query 与前面所有 token 的 Key 做点积得到权重，再对 Value 加权求和。KV Cache 缓存已算的 K/V，故前缀不能变。序列开头是"注意力储存池"（Attention Sink），模型对开头/结尾分配更高注意力（位置偏好）。
- **上下文学习 = 检索而非推理**：ICL 让模型像被"临时定制"——没有改参数，但效果类似一次小专项训练，不跨会话累积。这解释了 few-shot 有效、也解释了为何长上下文会"腐化"：模型擅长查、不擅长在单次前向里归纳统计。
- **无状态 API 的数学后果**：对话历史必须每轮完整重发 → 引出 KV Cache 缓存经济性、压缩、隔离等一整套工程。

## 我能复用/改编的点
> 换个需求，这套做法还能怎么用？
- 做任何**长程多轮 Agent**时：System Prompt/工具定义固化在前缀；所有动态信息（时间、计数、TODO、状态）追加到**末尾**的 user-role meta 消息，绝不改前缀。
- 需要**复杂业务规则**时：别堆规则，写 SOP 流程 + 把计费/成功率等规则细化到可执行程度，让产品定规则、工程只编码。
- 上下文**膨胀**时：先上分层压缩（工具预算/删噪声/归档摘要），再考虑全量压缩；能用**子 Agent 隔离**就不让噪声进主上下文。
- 给模型**示例**时：2-3 个覆盖边界的高质量示例，固定不随请求变（保缓存）。
- 给模型**状态**时：用代码确定性维护状态栏（键值对格式），把它当一线生产指标盯准确率，别让 LLM 去总结历史。
