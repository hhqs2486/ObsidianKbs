# 第4章 工具与函数调用

## 这条教程在解决什么
Agent 的「大脑」是 [[大语言模型 LLM]]，但它缺少连接真实数字世界的「手脚和感官」。本章回答两个核心挑战：
1. **工具选择的挑战**：当可用工具从十几个膨胀到成百上千，[[Agent]] 如何准确、高效地找到并完成当前任务所需的那个工具，甚至主动「发现」工具？
2. **异步与事件的挑战**：Agent 如何管理耗时任务、响应随时到达的外部事件（邮件、日历、系统告警），而不陷入同步等待的僵局？

本章给出五类工具的分类总览，讨论适用于所有工具的通用设计原则与 [[MCP]] 协议，并展开主动调用的三类工具（感知、执行、协作）、事件驱动的异步架构，最后以「主动工具发现」收尾。

## 关键内容（按 PDF 章节提纲）
- **4.1 五类工具分类**：按「调用方向 × 作用对象」审视——感知（主动获取信息）、执行（主动改变世界）、协作（主动驱动其他 Agent/人类）、事件触发（Agent 注册、外部触发，唤醒 Agent）、用户沟通（主动向用户传递信息）。
- **4.2 通用设计原则**
  - 能力表达形式：专用代码工具 vs **Skill + 通用执行器**（用自然语言描述流程，靠 bash/解释器执行）。
  - 粒度权衡：功能相似、场景重叠则整合（如 `read_document` 用 `file_type` 区分格式）；参数集差异大或高频则保持独立。工具超过 ~100 个时 [[大语言模型 LLM]] 选择易出错。
  - 通用性：通用工具（如 `code_interpreter`）优于大量专用工具，除非有明确安全/权限/性能理由。
  - **工具描述的艺术**：核心是让模型知道「什么时候用」，而非「能做什么」；写清边界（做不到什么）、用具体例子代替抽象参数规范（如 `phone: +8613888888888`）、描述返回值、附 1–5 个真实调用示例。加示例后调用准确率约从 72% 升到 90%。
  - **参数传递保真性**（反模式）：警惕「静默输入转换」（如中文弯引号被改成直引号）与「静默参数注入」——模型感知到的世界与工具操作的世界之间不能有系统性偏差。
  - 设计演进三阶段：第一代 API 封装 → 第二代 ACI（Agent-Computer Interface，对标 HCI，工具对应目标而非底层 API）→ 第三代（示例驱动调用、动态发现、代码编排执行）。
- **4.3 MCP 与工具选择挑战**：MCP 是 Anthropic 2024 年底发布的开放标准，统一工具互操作（客户端-服务器、JSON Schema、stdio/Streamable HTTP、资源/工具/提示三类原语）。面临：同步调用限制、上下文开销（5 个服务器约 55k token）、信任风险（工具描述投毒、同名遮蔽 tool shadowing、凭证泄露）。
- **4.4–4.6 三类主动调用工具**
  - 感知工具：粒度/组织/输出格式权衡；分页 cursor；`offset/limit` 与**显式截断**（静默截断危险）；只读性带来可缓存、可并行的红利。
  - 执行工具：错误代价高，需多层安全——输入验证（快速失败）、权限控制（黑名单只是基础）、提议者-审核者（事前审批/事后验证）、Sidecar（与主模型流式并行、只看结构化字段、门控单次调用）、执行-验证-反馈闭环（写代码后自动 linter）、长输出截断+持久化、沙盒隔离、可观测性、幂等性与取消语义。
  - 协作工具：子 Agent 专业化分工、四类上下文传递策略（最小化/手动/自动裁剪/LLM 生成）、HITL 人在回路与学习闭环。
- **4.7 事件驱动的异步 Agent**：用统一事件流建模所有输入；三类处理策略——取消式（紧急）、队列式（常规）、并行式（独立轻量查询）；工程上用「占位符」修复同步格式以支持异步打断；更根本的是将工具接口的「启动/完成」解耦。
- **4.8 主动工具发现**：检索预筛选、Agent 主动声明缺口（MCP-Zero 两层语义路由）、动态加载与 KV Cache 优化（schema 追加到末尾而非 system prompt）、Skills 渐进式披露（把发现变成按需查阅）。
- **4.9 小结**：工具设计质量决定能力上限，异步架构决定能否在真实世界可靠运行。

## 我卡住/没懂的地方
- 「训练同步 / 部署异步」矛盾的工程占位符方案，与「异步工具接口解耦」的边界——何时用提示工程、何时改工具接口，原文给的是原则性判断，落到具体业务仍需经验。
- Sidecar（轻量模型、只看结构化字段）与提议者-审核者（能力相近的不同家族模型）的取舍，在资源受限时如何折算成本，原文未给量化准则。

## 它背后的原理（别只记操作）
- **为什么需要工具**：[[大语言模型 LLM]] 只在文本空间推理，无法读实时数据、改外部系统。工具是把「语言智能」桥接到「真实世界动作/信息」的接口。
- **Function Calling 本质**：模型按 JSON Schema 生成结构化参数，由运行时执行并回灌结果，形成「思考→行动→观察」闭环。
- **为什么工具描述决定准确率**：模型选错工具大多不是能力问题，而是描述边界不清、缺反例、参数模糊——修正描述的 ROI 远高于换更强模型。
- **为什么 MCP 统一生态**：各框架工具格式不一导致重复适配，MCP 用统一「插座标准」做到一次开发、处处可用。
- **为什么异步要用占位符**：当前模型按严格同步序列训练（tool_call 后必接 tool_result），真实部署事件随时插入；占位符在常态保留完美同步轨迹，只在打断时妥协。
- **为什么沙盒**：通用执行工具等于「能跑任意代码」，必须与宿主机隔离，否则一次错误/被攻破就波及真实系统。

## 我能复用/改编的点
> 换个需求，这套做法还能怎么用？
- 做「带工具的客服 Agent」时，用**五类工具**框架梳理能力：哪些用感知（查订单）、哪些用执行（改地址需审批）、哪些用用户沟通（多渠道召回）。
- 做自己的工具集时，先写清**工具描述（何时用 + 边界 + 例子 + 返回值）**，再评估要不要加示例——这是性价比最高的优化。
- 工具数 > 50 时，直接用 **MCP + 延迟加载 / Skills 渐进式披露** 替代全量注入，省 token 且提升选择准确率。
- 任何不可逆操作（发消息、扣费、删文件）都套**提议者-审核者 或 Sidecar 门控**，并把拒绝当作一次普通工具失败让 Agent 自恢复。
- 需要 Agent「自己动起来」时，用**事件触发工具 + 异步架构**（取消/队列/并行三策略），而非轮询。
