# 工具调用错误处理

## 一句话定义
> 工具调用错误处理（Tool Call Error Handling）是让 Agent 在执行工具出错、超时、被拒或参数失真时，能诊断原因、安全回退并正确恢复的一整套机制。

## 它解决什么问题 / 为什么存在
- 执行工具错误代价极高（误删文件、错误命令、真实财务损失），且许多失败根因隐蔽——不是模型不会用，而是输入被悄悄篡改或描述不清。
- 好的错误处理让 Agent 把“调用失败”当作新输入，像处理正常结果一样自我修正。

## 核心原理（大二电子信息工程专业学生能懂）
- **参数保真性（最隐蔽的反模式）**：禁止静默输入转换（如弯引号被偷改成直引号，导致“找不到匹配”）、禁止静默参数注入（如 git commit 被偷偷加参数）。模型感知的世界与工具操作的世界不能有系统性偏差——否则模型无法自诊。
- **执行工具安全分层**：① 输入验证（路径遍历、命令注入，快速失败不“智能”修正）；② 权限控制（工作目录限制、命令黑名单，但黑名单非唯一手段）；③ 提议者-审核者（独立模型事前审批/事后验证）；④ Sidecar（与主模型流式输出并行、只看结构化字段的门控校验，亚秒级）。
- **执行-验证-反馈闭环**：写代码后自动跑 linter，把结构化错误返回给 Agent 下一轮修正。
- **幂等性与取消**：同一操作执行多次影响相同（带 idempotency key 或先查后改）；不可幂等操作（发邮件/转账）用“预检-确认”两段式。
- **异步打断的占位符**：工具未完成时被打断，注入占位符 tool result（“工具在后台执行，请优先处理新事件”）修复同步格式。

## 关键参数 / 易错点
- 易错点：把失败简单重试——非幂等操作重试会重复发信/重复转账；Sidecar 若读主模型自由文本会被话术操纵，必须只看结构化字段。
- 审查模型配对：提议者-审核者用能力相近但家族不同的模型（如 Opus 与 GPT-5 互审），Sidecar 可用轻量模型（任务是分类而非开放式推理）。

## 类比（帮助理解）
- 像银行双签：转账需经办+审核两道签字；再配一个边上的风控（Sidecar）实时拦异常，且所有操作留日志可审计。

## 设计时怎么用（反推思维）
> 做执行工具时，我会加输入校验+权限黑名单+事前审批（高危操作）+Sidecar 门控+自动 linter 验证，并对写操作保证幂等或预检确认。

## 典型应用 / 我在哪见过
- 实验4-2 执行工具 MCP（linter 验证、危险命令检测、长输出截断）；Claude Code 的 Sidecar；异步 Agent 的 cancel_tool(task_id)。
