# ReAct

## 一句话定义
> ReAct（Reason + Act，推理+行动）是 Agent 的核心执行范式：模型在“思考（Thought）→行动（Action，调用工具）→观察（Observation，看结果）”的循环中迭代，直到信息充分再作答。

## 它解决什么问题 / 为什么存在
- 一次性“检索-生成”管道（非智能体化）缺乏深度理解、分解和迭代探索的能力上限。
- ReAct 让 Agent 像人一样边想边做、根据反馈调整，而非盲目一次性输出。

## 核心原理（大二电子信息工程专业学生能懂）
- 循环：① Thought 分析需求、定关键词；② Action 调用工具（如 knowledge_base_search / web_search）；③ Observation 看结果是否充分——不够就回到 Thought 提炼更精确查询，够了才综合生成答案。
- 在 [[工具 Tool]] 中，ReAct 是 Agent 主导 [[函数调用 Function Calling]] 的“控制器”；在 [[RAG]] 中，它是“智能体化 RAG”的心脏（Agent 自主决定何时搜、搜什么、是否继续搜）。
- 同步训练假设与异步部署的矛盾：训练时假设“tool_call 后下一条必是 tool_result”，真实部署中用户可能打断。工程上用占位符修复格式、非紧急事件入队、只在真正紧急时打断（见 [[工具调用错误处理]] 异步部分）。

## 关键参数 / 易错点
- 易错点：复杂问题首轮关键词不精确→检索不全→事实错误；需多轮迭代弥补。弱模型可能陷入“只关注最后一个事件”的批量处理陷阱（用状态栏标记缓解）。
- ReAct 原生多用于单 session 一问一答；跨渠道异步沟通需配合用户沟通工具与事件驱动架构。

## 类比（帮助理解）
- 像做研究：先想“我缺什么资料”（Thought），去查（Action），看到结果（Observation），发现不够再换个关键词查，直到材料齐了才动笔。

## 设计时怎么用（反推思维）
> 做复杂问答 Agent 时，我会用 ReAct 循环让模型分解子问题、多轮检索并交叉验证，而非一次搜索就生成答案。

## 典型应用 / 我在哪见过
- 智能体化 RAG（实验3-9 司法问答，多跳准确率显著提升）；Agent 主导知识库检索；OpenClaw 等原生 ReAct 循环 Agent。
