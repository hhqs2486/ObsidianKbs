# 工具选择

## 一句话定义
> 工具选择（Tool Selection）是 Agent 在众多可用工具中准确找到并调用“完成当前任务所需那一个（或几个）”的能力，是工具规模变大后的核心挑战。

## 它解决什么问题 / 为什么存在
- 当工具从十几个增长到成百上千，平铺到上下文既浪费 token 又干扰决策，模型选择精度下降（“工具爆炸”）。
- 挑战分两步：从被动“选择”工具，进化到主动“发现”工具。

## 核心原理（大二电子信息工程专业学生能懂）
- **粒度权衡（整合 vs 分离）**：功能相似、场景重叠应整合（extract_pdf/docx/pptx → 统一 read_document 加 file_type 参数），降低 LLM 认知负担；但参数形态/延迟差异大的（OCR vs 视频解析）应保持独立。
- **通用性设计**：通用工具（code_interpreter）优于十几个专用计算器，除非有安全/权限/性能理由。
- **层次化组织**：按信息源分搜索/读取/解析/查询四类，在 system prompt 显式说明分类，帮 LLM 快速定位。
- **主动工具发现**：不一次性注入全部 schema，而是 Agent 用自然语言声明能力缺口（如 “我需要查 GitHub 贡献者”），系统两层语义路由（服务器级→工具级）匹配注入。MCP-Zero 在约 2800 工具上比全量注入省约 98% token；Anthropic 实验使 Opus 4 准确率从 49%→74%。
- **动态加载与 KV Cache**：新工具 schema 作为 user 消息追加到轨迹末尾，保持 system 前缀稳定以复用缓存（OpenAI tool_search、Claude Code 延迟加载）。

## 关键参数 / 易错点
- 易错点：工具数超 100 时 LLM 易选错；弱模型难理解“工具定义出现在上下文中间”，需强化学习（见 [[评估]]/[[SFT]]）。
- 先查描述再怀疑模型：频繁选错多半是 [[工具描述]] 不准，而非模型不行。

## 类比（帮助理解）
- 像大超市找商品：货架空了（工具全注入）你反而迷路；分好区（层次化）+ 导购台按需查（主动发现）才高效。

## 设计时怎么用（反推思维）
> 做大规模工具集时，我会用 MCP 统一暴露、按类分层组织，并接入 discover_tools 元工具做主动发现，避免一次性灌入全部 schema。

## 典型应用 / 我在哪见过
- 实验4-6 主动工具发现（Qwen3-4B 在 120+ 工具上，主动发现显著提准确率）；Skills 机制把“工具发现”变成“按需查阅文档”。
