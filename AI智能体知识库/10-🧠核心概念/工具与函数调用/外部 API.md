# 外部 API

## 一句话定义
> 外部 API（External API）是 Agent 通过工具调用的、位于自身之外的第三方服务接口（如天气、股价、邮件、GitHub、日历），让 Agent 获取或改变外部世界的状态。

## 它解决什么问题 / 为什么存在
- 模型自身无法触达实时、私有或远程的数据与动作。外部 API 把“真实世界的系统”变成 Agent 可调用的能力。
- 在工具演进史中，第一代工具设计就是“直接 API 封装”——把每个 API 端点对应一个工具。

## 核心原理（大二电子信息工程专业学生能懂）
- Agent 通过 [[函数调用 Function Calling]] 把 API 调用编码成结构化请求，由框架发往远端并取回结果。
- 暴露方式：早期每个 Agent 框架各自封装（OpenAI/Anthropic/LangChain 格式不一）；现在多经 [[MCP]] 服务器统一暴露，实现“一次开发，处处可用”。
- 常见外部 API 类型：公开数据源（天气、股价、Wikipedia、ArXiv）、私有数据源（日历、Notion，需授权）、以及执行类对接（发邮件、建 GitHub PR、Webhook 回调）。
- 异步场景：外部 API 回调（webhook）是事件触发工具 connect_channel 的典型来源，让“世界主动通知 Agent”。

## 关键参数 / 易错点
- 安全：调用外部 API 涉及凭证（OAuth token / API key），一旦被诱导用于非预期操作，损失真实即时。
- 可靠性：网络/超时/限流——需配额与速率限制；不可幂等的写操作（发邮件、转账）要“预检-确认”两段式（见 [[工具调用错误处理]]）。
- 信任：接入第三方 API 等于把一段不受控文本注入上下文并交出凭证，需最小权限、锁版本、审查描述。

## 类比（帮助理解）
- 像公司前台打电话给外部单位办事：能查到公司没有的信息、也能代办外部动作，但每次都要核实身份、控制授权范围。

## 设计时怎么用（反推思维）
> 做 Agent 时，我会把外部 API 包成 MCP 工具，配最小权限凭证，并对写操作加审批/幂等保护，防止误调用造成真实损失。

## 典型应用 / 我在哪见过
- 感知实验4-1（天气/股价/维基等开放 API）；执行实验4-2（日历、GitHub PR、邮件、Webhook）；PineClaw 的电话 API 回调。
