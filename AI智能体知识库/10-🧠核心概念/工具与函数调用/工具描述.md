# 工具描述

## 一句话定义
> 工具描述（Tool Description）是写给 LLM 看的“使用说明书”，核心任务是让模型知道“什么时候用这个工具”，而不只是“它能做什么”。

## 它解决什么问题 / 为什么存在
- 工具调用失败，绝大多数根因不是模型不知道工具能做什么，而是不知道它**不能**做什么。
- 高质量描述直接决定 Agent 调用准确率；调试时“频繁选错工具，应优先改描述而非换更强模型”。

## 核心原理（大二电子信息工程专业学生能懂）
- 说“当需要获取实时信息或查找未知事实时使用”远胜“搜索相关内容”——前者帮模型做调用决策，后者只讲功能。
- **边界最重要**：明确写清做不到什么、不接受什么输入（如“只能按文件名匹配，不能搜内容”），反例说明比能力描述更关键。
- **参数用例子代替抽象规范**：“timestamp：RFC3339，例如 2024-03-15T14:30:00Z”比单写“RFC3339”有效得多；phone 写成“E.164，例如 +8613888888888”。
- **返回值要说清**：“返回 JSON 数组，每项含 title/url/snippet”；耗时长的工具注明执行代价（如“完整网页需 5-10 秒”）。
- **附 1-5 个真实调用示例**：JSON Schema 只能描述类型，表达不了“时间戳是秒还是毫秒、过滤如何嵌套”这类隐式约定。加示例后准确率可从约 72% 升到 90%。

## 关键参数 / 易错点
- 易错点：边界不清、缺反例、参数含义模糊——这三条是工具选错的主因。
- 安全风险：工具描述会原样进模型上下文，恶意服务器可在 description 里夹带指令（提示注入变种，见 [[MCP]] 信任模型）。

## 类比（帮助理解）
- 像产品说明书：好说明书先讲“什么时候该用、什么情况不能用、参数长啥样（举例）”，而不是只列功能清单。

## 设计时怎么用（反推思维）
> 写工具时，我会先写清触发场景+边界反例+带例参数+返回格式，并附示例，再把描述当不可信输入审查（防投毒）。

## 典型应用 / 我在哪见过
- 所有 [[函数调用 Function Calling]] 工具的 JSON Schema 描述；MCP 工具的标准化描述；Tool Search 返回给模型的 schema。
