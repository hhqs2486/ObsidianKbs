# LoRA Low-Rank Adaptation

## 一句话定义
> LoRA 是"冻结大模型主干、只在旁边长出一小撮低秩矩阵"的参数高效微调法——用极少的参数让模型学会新风格/新概念，显存省、可热插拔、部署方便。

## 它解决什么问题 / 为什么存在
- 全量微调一个大模型（如 SDXL 2.6B、LLaMA 70B）要更新全部权重，显存吃紧、易灾难性遗忘、且每个任务存一份整模型不现实。
- LoRA 假设"任务带来的权重变化 ΔW 是低秩的"：把 ΔW 拆成两个瘦矩阵 B·A（r≪d），只训这两个小矩阵，主干 W 完全冻结。

## 核心原理（大二能懂的水平）
- 对任意线性层 `W ∈ ℝ^{d×d}`，冻结 W，注入低秩增量：
  `W' = W + ΔW = W + B·A`，其中 `A ∈ ℝ^{r×d}`、`B ∈ ℝ^{d×r}`，秩 r 远小于 d（注意力层常见 r=4–16，重度定制 r=64–128）。
- 参数量从 d² 降到 2·d·r。例：SDXL 注意力 d=640、r=16，单层适配器约 2 万参数而非 41 万，约 20× 缩减；整模型 LoRA 通常 20–200MB，对比基座 5GB。
- 推理时可缩放：`W' = W + α·B·A`，α（通常 0.5–1.5）控制"加多强"，可在运行时调，不必重训。多个 LoRA 可加性叠加（但非线性交互要注意）。
- 也可把 LoRA 烘焙进主干（`fuse_lora`）提速，但会丢失运行时调 α 的灵活性。
- 它本是 NLP 方法（Hu et al., 2021），几乎原样搬到了扩散模型，是社区微调事实标准。

## 关键参数 / 易错点
- 秩 r：r 太小学不下、太大失去高效意义。风格/概念常用 4–32；重度个性化用 64+。
- α 缩放：α>1.5（如 2、3）常导致过风格化/崩坏，建议 ≤1.5。
- 基座匹配：SDXL 的 LoRA 在 SD 1.5 上会因注意力维度不符而静默失效——LoRA 必须匹配基座结构。
- 显存：配合梯度检查点 + 量化（QLoRA），可在 8GB 显卡训 SD LoRA；多层 LoRA 也能叠在 4-bit 基座上。
- 易错：把多个 LoRA 权重都拉满（α 全设为 3），输出互相打架、崩坏。

## 类比（帮助理解）
- 像给原厂发动机（冻结主干）外挂一个小小的涡轮控制器（低秩矩阵）：不改发动机本体，只调一点点就能换驾驶风格，拆装也便宜。
- 又像在厚词典（W）边贴便签（B·A）记录新用法，不必重印整本词典。

## 设计时怎么用（反推思维）
> 要给模型加新风格/新概念（如品牌画风、某个人脸）时，我会直接上 [[微调]] 里的 LoRA 而非全量微调：冻结基座，只训 rank-16 上下的低秩矩阵，单卡消费级 GPU 十几分钟出 20–200MB 适配器。部署时把多个 LoRA 作为 rank-r 增量热插拔（不动基座权重），这比"每任务存一份全模型"省几个数量级显存——在 [[Stable Diffusion]] 里尤其常用。

## 典型应用 / 我在哪见过
- Stable Diffusion 社区海量风格/角色 LoRA（CivitAI、HuggingFace）。
- LLM 适配器微调（PEFT 库）、QLoRA 在单卡训大模型。
- 生产图生图 SaaS：同基座上热插拔几十个 LoRA + 数个 ControlNet 做多租户服务。

## 关联
- 前置知识：[[微调]]、[[Stable Diffusion]]

- 反例/误区：把 α 拉到 2–3 "让它更强"结果崩坏；或拿错基座的 LoRA 导致静默失效
