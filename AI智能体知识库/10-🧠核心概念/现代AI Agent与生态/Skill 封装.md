# Skill 封装

## 一句话定义
> Skill 封装是把「一类任务的标准做法」打包成一个可复用单元：包含触发条件、执行步骤、配套资源（脚本/模板）与验收标准，让 Agent 遇到同类问题时直接调用，而不必每次重新摸索。

## 它解决什么问题 / 为什么存在
- 很多任务反复出现（如「跑测试并修红」「生成周报」「接一个新 MCP 工具」），若每次都靠模型临场发挥，质量不稳、步骤易漏。
- Skill 把「人类验证过的好流程」固化下来，提升一致性、可审计性与可迁移性——是 Agent 从「会做」到「做得稳」的沉淀机制。

## 核心原理（大二电子信息工程专业学生能懂）
- 一个 Skill 通常四件套：
  - 触发器（trigger）：什么情况下该用这个 Skill（如「检测到单元测试失败」）。
  - 步骤（steps）：按顺序怎么做，可含调用工具、跑脚本、写文件。
  - 资源（resources）：配套的脚本、模板、提示词片段，拿来即用。
  - 验收标准（acceptance）：怎样算「做完了且做对了」，用于自检或门禁。
- 运行期：Agent 匹配到触发条件 → 载入该 Skill 的步骤与资源 → 执行 → 用验收标准核对。
- 与工具的区别：工具是「一个原子能力」，Skill 是「一组带流程的能力组合」，更接近「工序卡」。

## 关键参数 / 易错点
- 触发条件要精准：太宽会误触发，太窄会用不上。
- 验收标准要可判定：模糊的「做好了」没用，需具体（如「测试全绿」「文件存在且非空」）。
- 资源要与步骤绑定：脚本路径、模板变量要在 Skill 内自洽，否则换环境就失效。
- 易错点：把 Skill 写成「一大段提示词」而非「带资源与验收的结构化包」——那样只是又一段说明，不是可复用单元。

## 类比（帮助理解）
- 像「SOP 作业指导书 + 配套工具包」：不仅写「第一步第二步」，还附上要用的表格模板和「完工检查单」，新人照着做就不会跑偏。

## 设计时怎么用（反推思维）
> 做长期运行的 Agent 时，我会把高频、易错、要求一致的任务（如发布流程、代码评审）沉淀成 Skill：写明触发、步骤、资源与验收，让 Agent 复用而不每次重新发明轮子。
