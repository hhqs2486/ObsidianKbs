# τ-bench（Tau-Bench）

## 一句话定义
> τ-bench（Tau-Bench）是 Salesforce 提出的 Agent 基准，考察智能体在「带工具调用 + 与模拟用户多轮对话」的真实业务场景里，能否既完成任务又不破坏业务规则。

## 它解决什么问题 / 为什么存在
- 很多 Agent 评测只看「最终答案对不对」，却忽略两件事：(1) 是否通过正确调用工具完成动作（如改订单）；(2) 是否遵守领域策略（如「非本人不能改地址」）。
- τ-bench 把「工具使用正确性」「策略合规性」「与用户协作」放进同一个可复现的仿真环境一起测。

## 核心原理（大二电子信息工程专业学生能懂）
- 环境提供一组「领域工具」（如零售的查单/改单/退款 API、航空的订票 API），以及一个「模拟用户」Agent。
- 真实被测 Agent 要和用户多轮对话，理解意图，然后调用工具去执行；模拟用户会追问、改口、试探边界。
- 任务结束用「状态检查」判定：数据库最终状态是否符合预期，且全程是否违反策略（policy）。
- 分领域：如 retail（零售）、airline（航空），每个领域有一套工具与策略集。

## 关键参数 / 易错点
- 通过率（pass^rate）：任务是否既完成又合规。
- 工具调用准确率：是否调了对的工具、传了对的参数。
- 策略违规次数：是否在权限/流程上越界。
- 易错点：只追求「把事办成」而忽略策略——τ-bench 专门惩罚「违规完成的任务」。

## 类比（帮助理解）
- 像「银行柜员上岗考」：不仅看你有没有把业务办完，还看你有没有核对身份、有没有走审批——办成了但违规，照样不及格。

## 设计时怎么用（反推思维）
> 做「客服 / 业务办理 Agent」时，我会用 τ-bench 式仿真验收：在可控环境里让模拟用户反复「刁难」，确认我的 Agent 既会调对工具，又守住权限与流程红线。

## 典型应用 / 我在哪见过
- 评测工具调用型 Agent、客服/运营自动化 Agent 的可靠性与合规性。
- 论文与榜单常用基准（Salesforce Tau-Bench，retail/airline 双领域）。
