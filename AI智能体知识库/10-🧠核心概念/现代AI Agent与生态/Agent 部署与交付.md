# Agent 部署与交付

## 一句话定义
> Agent 部署与交付指把一个"能跑的 demo Agent"变成"能上线、可观测、可控成本、可回滚的生产服务"的全部工程：入口、日志/trace、超时重试、成本上限、权限边界、健康检查。

## 它解决什么问题 / 为什么存在
- demo 跑通 ≠ 能交付：demo 手动跑一次、出错就崩、无成本概念、危险操作直接做、只有代码无说明。
- 生产 Agent 要：固定入口（CLI/Web/Slack/Action）、日志+追踪、超时/重试/最大步数、成本上限、权限边界+人工确认、README（怎么跑、怎么配 key、怎么扩、有哪些限制）。

## 核心原理（大二电子信息工程专业学生能懂）
- **生产架构主线**：API 网关(鉴权+限流) → 输入护栏 → 提示路由 → 语义缓存 → LLM(流式) → 输出护栏 → 评估日志 → 成本统计 → 响应(SSE)。
- **流式交付**：用 SSE 把 token 一个个推给前端，首 token 200-500ms 到达，感知延迟降 ~90%。
- **三层容错**：
  - API 失败 → 指数退避+抖动，最多 3 次重试；
  - 模型失败（坏 JSON/幻觉函数名）→ 带错误信息重试；
  - 应用失败（向量库/缓存挂）→ 优雅降级，不拖垮主流程。
- **降级链**：主模型挂 → 依次 fallback 到更便宜/更可用的模型 → 缓存响应 → "暂时不可用"。
- **可观测三支柱**：结构化日志、追踪（OpenTelemetry）、指标看板（P50/P99 延迟、缓存命中率、护栏拦截率、单请求成本）。
- **上线检查清单**（摘录）：API key 进环境变量、按用户限流、输入/输出护栏、语义缓存、流式、退避、fallback、成本追踪、健康检查、最大 token、超时、CORS、压测。

## 关键参数 / 易错点
- 无超时 / 无 max steps：一个卡死任务拖垮整个服务。
- 无成本上限：Agent 疯调模型，账单爆炸。
- 危险工具无确认：删文件/发邮件/付款直接执行，出事无法挽回。
- 没有 README：别人 clone 下来不知道填什么 key、怎么跑。

## 类比（帮助理解）
- demo 像"实验室样品"，生产像"量产上市产品"——差的是品控、说明书和售后。

## 设计时怎么用（反推思维）
> 做 Agent 系统时，我会先定"明确用户、明确任务、明确成功标准"，再谈部署；所有外部副作用走三级门禁（见 [[Agent 安全门禁]]），并保留 trace 以便回放失败。

## 典型应用 / 我在哪见过
- 客服机器人、Cursor/ChatGPT 类产品的后端、内部 Coding Agent 服务，常配合 [[Knative 与 Agent 部署]] 做弹性伸缩。
