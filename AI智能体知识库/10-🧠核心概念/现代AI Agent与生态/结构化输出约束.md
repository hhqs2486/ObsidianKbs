# 结构化输出约束

## 一句话定义
> 结构化输出约束是让大模型「严格按预定格式（通常是 JSON Schema）吐出可机读结果」的一组技术，保证下游程序能稳定解析，而不是拿到一段飘忽的自由文本。

## 它解决什么问题 / 为什么存在
- Agent 要把模型输出喂给代码：调工具、写数据库、做分支判断。如果模型偶尔输出「带注释的 JSON」「多说一句废话」「字段名拼错」，解析就崩。
- 结构化输出约束把「格式正确性」从「靠提示词祈祷」变成「靠协议/解码强制保证」。

## 核心原理（大二电子信息工程专业学生能懂）
- 用一个 JSON Schema（Schema 遵循 2020-12 标准）描述「允许哪些字段、什么类型、是否必填、枚举值有哪些」。
- strict mode（严格模式）：模型被告知必须只产出符合该 Schema 的内容，不能有额外字段、不能省略必填项。
- 约束解码（constrained decoding）：在生成每个 token 时，解码器只放行「仍符合 Schema 的下一个字符」，从根本上杜绝非法 JSON（如未闭合括号）。
- 工程上常用 Pydantic（Python）/ Zod（TS）定义数据类，框架自动转成 Schema 并校验返回对象。
- 三种典型失败模式：格式非法（JSON 残缺）、字段缺失/多余、类型/枚举不符——约束技术分别用 strict mode 与约束解码解决前两者，用 Schema 强类型解决第三者。

## 关键参数 / 易错点
- Schema 复杂度：嵌套越深、枚举越多，模型越易跑偏，需配合 strict mode。
- 严格模式开关：开着最稳，但会限制模型灵活性（不能多解释）。
- 校验兜底：即使有约束解码，工程上仍建议用 Pydantic/Zod 二次校验，防止边界 case。
- 易错点：以为「提示词写『请输出 JSON』」就够——不稳，必须靠协议层或解码层强制。

## 类比（帮助理解）
- 像「填表」：Schema 是表格的格子与格式说明，约束解码是「只能往格子里写、写错格不让你提交」，而不是让你在白纸上随便写再指望别人认得。

## 设计时怎么用（反推思维）
> 做需要模型产出「可解析结果」的 Agent（如抽取订单信息、决定调哪个工具）时，我会用 JSON Schema + strict mode + Pydantic 校验，把输出锁死成可机读结构体，下游直接当对象用。
