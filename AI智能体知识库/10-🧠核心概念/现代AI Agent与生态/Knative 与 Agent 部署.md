# Knative 与 Agent 部署

## 一句话定义
> Knative 是构建在 Kubernetes 之上的"无服务器（serverless）"框架，用 `Knative Serving` 提供自动扩缩（含缩到 0）和基于请求的路由，很适合部署流量波动大的 Agent 服务。

## 它解决什么问题 / 为什么存在
- Agent 服务常"平时没流量、偶尔突发"：一直开着 GPU/实例太贵，突发时又不够用。
- Knative 让 Agent 在无人用时缩到 0 个实例（省钱），来请求时秒级冷启动扩容（可用），天然支持 [[Agent 部署与交付]] 里的弹性需求。

## 核心原理（大二电子信息工程专业学生能懂）
- **Knative Serving**：
  - `Service` 定义"要跑什么镜像 + 用多少资源"。
  - `Revision`：每次部署产生不可变版本，便于回滚（对应 Agent 提示词/模型版本管理）。
  - `Route`：把流量分到不同 Revision，可做灰度（如 10% 流量试新 prompt）。
- **自动扩缩（Autoscaler）**：
  - 基于并发/请求数自动加减 Pod。
  - 缩到 0（scale-to-zero）：无请求时实例数=0，来请求再冷启动。
  - 冷启动延迟是主要代价，长连接/WebSocket Agent 要考虑保活。
- **与 Agent 契合点**：Agent 多 I/O 等待，单实例可并发很多请求；配合队列、超时、成本上限（见 [[Agent 部署与交付]]）。

## 关键参数 / 易错点
- 冷启动：Agent 首次响应可能慢，需设就绪探针与最小实例数（部分热备）平衡成本与延迟。
- 状态：Knative Pod 可能被回收，Agent 的有状态数据要外置（数据库 / 对象存储 / 检查点，见 [[Agent 追踪 Trace]]）。
- 长任务：默认请求有超时，超长 Agent 任务要走异步队列，别卡在单个 HTTP 请求里。

## 类比（帮助理解）
- 像"按需开的出租车站"：没客时车位空着不花钱，来客了自动派车。

## 设计时怎么用（反推思维）
> 做流量稀疏、成本敏感的 Agent 后端时，我会用 Knative 跑服务、用外部存储存会话与检查点，并为长任务加队列，避免冷启动和回收丢状态。

## 典型应用 / 我在哪见过
- 客服 Agent、内部工具 Agent、事件触发的自动化（GitHub Action / 队列消费）部署在 K8s 集群。
