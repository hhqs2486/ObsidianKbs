# 工具接口设计

## 一句话定义
> 工具接口设计是指给大模型暴露「可调用的函数」时，如何命名、写描述、定义参数，让模型「看得懂何时用、怎么用、用对」，是 Agent 可靠性的第一道关口。

## 它解决什么问题 / 为什么存在
- 模型不会「猜」你的函数意图。名字歧义、描述含糊、参数过多，都会让模型选错工具或传错参。
- 好的工具接口等于给模型一份「清晰的使用说明书」，差的接口等于埋雷——很多 Agent 抽风的根源是工具 schema 写烂了。

## 核心原理（大二电子信息工程专业学生能懂）
- 命名用 snake_case 且语义唯一：如 `refund_order` 比 `do_action` 好；避免近义重名让模型纠结。
- 描述用「Use when X. Do not use for Y.」句式：正面说适用场景，反面划清边界，显著降低误用。
- 参数要「原子化」：一个工具只干一件明确的事，比「一个大杂烩工具传一堆可选参数」更易被模型用对。
- 枚举与类型写清：用 enum 限定取值、用 required 标必填，减少模型自由发挥出错。
- 把「复杂动作」拆成「小工具组合」，而不是塞进单一巨型工具——这呼应工具组合与链式。

## 关键参数 / 易错点
- 描述质量直接决定调用准确率：含糊描述 → 误调用。
- 参数数量与可选性：参数越多越易错，能用枚举就别用自由文本。
- 工具过多会「选择过载」：几十个工具堆一起，模型容易选错，需要路由/分组。
- 易错点：只给名字不给「何时不用」的边界说明，模型会过度泛化调用。

## 类比（帮助理解）
- 像「给新人写的操作手册」：步骤名清楚、写明「什么时候用这步、什么情况千万别用」，新人（模型）才不会乱按按钮。

## 设计时怎么用（反推思维）
> 给 Agent 接工具时，我会像写 API 文档一样写每个工具的「名称 + Use when/Do not use for + 原子参数 + 枚举」，先在小样本上测模型能否选对，再批量接入。

## 典型应用 / 我在哪见过
- 所有函数调用型 Agent 的工具定义；MCP server 暴露的工具描述。
- 仓库 `phases/13-tools-and-protocols/05-tool-schema-design` 专章讲解命名、描述句式与原子 vs 单体工具。
