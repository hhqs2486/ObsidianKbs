# Realtime API

## 一句话定义
> Realtime API 是一类以「低延迟双向流式」方式连接大模型的服务接口，让语音、音频或连续事件能近乎实时地进出模型，模型直接在流里完成理解与生成。

## 它解决什么问题 / 为什么存在
- 传统「语音→ASR→文本→LLM→文本→TTS→语音」多段串行管线延迟高（常 >1–2 秒），对话轮次感差、打断困难。
- 希望像人与人通话一样：边说边听、能随时打断、模型立即响应。Realtime API 把语音输入输出直接接入带状态的流式模型，省掉中间文本往返。

## 核心原理（大二电子信息工程专业学生能懂）
- 客户端与服务器之间建立一条长连接（常见 WebSocket），数据以小块音频帧/事件帧双向持续流动。
- 模型端维护一个「会话状态」（session），包含系统提示、可用工具、语音音色等配置。
- 用户说话的音频帧流入，模型在流中做语音识别 + 语义理解，决定「该回一句话」还是「该调用工具」。
- 模型回的音频帧流出，由客户端直接播放；如需查数据库/调 API，模型在流中发出函数调用事件，客户端执行后把结果送回流。
- 代表实现：OpenAI Realtime API（基于 WebSocket，支持音频与文本双模态）、Google Gemini 2.5 Live（原生多模态流式）。

## 关键参数 / 易错点
- 延迟（首包耗时）：端到端往返最好在数百毫秒级，否则对话不自然。
- 断句 / 端点检测（VAD）：何时判定用户「说完了」很关键，判错会抢话或等待过长。
- 打断（barge-in）：用户中途插话时，要立刻停掉正在播放的合成语音，否则体验差。
- 成本：双向流式长连接持续计费，需设会话超时与并发上限。
- 易错点：把 Realtime API 当普通 REST 调用用——它是有状态、长生命周期的会话，不是「一问一答」请求。

## 类比（帮助理解）
- 像打电话：普通 API 是「写信寄信等回信」，Realtime API 是「一直通着的电话线」，双方随时说、随时听。

## 设计时怎么用（反推思维）
> 做语音客服 / 语音陪练 / 实时翻译系统时，我会用 Realtime API 承载端到端语音流，把 ASR、LLM、TTS 的串行拼接换成一条有状态的流式会话，并在设计里预留「打断」与「工具调用回灌」的钩子。

## 典型应用 / 我在哪见过
- 实时语音助手、AI 电话客服、语音面试/口语陪练、实时字幕与翻译。
- 仓库 capstone `03-realtime-voice-assistant` 即以 Realtime API + 五段流式（ASR/VAD/turn-detector/LLM/TTS）构建语音 Agent。
