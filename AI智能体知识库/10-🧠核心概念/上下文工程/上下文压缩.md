# 上下文压缩

## 一句话定义
> 上下文压缩（Context Compression）是在两次 API 调用之间，由 Agent 框架对消息列表做预处理，用精炼摘要替换臃肿原文（尤其是工具结果），以控制长度、提升思考质量的技术。

## 它解决什么问题 / 为什么存在
- 多轮交互中上下文不断膨胀：工具结果动辄数万字符，几轮就撑爆窗口；同时长上下文导致"检索精度下降"（上下文腐化）。
- 压缩有两个动机：① 解决长度/成本约束；② 提升思考质量——总结后的高密度知识比原始堆叠更易被模型使用。

## 核心原理（大二电子信息工程专业学生能懂）
- 内部机制：**上下文学习本质是"检索而非推理"**——注意力擅长在已有内容里"查找"，不擅长一次前向就做统计归纳。压缩把"需思考才得的结论"变成"可直接检索的知识"（与状态栏同源）。
- **压缩与 KV Cache 互补**：压缩发生在两次调用之间；System Prompt 与工具定义（静态前缀）永远不动；只替换对话历史中的 tool results，之前的缓存仍有效。权衡：频繁压缩破坏缓存，最好在接近阈值时批量压缩。
- **六种策略对比**（实验 2-9）：无压缩（溢出失败）/ 个体摘要 / 组合摘要 / **上下文感知压缩**（把查询意图+已有信息纳入压缩决策，token 减 77%、成功率最高）/ 带引用 / 自适应窗口（<80% 保留原文，超出批量压）。
- **生产级分层压缩**（Claude Code 参照）：工具结果预算控制 → 噪声直接删 → API 层微压缩 → 归档式摘要 → 全量压缩（带熔断器）。

## 关键参数 / 易错点
- **压缩即理解**：负责压缩的模块需接近主模型的理解力（"模型调用模型"递归架构）。
- 保留优先级：架构决策/关键约束不得摘要；UUID、hash、IP、URL、文件名等标识符必须原样保留（改错一位工具调用即失效）。
- 隔离优于压缩：让大体积中间信息根本不进主上下文（子 Agent 隔离），比事后有损压缩更优。

## 类比（帮助理解）
- 压缩像写周报：把一周几十封邮件提炼成一页要点——既省纸（token），又让人一眼抓住重点，而不是在废纸堆里翻。

## 设计时怎么用（反推思维）
> 做多步搜索 Agent 时，我会在上下文接近 80% 阈值时做"上下文感知压缩"，把搜索结果压成带查询意图的摘要，并保留 URL 引用与关键标识符。
