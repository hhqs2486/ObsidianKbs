# 检索增强上下文

## 一句话定义
> 检索增强上下文（Retrieval-Augmented Context）是把"检索增强生成（RAG）"用到上下文管理上：在把上下文送进模型前，先检索相关外部知识注入，让模型基于最新/私有的资料做决策。

## 它解决什么问题 / 为什么存在
- 预训练有数据截止、且不含私有领域知识。Agent 需要"训练数据截止后的信息或私有知识"——这些不能靠模型参数，只能靠运行时检索注入上下文。
- 本质是把"外部知识"变成模型此刻能"看到"的上下文的一部分。

## 核心原理（大二电子信息工程专业学生能懂）
- RAG = Retrieval-Augmented Generation：先检索相关文档/片段，再让模型据此生成回答。在 Agent 中，检索结果动态注入到**用户消息**或轨迹里（第一章：用户消息可含通过 RAG 动态检索的外部知识）。
- 思路延伸：状态栏一节指出，把算好的结论显式写进上下文，"相当于把检索增强生成（RAG）内置进了每一次前向传播"——即上下文本身就是被检索/提炼过的高密度知识。
- 与上下文工程的配合：检索来的知识要控制信息密度、避免稀释注意力；可结合压缩与状态栏。
- 进阶形态是**智能体化 RAG（Agentic RAG）**：让 Agent 自主决定何时检索、检索什么（详见[[RAG]]与知识库章节）。

## 关键参数 / 易错点
- 检索结果若不加筛选地堆进上下文，会稀释注意力、引发上下文腐化——需做相关性过滤与摘要。
- 检索质量依赖嵌入与向量库（见[[嵌入 Embedding]]、[[向量数据库]]）；错误的检索 = 喂错上下文 = 错误决策。
- 注入位置：放在 user 消息或轨迹，属动态部分，不影响静态前缀缓存。

## 类比（帮助理解）
- 检索增强上下文像写报告前先去资料室调取相关档案，把关键页摊在桌上——而不是只靠脑中记忆硬写。

## 设计时怎么用（反推思维）
> 做企业问答 Agent 时，我会先把用户问题向量化检索知识库，取 Top-K 片段注入上下文，再做压缩提炼，避免把整库塞进窗口。

## 典型应用 / 我在哪见过
- 用户消息通过 RAG 注入外部知识（第1章）；Agent 状态栏"把 RAG 内置进前向传播"（第2章）；第三章知识库与 Agentic RAG。
