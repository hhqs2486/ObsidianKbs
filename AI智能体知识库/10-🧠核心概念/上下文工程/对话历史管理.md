# 对话历史管理

## 一句话定义
> 对话历史管理（Conversation History Management）是对 Agent 的"轨迹（trajectory）"——即随交互不断增长的消息历史——进行组织、保留与精简的工程实践，是上下文工程的日常核心。

## 它解决什么问题 / 为什么存在
- 每次 LLM 调用都是无状态的：框架必须每轮把完整历史（user/assistant/tool 消息）重新发回模型。历史既宝贵（含决策依据）又危险（膨胀、稀释注意力、破坏缓存）。
- 管理得当，Agent 才"不健忘、不重复、不爆窗"。

## 核心原理（大二电子信息工程专业学生能懂）
- **结构**：上下文 = 静态前缀（System Prompt + 工具定义）+ 轨迹（用户消息 + 模型回复含 reasoning/tool_calls/content + 工具结果）。每轮 LLM 看到完整轨迹。
- **滑动窗口的陷阱**（实验 2-3）：只保留最近几条消息 → ① 破坏前缀一致性使 KV Cache 失效；② 可能丢失关键工具结果，导致 Agent 反复执行同一工具调用（无限循环）。
- **管理手段**：
  - 分层**上下文压缩**（摘要替换 tool results，接近阈值批量压）；
  - **Agent 状态栏**：把隐式状态显式化，省去反复从原文检索；
  - **子 Agent 隔离**：让大体积探索不进主上下文；
  - 保留优先级：架构决策/验证状态/标识符不得丢。

## 关键参数 / 易错点
- 消融实验（1-1）：缺历史 → 重复操作（像失忆重做已完成步骤）；缺工具结果 → 盲目循环。
- 不要为省 token 用滑动窗口砍历史——优先用隔离/压缩。
- 状态栏一旦写错会原样传进答案（模型无条件相信），需把其准确率当生产指标盯。

## 类比（帮助理解）
- 对话历史像项目的工作日志：既要完整（知道干过啥、为啥这么干），又不能堆成垃圾山——定期归档、关键节点记仪表盘、大排查交给旁听的同事（子 Agent）。

## 设计时怎么用（反推思维）
> 做长程 Agent 时，我不用滑动窗口砍历史，而是保留完整轨迹 + 接近阈值时分层压缩 + 状态栏提炼状态 + 大搜索委派子 Agent 隔离。
