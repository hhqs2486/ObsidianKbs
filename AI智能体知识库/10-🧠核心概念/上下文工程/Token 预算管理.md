# Token 预算管理

## 一句话定义
> Token 预算管理是把"上下文窗口"当成一块有限预算来分配的工程方法：在系统提示、历史对话、工具结果、规划/思考之间划配额，确保关键内容进得去、无关内容不挤占注意力。

## 它解决什么问题 / 为什么存在
- 上下文窗口不是无限钱袋。生产里三类坑：溢出（长文档/多轮/工具轨迹超窗，截断后内容全没）、稀释（窗内塞太多无关内容，注意力被摊薄，前沿模型在长输入上也退化）、不持久（新会话空窗）。
- "窗口越大越好"是错觉——Mem0 实测 128k 窗口基线仍漏长视野事实，而 4k 窗口 + 外部记忆的 Agent 反而抓得住。所以要把窗口当预算精打细算：什么占多少、超了怎么挤、不要的全清掉。

## 核心原理（大二能懂的水平）
- 核心心法是 Anthropic 说的"把上下文当预算（treat context as a budget）"——就像嵌入式系统的 RAM：总量固定，每一块用途要规划。
- 一个 Agent 的上下文预算通常被切成几块（按优先级分配配额）：
  - 系统提示 / 指令（固定底仓，定义角色与规则）
  - 核心记忆分区（固定钉在 prompt 边的 persistent 段，如用户偏好、项目约定）
  - 近期对话历史（工作记忆，近期轮次）
  - 工具/检索结果（常是最大的变量，最容易爆）
  - 规划与思考区（如 CoT、子目标、待办）
- 管理手段（与上下文工程其他概念配合）：
  - 设主上下文 token 上限，超了就**压缩最旧消息**成摘要（见 [[上下文压缩]]）。
  - 工具结果做截断/摘要/只取必要字段，避免把整页 HTML 塞进来。
  - 用外部存储做"换页"（见 [[Agent 记忆]]）：不常访问的放外面，按需检索。
  - 长文档/长上下文用分块与检索而非整段塞入（见 [[长上下文]]）。
- 工程上常做一个"context-budget"可视化：实时看各块占比，拖动阈值观察何时溢出、何时稀释。

## 关键参数 / 易错点
- 要给每类内容设配额上限，尤其工具结果——它是最易暴涨的变量（一页网页、一份大日志就几千 token）。
- 压缩要有策略：无差别丢最旧消息可能丢关键约束；更好的做法是摘要旧消息并保留"核心分区"不动。
- 配额不是越大越好：把窗口填满无关内容会稀释注意力，反而降质——这是预算管理的反比陷阱。
- 跨会话不持久：预算只管单次窗口，长期事实要靠外部记忆，不是无限堆窗口。
- 注意和"成本预算"区分：这里是**上下文窗口内的 token 配额**（容量），而 `max_budget_usd` 是花钱上限（见 [[Agent 权限系统]] 的预算护栏）。

## 类比（帮助理解）
- 像嵌入式开发的 RAM 分配：bootloader 占一块、堆栈占一块、缓冲区占一块，总量固定；缓冲区（工具结果）最容易爆，要设上限和回收策略。
- 也像你写报告时一页纸字数有限：系统指令是页眉、核心记忆是便签、工具结果是正文素材——素材太多就得先摘要再贴，别把整本参考书糊上去。

## 设计时怎么用（反推思维）
> 做 Agent 的上下文设计时，我会先做 token 预算表：系统提示/核心记忆给固定底仓，对话历史设滚动窗口，工具结果设单条与总量上限并默认摘要，规划区单独留白；超窗时优先 [[上下文压缩]] 旧消息而非砍核心约束，并把长文档走分块检索而非整段入窗（配合 [[长上下文]] 与 [[上下文窗口]] 认知）。

## 典型应用 / 我在哪见过
- MemGPT/Letta 的 main-context 有固定 token 上限，超限自动 compact 最旧消息；archival 存储负责"换页"。
- 生产 Agent（Claude Agent SDK、OpenAI Assistants）用 threads + 分层记忆实现预算分配；Anthropic "Effective context engineering" 明确把上下文当预算。
