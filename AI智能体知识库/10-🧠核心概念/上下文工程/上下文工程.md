# 上下文工程

## 一句话定义
> 上下文工程（Context Engineering）是系统性地设计、组织和提供 Agent 在每个决策点能看到的全部信息的技术——它决定 Agent "能基于什么做决策"，是 Harness 中"上下文与工具"层面的核心实现。

## 它解决什么问题 / 为什么存在
- 模型能力是通用的，但执行具体任务需要背景知识（架构、业务规则、内部约定）。上下文质量才是 Agent 能力的真正上限——中等模型 + 精心上下文，常胜顶级模型 + 信息匮乏。
- 它不只是"往 prompt 里塞更多"，更是组织问题：把团队隐性知识结构化、可检索地送到模型面前。

## 核心原理（大二电子信息工程专业学生能懂）
- 上下文 = 静态前缀（System Prompt + 工具定义）+ 轨迹（消息历史）。工程围绕这个结构展开五层技术：
  1. **提示工程**：写好 System Prompt（语气/结构化/流程驱动/业务规则细化）。
  2. **KV Cache / Prompt 缓存友好布局**：静态前缀不变，动态信息追加末尾。
  3. **Agent Skills**：按需渐进式披露专业知识，避免提示词无限膨胀。
  4. **Agent 状态栏**：在上下文末尾注入结构化元信息（进度、环境、计数），弥补模型不会主动归纳状态。
  5. **上下文压缩**：对话历史膨胀时智能精简（摘要/隔离）。
- 还有安全面：提示注入防御——外部内容可能劫持上下文。

## 关键参数 / 易错点
- 前缀不变性约束：改了 System Prompt 一个字节，KV Cache 全失效，首 token 延迟飙升。
- 注意力被稀释：无关信息过多会让模型找不到关键信息（上下文腐化）。
- 工程范式演进：提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程。

## 类比（帮助理解）
- 上下文工程像给永远的新员工建一套"信息供给系统"：员工手册（静态）、实时仪表盘（状态栏）、按需取用的资料库（Skills）、定期归档（压缩）。

## 设计时怎么用（反推思维）
> 做生产 Agent 时，我会把上下文工程当头等大事：稳定静态前缀以命中缓存，用 Skills 按需加载知识，用状态栏显式给状态，接近窗口阈值时分层压缩。
