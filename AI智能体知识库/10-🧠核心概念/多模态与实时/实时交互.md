# 实时交互

## 一句话定义
> 实时交互（Real-Time Interaction）指 Agent 在输入持续流动、输出必须在严格时间预算内给出的条件下，与用户/环境进行低延迟的多模态交互——语音对话、GUI 操作、机器人控制都受这一约束驱动。

## 它解决什么问题 / 为什么存在
- 语音停顿超两秒就让人焦躁，机器人控制的毫秒级抖动可能导致碰撞——延迟和多模态是卡住三个场景的共性难题。
- 这两个约束把架构推向同一方向：从串行流水线（一环节做完才交下一棒）走向端到端模型（统一模型直接从输入到输出）。

## 核心原理（大二电子信息工程专业学生能懂）
- 延迟来源（以语音级联为例）：VAD（500–800ms）+ ASR（50–200ms）+ LLM（100–500ms）+ TTS（200–500ms）≈ 0.9–2.3s，仅空载理想值；生产环境还有排队延迟：总延迟 ≈ 空载延迟 × 1/(1−利用率)，利用率 0.8 时变成 5 倍。
- 全链路流式化：让 ASR 边听边转、LLM 按句切分、TTS 句级流式合成，三级像流水线上同时开工的工位，端到端延迟压到 600–800ms。
- 思考架构取舍（实时响应 vs 深度思考）：
  - 方案一：快慢并行，快思考应付、慢思考回答（易自相矛盾）。
  - 方案二：快思考交互、慢思考当「军师」经 Agent 状态栏给建议（GPT-Live 委派、Pine AI）。
  - 方案三：把思考内化进端到端模型，实现「边想边说」（Step-Audio R1 的 MPS 双脑架构）。
- 潜空间桥（Latent Bridge）：快慢之间不只传文字，可传「潜 token」，绕过「想法→文字→再理解」的往返（游戏场景 +26%~+82%）。

## 关键参数 / 易错点
- 关键指标：首 token 延迟 TTFT、首包延迟、利用率 ρ（ρ→1 延迟→∞）。
- 实用边界：快慢协作有无用，取决于瓶颈在「想不想得到」还是「来不来得及反应」——慢思考本来就比快反应强时桥才帮得上（相关性 r≈0.9）。
- 易错点：单纯堆算力和模块优化，仍难消除串行的累积延迟；Computer Use 实时性至今无系统性解法，靠快慢解耦「藏起来」。

## 类比（帮助理解）
- 像餐厅排队：厨房越忙等餐越久，且非线性飙升（利用率 0.8 时等 5 倍）；也像人边想边说——想一段说一段，而不是想完整句再一口气背出。

## 设计时怎么用（反推思维）
> 做语音客服 Agent 时，我会用它能解决「用户等得烦躁才出声」——把 LLM/TTS 改成句级流式，并让后台强模型当军师，前台轻模型维持对话，深度思考不阻塞语音输出。

## 典型应用 / 我在哪见过
- 语音三代范式：级联 → 端到端全模态（Omni）→ 全双工（Moshi、GPT-Live）。
- Computer Use 用「边想边操作」快慢解耦把语音回应加快约 15 倍。
- 机器人双层架构（长程规划 + VLA 控制）同属快慢解耦。
