# 代码审查 Agent

## 一句话定义
> 代码审查 Agent 是对生成的或既有的代码进行批判性审视（可读性、性能、安全、风格、规范符合度）的智能体，可自我审查，也可作为独立子 Agent 审查他人/他 Agent 产出的代码。

## 它解决什么问题 / 为什么存在
- 即使所有测试通过，代码仍可能有安全漏洞、性能问题或风格违规。审查是把关交付质量的最后一道工序。
- 把"审查"与"生成"分离（提议者-审核者 / 制造者与验证者分离）能降低上下文干扰、提升发现问题的概率。

## 核心原理（大二电子信息工程专业学生能懂）
- 在 Coding Agent 流程（图5-2）中，测试通过后进入"审查与交付"：Agent 自我审视代码，或通过运行 Linter、调用专门的代码审查子 Agent（Sub-Agent）实现。
- 自我审查维度：可读性/注释、潜在性能问题、安全漏洞、项目代码风格与最佳实践。
- 多 Agent 协作范式：生成与审查解耦（与 PPT 生成的 Proposer-Reviewer 同源）——主 Agent 专注写代码，审查子 Agent 独立给出批准/否决或改进建议，避免"自己审自己"的盲区。
- 发现问题应回到修改阶段完善（⑤→④回退），而非直接交付缺陷代码。

## 关键参数 / 易错点
- 审查不能只跑 Linter：还需语义级的安全/逻辑检查。
- 审查子 Agent 用不同模型家族可降低同类错误（与[[LLM-as-Judge]]的多源评判同理）。
- 文档同步：架构层面变更需更新架构文档，过时文档比没有更糟。

## 类比（帮助理解）
- 像论文的"作者自校 + 独立审稿人"双轨：自己先看一遍，再请别人挑刺。
- 像工厂的质检部门：不与生产线合并，独立把关。

## 设计时怎么用（反推思维）
> 做代码交付系统时，我会让生成 Agent 写完后触发独立审查子 Agent，对安全/性能/风格给结构化反馈，不通过则回退修改。

## 典型应用 / 我在哪见过
- Claude Code 的自审+lint、代码审查 Sub-Agent、PR 自动审查、以及 PPT/视频生成中的 Proposer-Reviewer。
