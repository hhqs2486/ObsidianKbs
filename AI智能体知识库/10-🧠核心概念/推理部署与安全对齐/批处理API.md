# 批处理API

## 一句话定义
> 所有主流提供商都提供异步批处理 API，统一 50% 折扣 + ~24 小时周转。叠加 prompt 缓存后，夜间管线成本可降至同步未缓存的 ~10%。任何容忍 24 小时延迟的工作负载不用批处理等于白扔钱。

## 它解决什么问题 / 为什么存在
- 夜间报告生成管线——50,000 篇文档摘要 + 聚类 + 简报——同步运行 4 小时，$2000/晚；批处理 + 缓存 → $180/晚（~9%）
- 大模型推理价格一直降，但用量一直涨——批处理是省钱的三条杠杆中最简单的一条
- 组织惯性：团队默认"实时"即使实际 SLA 是"明早生成就行"

## 核心原理
- 三大批处理 API：**OpenAI**（JSONL + /v1/batches + 50% 折扣）、**Anthropic Message Batches**（JSONL + cache_control 支持 + 50% 折扣）、**Google Vertex Batch Prediction**（BigQuery/GCS + 50% 折扣）
- 语义是异步而非慢——"24 小时内返回"不是"24 小时后"。P50 典型 2-6 小时，因为提供商在 GPU 闲置高峰期调度你的批作业
- **叠加缓存**：共享系统 prompt → 第一个请求写缓存，后面 49999 个用 10 倍便宜输入价格。批处理 + 缓存 = 同步非缓存的 ~10%
- 工作负载三级分流：**交互式**（同步 + 缓存，TTFT 敏感）、**半交互式**（异步队列 + 回退）、**批处理**（夜间，总是批处理 + 缓存叠加）

## 关键参数
- **部分交互性陷阱**：某些功能看似交互但容忍 5-10 分钟延迟（如"刷新"按钮）。问题："24 小时对这个用户意味着什么？"
- **输出模式陷阱**：不同提供商的批输出格式不同（OpenAI JSONL vs Anthropic JSONL vs Vertex BigQuery），网关的"多提供商批处理"仍需适配代码

## 类比
- 批处理 API = 快递的"隔日达"——同样的服务，不赶时间就半价

## 设计时怎么用
> 新 LLM 工作负载进来先分类：交互式/半交互式/批处理。任何"明天之前"的 SLA = 一定是批处理。
