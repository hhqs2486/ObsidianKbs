# Agent 推理加速

## 一句话定义
> 面向 Agent 工作负载（多轮工具调用、长上下文、结构化输出）的推理优化集合：批处理、KV 缓存复用、工具调用并行、投机执行，让 Agent 跑得又快又省。

## 它解决什么问题 / 为什么存在
- Agent 不是"一次问答"，而是"系统提示 + 工具 schema + 检索上下文 + 历史 + 多轮工具调用"反复拼成的长流量。朴素逐请求串行服务下，重复 prefill、工具等待、串行调用把延迟和成本堆高。
- 普通聊天优化（只压 decode 延迟）不够：Agent 的瓶颈常在 prefill 重复、工具往返、以及"草稿模型是否跟得上 Agent 分布"。

## 核心原理（大二能懂的水平）
- **批处理（连续批处理打底）**：Agent 多用户并发时，用 [[vLLM 推理引擎]] 的连续批处理让 GPU 始终满载；同批次里不同序列处于各自输出的不同阶段，融成一次前向。前提是 [[PagedAttention与连续批处理]] 提供的细粒度 KV 块资源。
- **KV 缓存复用（前缀缓存）**：Agent 流量几乎总共享长前缀——系统提示、工具 schema、few-shot、检索头、对话历史。把前缀的 KV 存进基数树（RadixAttention 思路），新请求只 prefill 不同的后缀。RAG/前缀重负载可达 6.4x；关键是**提示模板顺序固定**（系统/工具/上下文在前，用户问题在后），否则共享前缀对树而言是两个不同序列，命中率从 74% 掉到 7%。这与 [[Prompt 缓存]] 同源。
- **工具调用并行**：Agent 一轮里常要并发调多个独立工具（查库、搜网页、算数）。用 [[并行工具调用]] 让一次模型输出触发多个工具并行执行，再汇总，省掉串行等待。前提是被调工具彼此无依赖、且工具描述清晰（见 [[函数调用 Function Calling]]）。
- **投机执行**：Agent 输出高度结构化（JSON、固定模板），草稿模型更易猜中下一步，alpha 高，[[投机解码]] 收益比闲聊更稳。但要用真实 Agent 流量测 alpha，避免高并发负优化。
- **解聚合 + 前缀路由（进阶）**：prefill/decode 拆池，KV 感知路由把请求送到已持其前缀的 decode 节点，复用与扩缩容（见 [[GPU 自动扩缩容]]）叠加。

## 关键参数 / 易错点
- **提示模板顺序 = 缓存命中率**：动态内容插进前缀会毁掉 RadixAttention 共享，必须"不可变内容在前、用户问题在后"。
- **工具并行的前提是独立性**：有依赖链的工具不能并行，强行并行会拿到错序/过期结果。
- **Agent 流量上测 alpha 再开投机**：Agent 模板规整 alpha 高，但仍要在真实分布验证，且盯 P99。
- **KV 缓存要整体预算**：前缀复用省的是 prefill，但 decode 阶段 KV 随多轮历史增长，仍受显存约束（见 [[模型量化 Quantization]] 的 KV 账）。

## 类比（帮助理解）
- 像餐厅服务员团队：批处理=一次端多桌的菜（连续批处理）；KV 复用=常点的招牌菜预炒好、只现做每桌不同的部分（前缀缓存）；工具并行=让配菜、煮汤、烤串同时开火而非依次来（并行工具调用）；投机执行=熟客点单时服务员先按惯例备好、经理一次性确认（投机解码）。

## 设计时怎么用（反推思维）
> 给一个多工具 Agent 做推理加速时，我会先用它能解决"多轮+工具带来的延迟与成本"——先固定提示模板顺序以吃满前缀缓存（接 [[Prompt 缓存]]），用 [[vLLM 推理引擎]] 连续批处理扛并发，把互相独立的工具走 [[并行工具调用]] 并行执行；若 Agent 输出高度结构化、真实流量 alpha 高，再开 [[投机解码]] 并复测 P99；长上下文多轮下按 [[模型量化 Quantization]] 整体算 KV 显存，必要时用 [[GPU 自动扩缩容]] 按队列深度弹性应对突发。

## 典型应用 / 我在哪见过
- Coding Agent、RAG Agent、多工具编排 Agent 的生产服务。
- SGLang 在 Agent/RAG 前缀重负载上靠 RadixAttention 拿 29%–6.4x 优势；vLLM 也加了前缀缓存与缓存感知路由。
