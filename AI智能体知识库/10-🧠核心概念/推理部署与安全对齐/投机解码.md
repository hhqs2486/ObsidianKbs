# 投机解码

## 一句话定义
> 让一个"小草稿模型"先一口气猜出接下来 K 个 token，再让"大模型"一次性验证：猜对的免费通过，从而把逐 token 的自回归延迟压下去。

## 它解决什么问题 / 为什么存在
- decode 是内存带宽瓶颈：在 H100 上跑 Llama 3.3 70B FP8，每生成一个 token 要读约 140 GB/s 的权重却只吐一个 token，GPU 算力几乎闲置。瓶颈在"读权重"不在"算"。
- 自回归天生串行："生成第 N+1 个 token 必须等第 N 个完成"，延迟下不去。投机解码利用"顺带多读一点权重、一次验证 K 个"来摊薄每次读取成本。

## 核心原理（大二能懂的水平）
- **草稿 + 验证范式**：草稿模型（draft）便宜，并行提出 K 个候选 token；目标大模型（target）用一个前向传播把这 K 个一起验证，按概率接受前缀。被接受的 token 实际上"免费"——摊进本来就要做的一次前向里。
- **接受率 alpha**：草稿提出的 token 里被大模型接受的比例，是唯一真正重要的指标。预期加速 ≈ (1 + K·alpha) / (1 + 验证开销)。例：K=5、alpha=0.7 → (1+3.5)/1.1 ≈ 4.1x；真实多在 2–3x，因为生产流量 alpha 没那么高、batch 大时开销上涨。
- **三代演进**：
  - 经典草稿模型：同族小模型（如 1B 起草 70B），alpha 仅 0.3–0.5，分布偏离大。
  - EAGLE-1/2（2024–2025）：在目标模型隐藏状态上训练"草稿头"，alpha 升到 0.5–0.7，EAGLE-2 引入树状草稿。
  - **EAGLE-3（2025–2026 生产级）**：草稿头在目标模型**多层**状态上训练，对齐更好，通用闲聊 alpha 达 0.6–0.8。

## 关键参数 / 易错点
- **alpha 低于 ~0.55 就是负优化**：被拒的草稿要触发"二次目标前向 + 重roll"，在高并发（如 256）时内存带宽优势被抹平。别看平均，看生产流量分布上的 alpha。
- **opt-in，不是默认**：vLLM 2026 里必须显式设 `speculative_config`，否则无加速。盲目打开却不测 alpha 是生产反模式，尾延迟可能变糟。
- **P99 尾延迟陷阱**：平均 ITL 下降，但被拒草稿触发"草稿+验证失败+重roll"两趟串行，P99 ITL 可能恶化。盯 P99 而非 P50。
- **vLLM v0.18.0 兼容坑**：`--enable-chunked-prefill` + 草稿模型投机解码 + 旧调度不编译；唯一兼容 chunked prefill 的是 V1 的 N-gram GPU 投机解码。2026 正确姿势常是"EAGLE-3 不开 chunked prefill"。
- 领域流量（代码/医疗/法律）用通用数据训的草稿头 alpha 掉到 0.4–0.6，需训一个领域草稿头才能回血。

## 类比（帮助理解）
- 像秘书先起草一整段（草稿），老板（大模型）一次性审阅盖章：对的段落直接过，只错的那个重写在后。秘书越懂老板口味（alpha 高），整体越快；秘书乱写（alpha 低），老板反而更累。

## 设计时怎么用（反推思维）
> 给我的 Agent 加低延迟生成时，我会先用它能解决"自回归首 token / 逐 token 太慢"——先上线裸目标模型测基线 TTFT/ITL/吞吐，再用 vLLM `speculative_config` 开 EAGLE-3，跑真实流量看 `spec_decode_metrics.accepted_tokens` 算 alpha；若 alpha<0.55 就关掉或训领域草稿头，并复测 P99 ITL 没变差才保留。短输出（<50 token）或 batch-1 离线场景直接不用。

## 典型应用 / 我在哪见过
- Google 在 AI Overviews（2025）用投机解码：同质量、更快响应。
- vLLM V1 把 `speculative_config` 作为正式接口；SGLang 在前缀重的负载推荐 EAGLE-3。
