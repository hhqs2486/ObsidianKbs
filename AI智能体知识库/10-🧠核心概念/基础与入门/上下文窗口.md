# 上下文窗口

## 一句话定义
> 上下文窗口（Context Window）是模型单次推理能处理的 token 数量上限，决定了 Agent 一次"能看到"的信息总量。

## 它解决什么问题 / 为什么存在
- 模型算力有限，不能无限长输入。窗口大小直接限制任务能承载的上下文量，过小会撑爆、被迫中断。
- 它框定了上下文工程的所有取舍：什么该留、什么该压缩、什么该隔离。

## 核心原理（大二电子信息工程专业学生能懂）
- 窗口由五部分填占：System Prompt + 工具定义（静态前缀）+ 对话历史/轨迹（动态增长）+ 本轮生成。
- 所有内容序列化为 token 流交给 Transformer；窗口以 token 计（非字符）。
- 典型窗口大小：Qwen3 = 32K、Claude = 200K、Gemini = 2M；Kimi K3 达 100 万 token。
- 窗口用满会"溢出"（装不下，任务失败）；即便没满，过长也会"腐化"（找不准关键信息）。

## 关键参数 / 易错点
- 窗口 ≠ 能力：更大的窗口不保证更好用——长上下文下检索精度下降（"大海捞针"问题、上下文腐化）。
- 工具结果动辄数万字符，几轮就可能撑满；需要[[上下文压缩]]、[[对话历史管理]]、子 Agent 隔离来控制。
- KV Cache 随窗口线性增长，长窗口解码更慢、显存/带宽成瓶颈。

## 类比（帮助理解）
- 上下文窗口像你办公桌的大小：桌子越大能摊开越多资料，但桌子太大反而找不到东西（腐化），而且收拾更慢。

## 设计时怎么用（反推思维）
> 做长程 Agent 时，我会监控 token 占用，接近窗口 80% 即触发压缩或子 Agent 隔离，避免溢出中断，并保持信息密度。
