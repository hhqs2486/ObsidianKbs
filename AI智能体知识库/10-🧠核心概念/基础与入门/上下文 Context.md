# 上下文 Context

## 一句话定义
> 上下文（Context）是 Agent 在每个决策点能"看到"的全部信息——相当于 Agent 的"眼睛"，决定它能基于什么做决策。

## 它解决什么问题 / 为什么存在
- 模型能力是通用的，但执行具体任务需要背景信息（产品架构、业务规则、内部约定）。上下文质量才是 Agent 能力的真正上限。
- "模型和 Agent 一样，最重要的是 Context"——决定上限的不是参数量，而是每个决策点能获得多少、多精准的上下文。

## 核心原理（大二电子信息工程专业学生能懂）
- 从 API 视角，每次调用 LLM 的上下文由五部分构成：
  1. **系统提示词（System Prompt）**：开发者写，全程不变，Agent 的"岗位说明书"。
  2. **工具定义（Tool Definitions）**：声明可用工具的名称、功能、参数。
  3. **用户消息（User Messages）**：用户输入，可能含 RAG 检索注入的外部知识。
  4. **模型回复（Assistant Messages）**：含思考过程（reasoning）、文本（content）、工具调用（tool_calls）。
  5. **工具执行结果（Tool Results）**：工具返回，是下一步思考的直接依据。
- 结构：**上下文 = 静态前缀（系统提示词 + 工具定义）+ 轨迹（用户消息 + 模型回复 + 工具结果，随交互增长）**。
- 前两项是静态前缀（生产框架中也可按需动态加载），后三项是动态消息历史。

## 关键参数 / 易错点
- 消融实验表明五组件缺一不可：缺工具定义→无法行动；缺工具结果→盲目循环；缺思考过程→决策不连贯；缺历史→重复操作。
- 上下文决定了 Agent 能看到什么，它只能基于看到的信息决策——像蒙眼无法判断。
- "AI 原生团队"本质是一场文档化运动：把隐性知识结构化、可检索地送给模型。

## 类比（帮助理解）
- 上下文像你桌上摊开的所有资料：任务说明、参考手册、沟通记录、最新数据——Agent 的视野就是这叠资料。

## 设计时怎么用（反推思维）
> 做企业 Agent 时，我会把产品架构、业务规则、用户记忆系统性地组织成上下文，并区分"静态前缀（稳定、利于缓存）"与"动态轨迹（可压缩）"。

## 典型应用 / 我在哪见过
- 每次 LLM API 调用的 messages 列表；Coding Agent 的实时代码/流程/环境三类上下文。
