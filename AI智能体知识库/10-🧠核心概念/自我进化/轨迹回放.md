# 轨迹回放

## 一句话定义
> 轨迹回放（Trajectory Replay / Workflow Recording & Replay）指 Agent 首次手动完成重复性操作时把步骤「录」下来，之后面对同类任务只需点「回放」即可自动重跑——把成功操作序列固化为可复用的参数化工作流。

## 它解决什么问题 / 为什么存在
- 浏览器里大量重复操作（发报告邮件、查某网站信息）核心流程固定，但每次参数不同。让 Agent 每次都用昂贵多模态大模型「重新发现」流程，是极大的资源浪费。
- 本质：只依赖上下文学习、没把成功经验外部化为可复用工具，导致每次从头摸索。

## 核心原理（大二电子信息工程专业学生能懂）
- 类比 Excel 的「宏录制」：第一次手动操作时记录步骤，以后点「回放」自动重复。
- 学习阶段（Learning Phase）：Agent 首次通过「观察-思考-行动」循环完成操作。网页是 DOM 树（每个按钮、输入框是节点），用 XPath（如 /html/body/div[2]/button[1]）指向具体节点。系统把操作录成结构化步骤：操作类型（点击/输入）、目标元素 XPath、参数、执行后验证信息（URL 是否变、预期元素是否出现）。成功后 LLM 生成语义标签与描述，与步骤序列一起存入知识库，形成参数化「工作流」。
- 回放阶段（Replay Phase）：新任务到达，结合语义相似度（嵌入向量）+ 关键要素检查匹配已有工作流。匹配成功则按步骤高速执行：用 Playwright 的等待机制确保元素加载；参数化模板（「在收件人字段输入{{email}}」）通过轻量 LLM 从当前指令提取实际参数，无需完整视觉思考。
- 失效回退：若某步失败（找不到元素、超时），说明网页结构可能已变，标记工作流「可能过时」，回退到学习模式重新生成替换旧的。

## 关键参数 / 易错点
- 两个最脆弱环节：①何时敢信回放——更稳的做法是把成功序列编译成带「验证谓词」的状态机（回放每步前先核对实时屏幕「先看清、再动手」）；②别把坏程序存进去——编译完立即重置环境从头回放一遍，用评判器确认「这次真做成了」才准入库（存前验证闸门）。
- 命中缓存的重复任务可快 8.5–13 倍，LLM 调用成本大幅下降、成功率更稳定。
- 回放时一次模型调用都不需要；命中缓存的重复任务能快上 8.5–13 倍。

## 类比（帮助理解）
- 像用 Excel 录宏：录一次「发邮件」的操作，以后换收件人和主题点一下就自动发出；也像 Voyager 在 Minecraft 里把探索成功存进技能库，下次检索复用。

## 设计时怎么用（反推思维）
> 做浏览器自动化 Agent 时，我会用它能解决「每天重复给不同客户发同样格式的报告邮件」——第一次录制操作步骤并参数化，之后只传新收件人和内容即可高速回放，无需每次重新视觉推理。

## 典型应用 / 我在哪见过
- browser-use-rpa 项目：Gmail 发邮件的录制-回放，模拟网页改版验证失效回退。
- Voyager（NVIDIA）把成功动作序列存入技能库，是同一思路在开放世界的落地。
- PreAct（Li, 2026）把成功轨迹编译成带验证谓词的状态机 + 存前验证闸门。
