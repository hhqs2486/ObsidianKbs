# 知识库

## 一句话定义
> 知识库（Knowledge Base）是面向所有用户共享的集体知识存储——如行业法规、公司内部流程、某技术领域的专业文档，让 Agent 成为“领域专家”。

## 它解决什么问题 / 为什么存在
- 大语言模型 LLM 的训练数据有截止日期，且不包含你的私有/内部知识。
- 知识库让 Agent 能利用训练时没见过的、可随时更新的外部知识，而不必重新训练模型。
- 它与 [[用户记忆]] 是同一问题的两个尺度：一个关注个体，一个关注群体；两者共用 [[RAG]]、向量检索等底层技术，也面临信息冲突、知识过期、检索不准等共同麻烦。

## 核心原理（大二电子信息工程专业学生能懂）
- 知识库的核心技术是 [[RAG]]（检索增强生成）：把外部知识先切块、转成向量存进 [[向量数据库]]，查询时检索相关片段注入上下文，再由 LLM 生成答案。
- 知识库不是建好就一劳永逸：它要治理——知识会过期、内容会失效、且被多用户共享。
  - 增量更新：选支持增量插入的索引（如 HNSW）而非需全量重建的（如 ANNOY）。
  - 失效检测：给分块加版本号/生效时间，检索时过滤已废止内容。
  - 权限与租户隔离：检索必须按调用者权限过滤，防止越权文档进入某人上下文。

## 关键参数 / 易错点
- 知识组织方式影响检索上限：扁平分块（简单但丢结构）、结构化索引（[[知识图谱]] / RAPTOR 树）、文件系统范式（OpenViking 的 L0/L1/L2 三层按需加载）。
- 易错点：把原始文档直接平铺进库——“字典随机词条式”检索无法回答需要归纳/跨文档关联的问题（如“比例多少”“哪些职业符合规则”）。

## 类比（帮助理解）
- 像一个公司共享的资料室：每个人都能查，但资料室要定期更新、作废旧版、并且 A 部门不能看到 B 部门的机密文件。

## 设计时怎么用（反推思维）
> 做企业客服系统时，我会把内部政策文档建成带版本和权限过滤的知识库，配合 RAG，让 Agent 回答“退款流程”时引用最新且当前用户可见的条款。

## 典型应用 / 我在哪见过
- 维基百科式问答、公司退款/政策库、司法判例库、技术手册检索。
- 组织范式：RAPTOR（树状层次）、GraphRAG（实体关系图）、OpenViking 文件系统范式、[[智能体化 RAG]]（Agent 主导迭代检索）。
