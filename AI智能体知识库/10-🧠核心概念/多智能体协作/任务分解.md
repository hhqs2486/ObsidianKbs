# 任务分解

## 一句话定义
> 任务分解（Task Decomposition）指把复杂任务拆成可分配、可并行、有清晰依赖关系的子任务，并决定调度顺序与粒度——它是编排（[[编排 Orchestration]]）里 Manager 最关键的职责，也决定系统成败。

## 它解决什么问题 / 为什么存在
- 任务太复杂、子任务太多或有复杂依赖时，单 Agent 或简单对等协作无力应对，需先「拆得对」才能「做得好」。
- 分解质量直接决定下游：规划者一旦拆错，所有执行者都建立在错误前提上。

## 核心原理（大二电子信息工程专业学生能懂）
- 管理者模式下，Manager 先把任务理解→分解为子任务→选择 Agent 执行→跟踪进度→异常处理→综合结果。每个专门 Agent 被建模为 Manager 可调用的工具。
- 规划是关键瓶颈（Plan-and-Act 实证）：WebArena-Lite 上 Planner 规划质量足够高时，即便 Executor 简单也能 54% 成功；Planner 分解错则全盘皆输。启示：最强模型与最精心提示词优先给规划者。
- 预算感知分解：给子任务动态分配步骤预算（简单少给、复杂多给），并引导子 Agent 先规划→实现→测试→改进，而非一头扎进去。对应 BAVT：随剩余预算减少，从「广撒网」切到「深挖掘」。
- 粒度：分解粒度需适中——太粗单 Agent 撑不住，太细协调开销爆炸；同时需理顺依赖顺序（如 MetaGPT 的模块依赖顺序）。

## 关键参数 / 易错点
- 依赖关系：子任务有先后依赖→顺序协调；可并行→并行协调（消息总线）。
- 移交包内容（不共享上下文时）：任务描述+已确认事实约束+结构化产物引用（文件路径而非内容），刻意不传全量轨迹（试错过程是噪声）。
- 易错点：平均分配算力给所有 Agent——规划者才该最强；以及把任务拆太碎导致协调成本超过执行收益。

## 类比（帮助理解）
- 像项目经理把「做一桌菜」拆成洗切炒摆、按依赖排程（先洗再切再炒），并给每道菜配厨师；也像把大作业拆成可并行的小模块分给组员。

## 设计时怎么用（反推思维）
> 做长程软件任务时，我会用它能解决「Executor 写得飞快但方向错了」——投入最强模型做 Planner 把任务拆对、定好依赖与预算，Executor 按分解结果执行，失败也只在局部。

## 典型应用 / 我在哪见过
- 实验10-3 书籍翻译：Manager 把任务拆为术语表/翻译/审校三类子任务。
- Plan-and-Act（2025）Planner-Executor 双 Agent，改善规划而非执行。
- MetaGPT 由 Project Manager 把设计拆成文件级任务清单与依赖顺序。
