# 编排 Orchestration

## 一句话定义
> 编排（Orchestration）是多智能体系统中「中心化协调」的拓扑模式：一个 Manager Agent 负责理解整体任务、拆解为子任务、调度专门 Agent、跟踪进度并处理异常，最后整合结果——相当于项目经理带专业工程师。

## 它解决什么问题 / 为什么存在
- 当任务涉及五个以上子任务、需要动态调度、或子任务间有复杂依赖时，对等协作力不从心，需要中心协调者。
- 把每个专门 Agent 建模为 Manager 可调用的「工具」，赋予系统良好可扩展性（新增能力只需注册 Agent，Manager 核心逻辑不改）与异构性（不同 Agent 可用不同模型/硬件）。

## 核心原理（大二电子信息工程专业学生能懂）
- 「Agent 互为工具」抽象：Manager 的工具集里不仅有 search/write_file，还有 call_agent_A 等；从 Manager 视角，调 Agent 与调普通工具无本质区别（发请求→获响应）。
- 两种协调形态：
  - 顺序协调：Manager 依次调用 A→B→C，控制流线性，适合子任务有清晰先后依赖。
  - 并行协调：多个 Agent 同时工作，靠消息总线（Message Bus）异步通信、互不阻塞，Manager 实时监控、级联终止。
- 上下文控制：子 Agent 应返回「结构化摘要而非全量轨迹」（结论、关键发现、产物文件路径、遇到的问题），Manager 只维护文件索引，上下文随子任务数缓慢线性增长而非爆炸。
- 资源分配：最强模型与最精心设计的提示词应优先给 Manager（规划者）——Planner 分解错，后续 Executor 再强也白费（Plan-and-Act 实证）。

## 关键参数 / 易错点
- Manager 是单点瓶颈与单点故障：必须理解所有子任务、准确传上下文，决策偏差影响全局。
- 需特别注意 Manager 提示词质量、上下文管理策略、任务分解粒度。
- 易错点：把最强资源平均分配给所有 Agent——规划者才应最强（与提议者-审核者「审查者要跟得上被审者」不同，那是另一回事）。

## 类比（帮助理解）
- 像项目经理拆任务派活：分活给不同工程师，工程师只把结果汇报回来，经理不亲自写每行代码，也不把每个人的草稿全存自己脑子里。

## 设计时怎么用（反推思维）
> 做书籍翻译系统时，我会用它能解决「单 Agent 上下文撑不住整本书且会术语前后不一致」——设 Manager 只维护文件索引，Glossary/Translation/Proofreading 各 Agent 在独立上下文工作，产物落共享文件系统。

## 典型应用 / 我在哪见过
- 实验10-3 书籍翻译 Agent（Manager + Glossary + Translation×N + Proofreading）。
- 实验10-6 并行网页搜索（Manager 动态起 10 个 Agent、级联终止，加速约 15×）。
- 灵台（Lingtai）产品化：主器灵=Manager，分神=短时并行子 Agent，分身=持久专门队友。
