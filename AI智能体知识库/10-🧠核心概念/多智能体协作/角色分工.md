# 角色分工

## 一句话定义
> 角色分工（Role Specialization）指在多智能体系统中，让不同 Agent 各持专门的系统提示词、工具集与关注点，分别承担需求分析、实现、审查、检索、写作等职责——每个「身份」独立打磨，阶段边界天然成为质量门控点。

## 它解决什么问题 / 为什么存在
- 若始终用同一套静态提示词，要么过于笼统缺乏针对性，要么把所有阶段指导塞一起导致冗长。
- 复杂任务中角色/职责随阶段显著变化，需要 Agent 在每个阶段以最合适的「身份」工作。

## 核心原理（大二电子信息工程专业学生能懂）
- 多阶段角色转换（共享上下文）：同一执行会话中动态切换系统提示词和工具集，对话历史与任务状态连续共享。如实验10-1：需求分析师（提问确认）→软件工程师（写代码）→代码审查员（run_linter/run_tests），靠 complete_requirements_analysis() 等工具触发转换。
- 跨领域角色转换（共享上下文 + transfer_to_agent）：如实验10-2 的 triage（前台分诊）+ research/coding/data_analysis/writing 五种角色，用 transfer_to_agent(target_role, reason) 移交，新角色继承完整历史。路由规则写在 triage 提示词里（查数据转 research、算指标转 data_analysis、成文转 writing）。
- 角色转换的本质收益：每个身份提示词/工具集独立打磨；阶段边界成为质量门控（不会跳过需求直接写代码、未经审查不交付）。

## 关键参数 / 易错点
- 共享上下文角色切换：上下文连续流动（信息零损耗），但上下文快速膨胀——需让当前 Agent 专注本职不被历史干扰。
- 循环切换问题：需避免 Agent 在角色间反复横跳（如 research↔data_analysis 死循环），要有终止/收尾机制。
- 易错点：共享上下文下若信息零损耗是硬约束则选共享；若累计上下文将超窗口 50%，应切到不共享 + 显式 handoff。

## 类比（帮助理解）
- 像公司里前台分诊把客人引到对应部门，部门间靠交接单传递；也像软件开发流水线上需求/开发/测试各司其职，每段都有专业工具和检查点。

## 设计时怎么用（反推思维）
> 做 Coding Agent 时，我会用它能解决「一个笼统提示词既要想需求又要写代码还要自查，容易顾此失彼」——按阶段切换「需求分析师/工程师/审查员」身份与工具集，并用阶段完成信号触发转换。
