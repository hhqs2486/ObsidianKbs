# MoE 混合专家

## 一句话定义
> MoE 把每个前馈层换成"一堆专家 + 一个路由器"：每个 token 只激活其中少数几个专家——总参数巨大、但每 token 算力只等于一个小稠密模型，用"稀疏"换"容量"。

## 它解决什么问题 / 为什么存在
- 稠密模型每个 token 都要跑过全部参数。想提升能力就得整体变大，算力和显存线性飙升。
- MoE 的洞见：不必每个 token 都用全部参数。给每层配 K 个专家 MLP，路由器按 token 挑 top-k（常见 top-2），只算被选中的几个——总参数量撑得很大（容量高），每 token 实际算力却很小（便宜）。

## 核心原理（大二能懂的水平）
- 路由：`router_logits = x·W_r`，取 top-k：`indices, weights = top_k(router_logits, k=2)`，输出是选中专家的加权和：
  `output = Σ_i weights[i] · expert[indices[i]](x)`。
- 经典配置：Mixtral 8×7B 有 8 个专家、每 token 激活 2 个，总参 47B 但每 token 只跑 13B；DeepSeek-V3 总参 671B、每 token 激活 37B（256 专家、top-8）。
- 与稠密模型对比：同一算力预算下，MoE 能塞更多总参数 → 更高容量/质量；但**专家权重整体必须驻留显存**，所以 serving 显存比同算力的稠密模型大。
- 负载均衡：若路由器总偏爱某几个专家，其余饿死、容量浪费。需 auxiliary loss 或 DeepSeek 的"无辅助损失负载均衡"来摊匀。
- 训练涉及 [[分布式训练]]：专家常分片到不同设备（专家并行），路由跨设备通信。

## 关键参数 / 易错点
- 专家数 K 与 top-k：k 太小容量受限，太大失去稀疏优势；Mixtral top-2/8，DeepSeek top-8/256（更"密"的稀疏，每 FLOP 容量更高）。
- 负载均衡：不做会塌成"只用 2 个专家"，其余变摆设——这是 MoE 训练首要坑。
- 显存：激活参数小但总参数大，部署显存压力大（要容纳全部专家）。
- 对齐难点：在后训练/[[微调]] 阶段训练路由器本身是独立研究方向。
- 易错：以为"MoE 每 token 算力 = 总参数"（错，是激活参数）；或忽略负载均衡导致容量浪费。

## 类比（帮助理解）
- 像一家医院：墙上挂着"全院 47 位专家"的牌子（总参数大），但每个病人（token）只被分诊台（路由器）送到最对口的两三位（top-2）那里看——医院容量大，单个病人花的诊疗时间却很少。
- 又像稀疏矩阵：大部分权重对当前 token 是 0（不激活），只有少数"非零块"参与计算。

## 设计时怎么用（反推思维）
> 我要冲"最高能力/每激活FLOP"又接受工程复杂度时，会选 MoE（DeepSeek-V3、Mixtral 思路）；若只有单卡、显存紧张、不想搞专家并行，就退回稠密模型（Llama 3）。反推：先看部署显存能否装下全部专家，再看路由 top-k 与负载均衡是否能摊匀——否则容量只是纸面数字。对齐阶段要额外关心路由器是否可训，见 [[微调]] 与 [[分布式训练]]。

## 典型应用 / 我在哪见过
- 开源顶尖模型：Mixtral 8×7B/8×22B、DeepSeek-V2/V3（MLA+MoE）、Qwen-MoE 系列。
- 用 MoE 把"总参数"与"每 token 激活算力"解耦，是 [[缩放定律 Scaling Law]] 在"有效算力"上的关键杠杆。
- 大规模在线服务：用专家并行分摊显存与计算。
