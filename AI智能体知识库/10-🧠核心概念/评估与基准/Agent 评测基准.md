# Agent 评测基准

## 一句话定义
> Agent 评测基准是"怎么给 Agent 打分"的方法与集合总览：核心维度是任务成功率、轨迹质量、工具调用正确性，并分静态基准 / 自定义离线 / 在线生产三层来做。

## 它解决什么问题 / 为什么存在
- Agent 能过 demo，却会在生产里以 demo 预测不到的方式翻车。单看榜单"哪个模型赢"回答不了：基准是否被污染？测的是不是你关心的？评测稳不稳？
- 评测不是最后一步，而是驱动所有其他决策的"外循环"——Anthropic 的建议就是：先用简单 prompt，用全面评测去优化，只在确实需要时才上多步 Agent 系统。

## 核心原理（大二能懂的水平）
- **三个评测层**（Anthropic / AIEFS 实践）：
  1. 静态基准：SWE-bench Verified（代码）、WebArena/OSWorld（浏览/桌面）、GAIA（通用工具）、BFCL（工具调用）。用于跨模型比较和回归门禁。注意污染：SWE-bench+ 发现 32.67% 的成功 patch 在题目里泄露了答案。
  2. 自定义离线评测：按你产品的形状造——LLM-as-Judge（用模型当裁判，需接地避免幻觉）、执行式（跑 patch 看测试）、轨迹式（动作序列对比 gold，OSWorld-Human 显示顶尖 Agent 用 1.4–2.7 倍步数）。
  3. 在线生产评测：会话回放、护栏触发告警、每步成本/延迟追踪（OTel span）。
- **核心评测维度**：
  - 任务成功率：最终目标达成没（常以执行结果而非文本判定）。
  - 轨迹质量：动作序列是否高效、合理（步数/gold、是否有冗余/死循环）。
  - 工具调用正确性：参数是否合法、未知工具是否拒掉、异常处理对不对。
- **怀疑清单（读基准声明时）**：哪个基准哪个 split？是否污染？基线比的是谁（单 LLM / 随机 / 旧版）？统计显著吗（N、p 值、置信区间）？任务多样吗？成本披露了吗（每任务 token、墙钟）？
- 什么基准都测不好：长程协调（按天计）、对抗韧性（有 Agent 被攻陷）、部署漂移、成本归一化表现。

## 关键参数 / 易错点
- 单数字执念：SWE-bench 50% 不如 P50/P75/P95 的成本+步数分布有用。
- 污染声明：报 SWE-bench 不提 Verified 或 SWE-bench+ 就是误导；"过了 Verified"不再是能力证据，SWE-bench Pro 才是当前门槛（前沿模型 Pro 仅 23–59% vs Verified 70%+）。
- LLM-as-Judge 不接地会自己幻觉——要用 CRITIC 式让裁判基于外部工具。
- 过拟合评测：为刷分优化会偏离生产价值，要轮换用例；flaky 用例要固定随机种子、快照状态。

## 类比（帮助理解）
- 像造车质检：静态基准=碰撞测试（统一标准横向比），自定义离线=你自己的路试（按真实路况），在线生产=上路后的遥测（每辆车回传故障）。三层缺一不可。
- 轨迹质量像"不仅看是否到达，还看路线绕没绕远"。

## 设计时怎么用（反推思维）
> 做 Agent 系统时，我会把评测当外循环：用 [[AgentBench]]/[[WebArena]]/[[OSWorld]] 等静态基准做回归门禁，再用贴近我产品的自定义离线评测（执行式 + 轨迹效率 + [[LLM-as-Judge]] 接地）补上它们不测的成本与安全；并给每条护栏/学到的规则都映射一个评测用例，在 CI 里卡回归。

## 典型应用 / 我在哪见过
- 2026 最佳实践：evals 与代码同仓、每次 PR 跑、用"相对 main 回归不超 5%"卡合并。
- 多 Agent 基准（MARBLE 测 star/chain/tree/graph 拓扑、COMMA 测多模态不对称信息）也属于此范畴，但本卡聚焦通用 Agent 评测方法。
