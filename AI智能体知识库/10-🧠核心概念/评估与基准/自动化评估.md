# 自动化评估

## 一句话定义
> 自动化评估是搭建可重复运行的测试环境，自动运行 Agent、按预设标准打分，无需每次人工干预——是评估体系的"考场基础设施"。

## 它解决什么问题 / 为什么存在
- 好的评估不只测成功场景，更要测边界和陷阱（如超出退款期能否拒绝、被虚假"已批准"话术误导能否识破）。这些需可重复、低成本地反复跑。
- 回答三个问题：评什么（任务定义+验证标准）、对谁评（如何模拟交互对象）、用什么标准打分。

## 核心原理（大二电子信息工程专业学生能懂）
- 评估环境五要素：数据集、环境状态、工具接口、评分标准（Rubric）、执行协议。
- 两种核心范式（图6-2）：
  - 工具调用型（Verifiers）：Agent 调预定义工具，验证基于可执行标准（测试是否通过、答案是否匹配），无需人工/LLM 评判。层次化环境：SingleTurnEnv（单轮）、ToolEnv（多轮工具循环）、StatefulToolEnv（有状态）、SandboxEnv（沙盒代码执行）。
  - 人机交互型（τ-bench）：用另一个 LLM 模拟用户，关键原则是渐进式信息透露（不一次性给全信息，逼 Agent 主动澄清）；双重验证（DB 状态 + 对话关键词）。改进版 τ²-bench 增加双控环境（用户也能操作共享环境）。
- 环境需处理状态依赖：工具效果取决于当前状态，失败应返回清晰错误而非简单失败标志，让 Agent 能学习修正。框架支持并行采样与轨迹缓存（保存观察-行动-奖励供回放）。

## 关键参数 / 易错点
- 工具接口应提供原子操作（查订单、改预订），而非高层抽象（"解决用户问题"），逼 Agent 自己规划。
- 真实性 vs 可控性：状态变化要符合业务逻辑，且每次可重置到相同初始状态。
- 评估环境可改造为后训练环境（仿真环境），但评估集题目须与训练数据严格隔离。

## 类比（帮助理解）
- 像驾考的自动评判系统：倒车入库是否压线由传感器（可执行验证）判定，无需考官目测。
- 像带陪练机器人的健身房：机器人按脚本逐步透露要求，考察你能否正确应对。

## 设计时怎么用（反推思维）
> 搭建评估时，我会为代码类任务用 Verifiers 做可执行验证，为人机对话类用 LLM 模拟用户+渐进式透露，并把轨迹完整缓存以便回放。

## 典型应用 / 我在哪见过
- Verifiers 框架、τ-bench / τ²-bench、SWE-Gym（训练侧）、AWorld 的 MCP 沙盒。
