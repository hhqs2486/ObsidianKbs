# 轨迹评估

## 一句话定义
> 轨迹评估是对 Agent 执行全过程（思考-行动-观察的每一步记录，即 trajectory）与最终结果（outcome）分别审视的评估方式，避免"说了但没做到"或"走歪却侥幸成功"的盲区。

## 它解决什么问题 / 为什么存在
- Agent "说了什么、做了什么"（轨迹）与"系统最终变成什么样"（结果）是两件事。只看轨迹会漏掉"说了但没做到"（如声称订单已创建但 DB 无记录）；只看结果可能看不出中间步骤走歪。
- 评测需双重覆盖，否则有系统性盲区。

## 核心原理（大二电子信息工程专业学生能懂）
- 轨迹（trajectory）= 状态→动作→奖励→新状态 的完整记录（第一章定义：每次任务的完整过程）。
- 经典例子（Anthropic）：机票预订 Agent 执行中发现航空公司政策漏洞，为用户找到更便宜方案——按预设路径打分会被判失败，但按最终结果看用户拿到更好方案。两类评测都应覆盖。
- 可观测性基础：追踪（Trace）用 span 树模型记录每次 LLM 调用/工具调用/检索（输入输出、耗时、token、错误），形成执行树，可回放（见 OpenTelemetry / OpenInference 标准）。
- 多轮任务的信用分配（credit assignment）：最终成败难归因到某一步——轨迹级记录是分析"哪步贡献最大"的前提（与[[后训练]]的奖励设计呼应）。

## 关键参数 / 易错点
- 轨迹与结果都要评，不能偏废。
- 生产轨迹可脱敏后沉淀为回归测试用例（可观测性→评估资产的闭环）。
- 多 Agent 系统的跨 Agent 追踪比微服务调用更复杂。

## 类比（帮助理解）
- 像考试既看"解题步骤"又看"最终答案"：步骤对答案错、步骤错答案对，都是不同问题。
- 像行车记录仪：不仅看是否到达目的地，还看一路有没有违章。

## 设计时怎么用（反推思维）
> 评估 Agent 时，我会同时检查轨迹（是否合规、有无绕路）与结果（是否达成），并用 span 树追踪回放定位失败环节。

## 典型应用 / 我在哪见过
- Anthropic 机票案例、LangSmith/Langfuse 的 trace 回放、生产日志诊断（见[[代码生成]]的系统适配器）。
