# 评估

## 一句话定义
> 评估是为 Agent 系统建立可重复、可量化的测试与对比体系，用以科学决策（模型选型、架构优化、持续迭代），而非凭直觉判断好坏。

## 它解决什么问题 / 为什么存在
- 构建 Agent 时面临大量无标准答案的选择（用哪个模型、哪些工具、怎么组织提示词）。评估提供"改变一个变量看效果"的对比实验，以及"逐一关闭组件看贡献"的消融实验，区分真实能力提升与表面波动。
- 核心认识：评估对象应是"模型 + Harness 的组合体"，而非仅模型。同一个模型在不同 Harness 表现可能迥异——表现不佳时瓶颈可能在 Harness 而非模型。

## 核心原理（大二电子信息工程专业学生能懂）
- 三层体系（图6-1）：
  1. 评估环境（"在哪里测"）：工具调用型（Verifiers，靠可执行验证）与人机交互型（τ-bench，用 LLM 模拟用户）。
  2. 评估方法（"怎么判"）：数据集设计、指标体系、LLM-as-Judge、配对比较与排名。
  3. 评估驱动决策（"测了干什么"）：模型选型、架构优化、持续迭代。
- 两类诊断手段：消融实验（关掉 Harness 某组件看整体变化） vs 模型替换实验（固定 Harness 只换模型）——前者定位 Harness 内部重要部件，后者区分瓶颈在模型还是 Harness。
- 统计显著性：分差小于噪声带宽时不切换模型；同批任务上用配对分析（如 McNemar 检验）比"两个独立成功率相减"更灵敏；警惕多重比较的假阳性。

## 关键参数 / 易错点
- 模型快速演进时代，新模型公开基准更好≠在你的任务更好，甚至可能回归（regression）；必须在自己的评估集上完整测试。
- 看到分数下降先查评测系统本身（资源不足、评分器 bug、用例脱节），再动 Agent。
- 评估环境与后训练环境往往同源，但评估集题目必须与训练数据严格隔离（防泄漏）。

## 类比（帮助理解）
- 像软件工程的"没有度量就没有改进"：不建可重复评估，迭代方向只能靠猜。
- 像给汽车做碰撞测试：同一辆车在不同测试场地（Harness）成绩不同，要分清是车不行还是场地不行。

## 设计时怎么用（反推思维）
> 做 Agent 系统时，我会先搭可复现评估环境+数据集，用消融/模型替换定位瓶颈，再据统计显著性做选型与迭代决策，而不是盲目换模型。

## 典型应用 / 我在哪见过
- Chatbot Arena 的配对排名、AndroidWorld 的 Benchmark→改进闭环、内部评估基础设施（消融、AB 测试、特性开关）。
